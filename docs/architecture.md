# Архитектура и активные ограничения дня 16

FastAPI обслуживает API и статический клиент без сборки. SQLite — из стандартной
библиотеки; версии прямых зависимостей заданы в `requirements.txt`, включая
официальный MCP SDK. Клиент ничего не загружает из сети: ни библиотек, ни
шрифтов, ни иконок. Python >=3.11; переносимые команды — в корневом Makefile.

## Промпт, контекст и метрики

- Каждый вызов в `app/llm.py:build_payload` требует `provider.require_parameters`,
  отключает `context-compression` и запрашивает `usage: {"include": true}`.
  Токены и стоимость сообщает провайдер; своих оценок нет.
- `Agent.context_cut` — единственный разбор стратегии: `full` отправляет всю
  историю; `window` последние `keep_last` реплик; `summary` сводку и хвост.
  Незнакомая сохранённая стратегия читается как `full`; числа без выбранной
  стратегии ничего не обрезают. На API неизвестная стратегия — 400.
  `strategy` остаётся строкой, не bool/Literal; bool не принимается как число.
- Обрезка только явно выбранная и всегда названа: `dropped` — отброшено окном,
  `summarized` — заменено сводкой. Память добавляется при любой стратегии,
  ничего не заменяет и не получает такой приписки. У окна нет зажима по памяти.
- Без сводки или без `keep_last` стратегия `summary` отправляет всю историю;
  покрытие плюс хвост равно длине истории. `summary_cover` зажимает `upto`
  длиной истории, в том числе после снятия пары для перегенерации.
- Сжатие не меняет полную `self.history`. Граница округляется вниз до чётного,
  чтобы вопрос и ответ не разделялись. Сжатие инкрементально: предыдущая
  сводка плюс новые реплики; `response_format` и `stop` у него сняты.
- `build_compress_prompt` не получает системный промпт чата, память, профиль,
  состояние задачи и инварианты: пересказ не должен дублировать эти сведения.
  Ведение памяти не вызывает модель; обмен — ответ и, при выборе, сжатие.
- Системное сообщение максимум одно: `spec.system`, заполненные поля профиля,
  правило этапа, жизненный цикл, инварианты — через пустую строку.
  Если ни один блок не задан, системного сообщения нет, включая режим задачи.
  Это распоряжения человека; сведения и сводка идут ролью `user` с подписью.
- Порядок: system → долговременная память → рабочая память → задача →
  врезка стратегии → хвост → вопрос. Подписи `[долговременная память]`,
  `[факты о разговоре]`, `[задача]` и строки «подпись типа: содержимое» —
  часть промпта; изменение хранения не повод менять их. Закрывающая подпись
  памяти нейтральна, она не обещает, что дальше идут только сообщения истории.
- Долговременная память, профиль и инварианты снимаются один раз на обмен
  в `ask` после сжатия. Один снимок передаётся сборке промпта и слотов;
  сторож использует его же. Для рабочей памяти также сохраняйте требование
  согласованного чтения для промпта и слотов, без расходящихся снимков.
  `Agent.prompt_head` собирает начало и берёт номера из его текущей длины.
  `PROMPT_SLOTS`: `memory_at`, `working_at`, `task_at`, `summary_at`;
  отдавать их нужно вместе, не отдельными копиями формулы. Ноль — законный
  индекс, отсутствие — только `None`; клиент сравнивает строго.
- `start` несёт `resolved_messages`, слоты и `strategy`. Клиент не ищет
  врезки по тексту. `SERVICE_CALLS` — одна карта подписей ролей и статусов;
  ветки `promptRole` идут в порядке промпта. У `window` `summary_at` отсутствует.
- `Agent.service_plan` определяет служебные вызовы. `compressing` приходит
  перед настоящим вызовом с `strategy`; без события клиент не обещает паузу.
- `Agent.usage_summary` суммирует метрики ответов и сводок; клиент показывает
  `usage_total`. Неизвестное не становится нулём. Сжатие оплачено и учитывается
  в суммах, но не увеличивает `history_len` и плитку «Сообщений».
  Метрики служебного вызова хранятся рядом с результатом в `summaries`.
  Врезки памяти не порождают отдельного вызова; их текст входит во входной
  промпт и может увеличивать его токены и цену.

## Хранение и очистка

- `app/store.py`: запись через `tx()` с `BEGIN IMMEDIATE`; занятая база —
  `StoreBusyError` и HTTP 503, не 500. Транзакция отдаёт обёртку `_Writer`,
  не соединение; `redact()` чистит любой строковый параметр SQL.
- История целиком одной транзакцией: DELETE плюс executemany, PK
  `(session_id, seq)`, номера от нуля без дыр. Сводки — отдельная таблица
  `summaries` с таким же PK и порядком записи; у каждого сжатия свои метрики.
- У редактируемых записей `memory`, `working_memory`, `invariants` seq —
  AUTOINCREMENT: правка не перенумеровывает, удалённый номер не переиспользуется.
  У рабочей памяти индекс по `session_id`; глобальная память читается целиком.
  Id агентов и счётчики имён выдаёт база, чтобы процессы не пересекались.
- `_migrate` вызывается из `Store.init` после executescript и идёт через `tx`,
  включая чтение колонок. Миграция идемпотентна, сохраняет записи пользователя,
  снимает `author` у обоих слоёв памяти, удаляет `facts` и `working_state`.
  Удалить пользовательскую базу вместо миграции нельзя.
- Каскада и FK нет: каждый путь очистки обязан явно выполнить свою часть.
  Таблица ниже — граница владения, включая то, что намеренно остаётся.

| Слой | delete_session | clear / kill_all | Agent.forget |
|---|---|---|---|
| messages | удалить | удалить | удалить |
| summaries | удалить | удалить | удалить |
| working_memory | удалить | удалить | удалить через clear_working |
| task_state | удалить | удалить | удалить |
| branches | удалить свою строку | удалить | оставить |
| memory | оставить | удалить | оставить |
| profile | оставить | удалить | оставить |
| invariants | оставить | удалить | оставить |

## Память и профиль

- Три слоя: краткосрочный — реплики, рабочий — состояние задачи в
  `working_memory(session_id, kind, content, at)`, долговременный — глобальная
  `memory` без session_id. Сводки — производный контекст рядом с репликами,
  не отдельная память. В оба редактируемых слоя пишет только человек через
  ручные операции; агент не выводит из разговора правки и не ведёт слой сам.
  У записей нет author, курсора прочитанного и метрик служебного вызова.
- `WORKING_KINDS`: цель, ограничение, решение, открытый вопрос; долговременные
  типы: о собеседнике, решение, факт. `WORKING_LABELS`/`MEMORY_LABELS` — общие
  карты для промпта и показа. В интерфейсе везде «тип записи».
- Область рабочей памяти — `/api/agents/{id}/working`, долговременной —
  `/api/memory`. `_record_body` общий; `_kind_field` получает список слоя:
  тип при добавлении обязателен, умолчания нет. `_content_field` требует
  непустой текст; лишние поля и пустая правка — 400, чужой номер — 404.
- Пусто или хранилища нет — врезки нет вообще (`memory_items`, `working_items`);
  выключателя памяти у чата нет. Слой глобальный не копируется при ветвлении.
- Профиль про форму ответа, инварианты про суть решения. `PROFILE_FIELDS`
  (style, format, context) — свободный текст с `PROFILE_LABELS`, не закрытый
  список и не четвёртый слой памяти. Только человек пишет через GET/PATCH
  `/api/profile`; профиль глобальный, не AgentSpec и не колонки sessions.
- `profile(field PK, content, at)` хранит непустые поля; пустая строка удаляет
  строку. `_profile_field` отвергает не-строку; PATCH обновляет только названное.
  `[как отвечать]` включает только заполненное. Пустой/отсутствующий профиль
  не создаёт ни блока, ни системного сообщения; ветка его не копирует.

## Ветвление

- Ветка — отдельная sessions с собственным id, копией конфига и первых `at`
  сообщений; PK messages не меняется. `Agent.detach` обеспечивает одного
  владельца сессии: save_history начинается с DELETE. Продолжения независимы,
  ветвление работает поверх любой стратегии, не является стратегией контекста.
- Родитель только читается (`carry_off`); `take_branch` пишет свою сессию.
  Можно ветвиться у занятого родителя, уносятся записанные сообщения.
  Проверка неизменности базы родителя должна смотреть до его следующего persist.
- `_fork_point`: пропуск, не-целое, отрицательное или больше длины — 400,
  без молчаливого зажима. Ветка получает seq от нуля без дыр.
- Сводки копируются только с `upto <= at`, целым префиксом; рабочая память
  копируется вся с новыми номерами. Метрики сохраняются; копии в памяти глубокие.
  Задача переносится целиком, с отметкой входа в этап, собственным объектом.
- Происхождение — `branches(session_id PK, parent_id, forked_at)`, не config.
  forget сохраняет происхождение. По parent_id ничего не удаляется: удаление
  родителя не удаляет ветку. Сервер присылает только id; клиент ищет актуальное
  имя и явно показывает «ветка от удалённого чата», если родителя уже нет.
- «Ветка отсюда» есть у каждого ответа при любой стратегии и копирует
  сообщения по карточку включительно (`index + 1`).

## Состояние задачи

- Человек управляет строгой машиной: stage, step, expects в `task_state`,
  строка на чат. Модель не определяет и не переключает этап. Слеш-команды
  `/task`, `/task-next`, `/task-step`, `/task-expect`, `/task-pause`,
  `/task-resume`, `/task-off` разбирает клиент; сервер получает обычные поля.
  При запуске `/task` посылается описание; правки шага/ожидания, пауза и
  выключение не создают обмен. Успешный next/resume запускает обмен перехода.
- `TRANSITIONS` в `app/schema.py` — единственная таблица ходов; нет ребра —
  409 без изменения состояния. done терминален, пауза возможна с любого
  незавершённого этапа и возвращается в paused_from; из проверки назад нельзя.
- `GATED_MOVES`/`gate_shut` закрывают next, пока на этапе нет записанного
  ответа. `stage_at` меняется при переходе, не при правке текста/общего at.
  Отказ 409 называет этап и ожидаемое действие. Ворота не ограничивают паузу,
  resume или незаконные ходы; последовательные осознанные next допустимы.
- stage и expects хранятся; пустое expects использует `STAGE_EXPECTS`,
  смена этапа сбрасывает прежнее. `[задача]` — user-врезка; правило
  `STAGE_RULES` и весь `[жизненный цикл задачи]` — части system.
  `lifecycle_block` строится из TRANSITIONS с текущим этапом, командами и
  запретом работы чужого этапа; MOVE_LABELS/MOVE_COMMANDS/STAGE_EXPECTS
  не дублируют карты. Блок не заводит слот и отдельное сообщение.
- Нет состояния или этап неизвестен — нет врезки, правила и блока автомата.
  Сама строка — единственный факт режима, поля конфига о нём нет.
- `_task_save`/`stop_task` меняют память только после успешной записи базы.
  Необязательный `from` в PATCH проверяет этап, увиденный человеком:
  несоответствие — 409 с обоими этапами; без from дополнительной сверки нет.
- Наружу задача идёт только полем task у чата, без второй ручки чтения.
  У выгруженного чата тоже: LEFT JOIN в list_sessions, общий `task_view`
  для списка, шапки и врезки; отдельного запроса на каждый чат нет.
- `runCommand` снимает id до запроса, сверяет после и держит замок команды.
  Переключение чата не посылает обмен в новый чат, двойной Enter не делает
  двойной ход. Шапка видна только при режиме: этап словами, шаг, ожидается;
  кнопок управления нет, пауза различима без цвета. Неверная команда не
  посылает запрос; объяснение стоит под вводом. Отказ не пишется в историю.

## Инварианты и сторож

- Глобальная `invariants` без session_id; виды `INVARIANT_KINDS` с
  `INVARIANT_LABELS`: архитектура, техническое решение, ограничение стека,
  бизнес-правило. Названия не совпадают с типами соседних слоёв. Только человек
  пишет через `/api/invariants`; ветка ничего не копирует.
- `[чего нельзя]` — последняя часть единственного system, без своего слота.
  Пустой/отсутствующий слой не создаёт блока. В промпт идут вид и текст,
  список banned туда не добавляется: это настройка сторожа, не второе правило.
- `banned` — JSON-массив в колонке. Общие `_record_body`, `_kind_field`,
  `_content_field` плюс `_banned_field`: список строк, пустой список допустим,
  не-список и пустое слово — 400. По умолчанию список пуст, проза работает сама.
- `banned_hits` проверяет полностью собранный ответ в ask до коммита,
  по тому же снимку инвариантов, что видел промпт. Ищет целые слова без учёта
  регистра, границы `_EDGE` «не буква и не цифра», не `\b`: поддерживает
  кириллицу, латиницу, C++, .NET; Java внутри JavaScript не совпадает.
  Морфологии нет, словоформы не ловятся.
- `BANNED_METRIC`/banned_hits — метрика обмена, не провайдера и не сумма по
  чату. Новых таблиц, колонок или счётчика попаданий нет. Сохраняются слово
  и правило на момент обмена; `invariant_line` задаёт общую форму показа.
- Сторож только отмечает: не скрывает/режет/переписывает ответ, не вызывает
  модель заново, не проверяет сжатие и не разбирает отрицания эвристиками.
  Следующий вопрос видит полный оплаченный ответ.
- `guardLine`/`.card-guard` — отдельная видимая строка даже без токенов;
  показывает слово и правило: «задело запрет», не автоматический приговор.
  Ложные совпадения (законный отказ, цитата вопроса, имя пакета) и пропуск
  словоформ должны быть объяснены в подсказке, коде и документации продукта.

## Клиент и независимый стенд

- Оболочка: список чатов слева, общая шапка с именем выбранного чата,
  переключателем «Чат»/«Настройки» и глобальным профилем справа. Настройки
  занимают центральную область с шестью подписанными страницами; на телефоне
  навигация становится сеткой, список чатов — модальным ящиком. Скрытые области
  недоступны фокусу; Escape и закрытие возвращают фокус открывшей кнопке.
- `showWorkspace` меняет видимость смонтированных ленты и форм, не вызывает
  `openAgent` и не останавливает поток. Сохраняются черновик, положение ленты,
  выбранный раздел, его прокрутка и незаписанные поля. Шапка задачи находится
  над обеими областями; шесть серверных метрик — общей строкой снизу.
- Аватар — вход в существующий профиль `style`/`format`/`context`, без имени,
  фотографии или авторизации. Меню показывает ответ API, редактор один.
  Грязные поля профиля не затирает повторное чтение; PATCH меняет только
  тронутое поле, ошибка сохраняет текст и видимую причину для повторной попытки.
- «Показать промпт запроса» есть при любой стратегии, когда промпт получен,
  и привязывается только к committed обмену: failed start не занимает ключ
  прежнего ответа. `state.prompts` живёт только в памяти вкладки, не в базе.
- Панель контекста показывает только действующие поля (CONTEXT_LABELS,
  syncStrategyFields): full без чисел, window с размером, summary с двумя.
  Начальная разметка прячет поля, переключение меняет показ сразу.
  Скрытие не меняет сохранённые значения; API принимает числа при любой стратегии.
- Краткосрочный раздел повторяет `context_cut`/`summary_cover` по сохранённому
  конфигу и входам из API, не по ещё несохранённой панели. Если API станет
  отдавать готовый срез, копию расчёта убрать.
- `PANEL_TABS` перечисляет страницы поимённо. «Память» показывает
  «Краткосрочная — реплики», «Рабочая — записи о задаче»,
  «Долговременная — записи навсегда»; loadMemory ленивый, одной ручкой на слои.
  Отрисовка не делает запросов. При смене чата/обмене перечитывать только
  при видимой области «Настройки» и открытой вкладке. Профиль/инварианты/
  инструменты тоже загружаются лениво. Повторное чтение не пересоздаёт активный
  редактор записи; неуспешная правка оставляет редактор и текст для повтора.
- Поля памяти, профиля и инвариантов без f-: это префикс конфига чата,
  общий change не должен посылать PATCH чата за правку другого слоя.
- `startRecordEdit` общий для памяти и инвариантов, различия параметрами
  (в том числе banned/redraw); тип меняется вместе с текстом. Enter и уход
  фокуса сохраняют, Escape отменяет; пустое/неизменное ничего не отправляет.
  settled предотвращает дубль Enter/focusout, завершение на блоке сохраняет
  возможность перейти к списку типов. PATCH содержит только тронутое.
- При правке первый пункт «— оставить тип —», при добавлении
  «— выберите тип —»/«— выберите вид —», ничего не предвыбрано.
  `fillKinds` получает список слоя; пустой текст/тип не отправляется.
  Форма рабочей памяти скрывается вместе с недоступным слоем.
- «Запомнить надолго» только заполняет общую форму строкой working_lines,
  сбрасывает тип и ждёт человека. Автозаписи/второй формы/дедупликации нет.
  Список пополняется ответом API с id и очищенным текстом, не телом запроса.
- Профиль — только поля с примерами в placeholders. На change отправляется
  тронутое поле; показывается записанное значение из ответа после redact.
  Инварианты: список, правка на месте, удаление и форма без выбранного вида.
- `checks/dom.js` независимо повторяет серверное поведение: один promptHead
  для промпта и start обоих потоков, включая system/инварианты; одна формула
  слотов, свои task-ворота. RecordBody не принимает больше сервера:
  обязательный тип, 400 для пустого/лишнего, устойчивые id. Рабочие записи
  живут в состоянии стенда, правка не исчезает при следующем чтении.

## MCP

- В день 16 менеджер подключает stdio, initialize и tools/list; модель
  инструменты не вызывает. `McpManager.call` проверяется локально.
  `mcp.json` принадлежит приложению; MCP_CONFIG_PATH меняет путь.
  Команда всегда sys.executable, cwd — корень репо.
- Нет файла или MCP_DISABLED=1 — ни процессов, ни инструментов;
  `/api/mcp` возвращает `{"servers": []}`. Стандартные проверки выключают MCP,
  MCP-проверки включают только локальными фикстурами через `_mcp_env`.
- Дочерний env только CHILD_ENV_KEYS (PATH, HOME, LANG), никогда весь
  os.environ: ключ OpenRouter не наследуется. Зонд перечисляет env в отказе
  initialize, а не делится файлом через отсутствующий TMPDIR.
- Процессы запускает менеджер через anyio.open_process, не stdio_client;
  протокол — ClientSession SDK (initialize, tools/list, tools/call).
  stop посылает terminate всем, через две секунды kill оставшимся.
  Проверять выход и SIGTERM отдельно от запасного SIGKILL. Строкам транспорта
  нужен перевод строки, иначе stdout-помпа ждёт в буфере.
- Коллизии: оба инструмента получают `сервер__инструмент`, голого имени
  не остаётся. API и UI показывают настоящее вызываемое имя.
- Ошибка сервера — down с причиной, соседние серверы и приложение стартуют.
  Соединение одно на сервер за старт; переподключения нет. Описание/схема
  показываются как получены, мусор stdout приводит к ошибке транспорта.
- «Инструменты» только показывает серверы, статусы, описания, свёрнутые
  схемы; полей редактирования нет. Пусто явно названо «MCP не подключён».
  Имена серверов и вызываемые имена инструментов отделены от описаний;
  длинный текст переносится, JSON имеет ограниченную прокручиваемую область.
  В день 16 запрос один на открытие видимых инструментов, без таймера.
  `toolsVisible` учитывает рабочую область и видимость документа; уход
  отменяет незавершённый GET, поздний ответ не заполняет скрытую страницу.

## Проверки

- `make check` вызывает checks/run_checks.py один раз, включая spawn_100,
  restart, two_processes и browser_check. Проверки offline: stream_completion
  подменяется checks/_stub.py, каталоги моделей тоже локальны, ключ не нужен.
  MCP-фикстуры — настоящие локальные процессы, без живых LLM-вызовов.
- Browser_check исполняет настоящий app/static/app.js под Node на dom.js
  с DOM и SSE. Grep не заменяет клиентские проверки. Не заводить проверки
  документационных формулировок, мета-проверки, самопроверки стенда или
  таблицы запрещённых слов вместо поведения. Объём проверок меньше продукта.
- Сценарные помощники не содержат утверждений и не прячут измеряемые числа,
  обмены/счётчики вызовов/сравнения: они видны в проверке. `_body_rules`
  возвращает нарушения, утверждение остаётся снаружи. Подмену и восстановление
  делают patch.object/patch.dict, без собственного дублирующего помощника.
- CLEANUP_TABLE/CLEANUP_PATHS — единая матрица удаления и сохранения всех
  слоёв. `_filled_chat` заполняет их заранее, рабочую память вручную.
  Проверять пустоту после очистки только на предварительно непустом слое;
  обратные утверждения о сохранении так же обязательны.
- Различающее утверждение использует различающие данные: общий тип
  «решение» не доказывает выбор списка слоя, берите «открытый вопрос» или
  «о собеседнике»; у инвариантов — свой исключительный вид.
- Проверка влияния памяти сравнивает ответ с пустым/непустым слоем по
  функциональной заглушке reply(messages, index). Остальной промпт одинаков,
  вызовов поровну; проверяются оба слоя. Утверждение о промпте должно
  подтверждать условие ответа заглушки. Offline-результат не обещает
  поведение живой модели; живой прогон отдельно выполняет человек.
