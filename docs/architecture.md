# Активные инварианты day-20

Перед изменением прочитайте затрагиваемые разделы. Это ограничения текущего
приложения, а не история заданий; источники указаны рядом с правилами.
Стек: FastAPI, uvicorn, httpx, MCP SDK (`requirements.txt`), SQLite стандартной
библиотеки и ванильный JS. Клиент не загружает шрифты, библиотеки или иконки из сети.

## Хранение, история и очистка

Источники: `app/store.py`, `app/registry.py`, `app/agent.py`.

- Транзакция начинается с `BEGIN IMMEDIATE`; занятая база даёт 503.
  `tx()` отдаёт обёртку, которая применяет `redact()` ко всем строковым
  SQL-параметрам. Записи и миграции проходят через неё, без обхода соединением.
- История — пары user/assistant, PK `(session_id, seq)`, номера от нуля без
  дыр. Снимок истории сохраняется целиком одной транзакцией (`DELETE` и
  вставки). Сжатие не меняет `self.history`; перегенерация снимает последнюю
  пару и восстанавливает её с проверкой длины. Tool-сообщения туда не попадают.
- `summaries` хранит последовательность сводок и их метрики, PK
  `(session_id, seq)`; снимок переписывается одной `tx()`, номера без дыр.
  `memory`, `working_memory`, `invariants` имеют устойчивые AUTOINCREMENT id:
  правка не перенумеровывает записи, удалённый номер не используется снова.
  У рабочей памяти есть индекс по чату; глобальная память читается целиком.
  Идентификатор агента выдаётся базой (`claim_agent_id`), в том числе между процессами.
- Миграция живой базы идемпотентна, сохраняет записи и идёт через `tx()`;
  удалять пользовательскую базу вместо миграции нельзя. Текущая миграция
  снимает `author` обоих слоёв памяти и удаляет старые `facts`/`working_state`.
  У рабочей памяти нет курсора покрытия истории или метрик служебного вызова.
- Каскада и FK нет: очистка каждого слоя явная. Родство не содержимое
  разговора; глобальным слоям отдельный чат не владелец.

| Слой | `Agent.forget` | `delete_session` | `Store.clear` |
| --- | --- | --- | --- |
| История, сводки, рабочая память, состояние задачи | удалить | удалить | удалить |
| `branches` | оставить | удалить строку чата | удалить |
| `memory`, `profile`, `invariants` | оставить | оставить | удалить |

- Ветка — самостоятельная сессия с новым id, глубокими копиями конфига и
  первых `at` сообщений. Третьей координаты в PK истории нет. Родитель при
  ветвлении только читается, даже если занят; его история и родство не пишутся.
  У сессии один владелец (`detach`), иначе сохранение снимка стёрло бы чужой хвост.
- `at` обязателен: нецелое, отрицательное или больше длины истории — 400,
  без молчаливого зажима. Кнопка на каждом ответе уносит историю по него включительно.
  `branches` хранит `parent_id`/`forked_at` отдельно от конфига; удаление родителя
  не удаляет ветку. Сервер отдаёт только id родителя, клиент разрешает имя
  из списка чатов и обозначает удалённого родителя.
- Ветка берёт префикс сводок с `upto <= at`, всю рабочую память с новыми
  номерами и всё состояние задачи, включая отметку этапа. Копии независимы,
  метрики перенесённых ответов и сводок сохраняются. Глобальные слои не копируются.

## Промпт, контекст и метрики

Источники: `app/agent.py`, `app/llm.py`, `app/schema.py`.

- Каждый payload требует `provider.require_parameters`, отключает плагин
  `context-compression` и запрашивает `usage: {"include": true}`. Токены и
  стоимость сообщает провайдер, своих оценок нет.
- Выбор стратегии разбирается в `context_cut`: `full` — вся история;
  `window` — ровно последние `keep_last` реплик без зажима по памяти;
  `summary` — сводка плюс хвост. Незнакомая стратегия внутри расчёта — `full`,
  числа без выбора стратегии историю не режут. На API чужая стратегия — 400;
  поле строковое, не `bool`/`Literal`, bool не принимается за число.
- При `summary` без сводки или без `keep_last` передаётся вся история.
  `summary_cover` зажимает `upto` длиной истории; граница сжатия округляется
  вниз до чётного. Сжатие инкрементально: предыдущая сводка плюс новые пары.
  `summarized` называет заменённое начало, `dropped` — отброшенное окном;
  вставки памяти ничего не заменяют и этих метрик не получают.
- Единственное системное сообщение собирает `system_message`: промпт чата,
  заполненные поля профиля, правило этапа и граф задачи, инварианты, через
  пустые строки. Системная роль — распоряжения человека. Сводка и сведения
  памяти — роль `user` с явными подписями. Пустые/отсутствующие слои не
  создают блоков; без всех распоряжений системного сообщения нет.
- Порядок `prompt_head`: system → долговременная память → рабочая память →
  состояние задачи → сводка → хвост истории → вопрос. Подписи:
  `[долговременная память]` с нейтральным закрытием, `[факты о разговоре]`
  и строки «тип: содержимое» (`working_lines`), `[задача]`, подписанная сводка.
  Форму вставок не меняют попутно с устройством базы.
- `memory_at`, `working_at`, `task_at`, `summary_at` (`PROMPT_SLOTS`) берутся
  из длины уже собранного начала одним вызовом, не независимыми формулами.
  Слои читаются один раз на обмен и передаются в сборку промпта и слотов.
  Ноль — законная позиция, отсутствие — только `None`; у окна вставки нет.
  Кадр `start` несёт `resolved_messages`, слоты и `strategy`: клиент не
  ищет сводку разбором текста и не скрывает просмотр при пустом `summary_at`.
- `compress` снимает `response_format` и `stop`; его собственный промпт
  не получает системных распоряжений чата, памяти, профиля, задачи,
  инвариантов или инструментов. `service_plan` определяет реальные служебные
  вызовы; `compressing` выходит перед вызовом, с его `strategy`, без ложной паузы.
- `usage_summary` на сервере складывает метрики истории и отдельно сводок;
  клиент показывает `usage_total`. `history_len` считает реплики, а не сжатия.
  Вставки ручной памяти не вызывают отдельную модель, но увеличивают входной
  промпт и могут влиять на его токены/стоимость. Автоведения памяти нет.

## Редактируемые слои и сторож

Источники: `app/schema.py`, `app/main.py`, `app/store.py`, `app/agent.py`.

- Память заполняет человек через API/интерфейс; модель туда не пишет.
  Методы агента для рабочей памяти обслуживают ручные действия.
  Рабочая память — состояние задачи одного чата (`kind`, `content`, `at`),
  долговременная — сведения на всю базу без `session_id`, переживающие задачу.
  Сводки лежат отдельно, показаны рядом с краткосрочной историей и её не заменяют в базе.
- Карты `WORKING_KINDS`/`WORKING_LABELS`, `MEMORY_KINDS`/`MEMORY_LABELS`
  общие для промпта и показа. Рабочие типы: цель, ограничение, решение,
  открытый вопрос; долговременные: о собеседнике, решение, факт. «Тип записи»
  — единый термин интерфейса. Совпадение «решения» намеренно: область и срок
  жизни различают слои. Рабочие ручки — `/api/agents/{id}/working`, глобальные — `/api/memory`.
- `_record_body`, `_kind_field`, `_content_field` общие с параметрами слоя:
  тип добавления обязателен без умолчания, текст непустой, лишние поля и
  пустая правка — 400, чужой номер — 404. Правка меняет только названные поля.
- Профиль — распоряжения о форме ответа (стиль, формат, контекст), свободный
  текст `PROFILE_FIELDS`/`PROFILE_LABELS`, блок `[как отвечать]` только из
  заполненных полей. Это не слой памяти и не ограничения технического решения.
  Глобальная таблица `profile` по `field`, вне конфига; `/api/profile` GET/PATCH
  пишет только названные поля. Пустая строка удаляет поле; нестрока — 400.
- Инварианты — ограничения сути решения: архитектура, техническое решение,
  ограничение стека, бизнес-правило (`INVARIANT_KINDS`/`INVARIANT_LABELS`).
  Виды не совпадают с типами памяти. Глобальная таблица `invariants`,
  `/api/invariants`, только ручные записи. Блок `[чего нельзя]` системный,
  своего слота нет. `banned` хранится JSON-массивом; в промпт не попадает.
  Список строк необязателен и пуст по умолчанию; не-список, нестрока или пустое слово — 400.
- `banned_hits` проверяет целый готовый ответ до `_commit` по снимку правил,
  отправленному в этот обмен. Поиск без учёта регистра, границы «не буква и
  не цифра» для кириллицы/латиницы и слов со знаками (`C++`, `.NET`), не
  подстрока (`JavaScript`). Морфологии нет. Ложные совпадения при отказе,
  цитате или имени пакета явно названы в документации и подсказке интерфейса.
- Отметка `metrics.banned_hits` хранит слово и правило в форме `invariant_line`
  на момент обмена, переживает перезапуск, не входит в суммы по чату.
  Новых таблиц, колонок и счётчика для неё нет. Сторож не скрывает, не режет,
  не переписывает ответ, не проверяет сжатие, не вызывает модель для самопроверки
  и не разбирает отрицания. Совпадение судит человек.

## Состояние задачи

Источники: `app/schema.py`, `app/agent.py`, `app/main.py`, `app/static/app.js`.

- `task_state` — единственное состояние режима на чат: сохранённые этап,
  шаг, ожидаемое действие; флага режима в конфиге нет. Управляет человек
  командами `/task`, `/task-next`, `/task-step`, `/task-expect`, `/task-pause`,
  `/task-resume`, `/task-off`, которые разбирает клиент. Сервер не разбирает
  слеши; модель не выбирает этап и её ответ не меняет автомат.
  `/task` отправляет описание, переходы — фразу для нового этапа после
  успешного изменения состояния (при наличии ключа); шаг/ожидание и
  выключение режима сами обмена не вызывают.
- `TRANSITIONS` — один граф для API, команд и системного блока
  `[жизненный цикл задачи]`: весь граф, текущее место, команды и запрет чужого
  этапа. `MOVE_LABELS`/`MOVE_COMMANDS` также задают умолчания `STAGE_EXPECTS`.
  Недопустимый ход — 409 без изменения; готово терминально, пауза возвращает
  в `paused_from`, обратного хода из проверки в выполнение нет.
- `GATED_MOVES` запрещает `next` с этапа без записанного ответа:
  `stage_at` меняет только переход, не правка шага. Отказ называет этап и
  ожидаемое действие и не попадает в историю. Ворота проверяют пустоту,
  не задержку между командами; пауза/возврат не ограничены.
- Заданное `expects` хранится, пустое использует умолчание этапа, переход
  сбрасывает старое. Состояние в памяти меняется после успешной записи базы;
  снятие режима атомарно. Необязательное `from` защищает от перехода из
  устаревшего состояния другой вкладки: несовпадение — 409 с обоими этапами.
- Выключенный/незнакомый этап не создаёт вставки, правила или системного
  блока. Состояние выходит только полем `task` чата; отдельного GET нет.
  Выгруженные чаты получают его через `LEFT JOIN`, без запроса на каждую
  строку; общий `task_view` обслуживает список, шапку и промпт.
- `runCommand` фиксирует id до запроса и сверяет после; смена чата не
  отправляет обмен в чужой разговор. Замок команды предотвращает двойной
  Enter. Шапка видна только в режиме, показывает этап/шаг/ожидание; кнопок
  управления нет, пауза различима словами, неправильная команда не отправляется.

## Интерфейс

Источники: `app/static/app.js`, `app/static/index.html`, `checks/dom.js`.

- `CONTEXT_LABELS`/`syncStrategyFields` показывают только нужные числа:
  full — никаких, window — размер окна, summary — хвост и порог. Начальная
  разметка скрывает числа до синхронизации; выбор обновляет показ сразу.
  Скрытие не меняет конфиг, API принимает оба числа при любой стратегии.
- Просмотр промпта есть у каждого записанного обмена и любой стратегии;
  `state.prompts` живёт только в памяти вкладки, без хранения в базе.
  Привязка по `committed`: кадр start упавшего обмена не заменяет промпт
  прошлого ответа. Роли берутся из серверных слотов строгим сравнением,
  в порядке сборки; подписи и статусы стратегии — из одного `SERVICE_CALLS`.
- `PANEL_TABS` перечисляет все страницы поимённо. Память, профиль,
  инварианты загружаются лениво на открытие, не при каждой отрисовке.
  Слои памяти перечитываются при смене чата и после обмена, если вкладка
  открыта. Её разделы: краткосрочная — реплики, рабочая — записи о задаче,
  долговременная — записи навсегда. Расчёт «дословно» повторяет серверный
  `context_cut` по конфигу агента, не неприменённым полям; если API начнёт
  отдавать готовый расчёт, клиентскую копию следует убрать.
- Поля памяти, профиля и инвариантов без `f-`: эта приставка только у
  конфига чата. Профиль сохраняет на change лишь изменённое поле и показывает
  очищенное значение из ответа; подсказки в полях, без объясняющих абзацев.
- Единый `startRecordEdit` правит текст/тип памяти и инварианты на месте;
  `fillKinds` принимает список типов параметром. Enter/focusout блока
  сохраняют один раз (`settled`), Escape отменяет; пустая/неизменённая правка
  не шлётся. Выбор «— оставить тип —» пуст, PATCH несёт только изменённое.
  В формах добавления «— выберите тип/вид —» не предвыбран; без типа или
  текста нет запроса. Форма рабочей памяти скрывается вместе со слоем.
- «Запомнить надолго» заполняет существующую форму строкой `working_lines`,
  снимает тип и ждёт выбора человека; сама не пишет. Список пополняется
  ответом API, не телом запроса. Дедупликации нет: повтор — новая запись.
- Сторож показан отдельной `guardLine` даже без токенов: слово и правило,
  «задело запрет», без приговора. `toolBadge`/`toolLine` показывают вызов
  отдельной строкой сразу по SSE и затем из метрик одной функцией; ошибку
  обозначают «ошибка вызова:», перерисовка и перезагрузка её сохраняют.

## MCP, инструменты и оркестрация

Источники: `app/mcp.py`, `app/agent.py`, `app/mcp_servers/`, `mcp.json`.

- `mcp.json` принадлежит приложению: echo (стенд связи), git, remind,
  pipeline. Нет конфига или `MCP_DISABLED=1` — нет процессов/инструментов,
  `/api/mcp` пуст. Разработка через OpenCode/Pi не меняет этот конфиг.
- Менеджер запускает `anyio.open_process`; SDK `ClientSession` ведёт
  initialize, tools/list, tools/call. Дочернее окружение — только
  `CHILD_ENV_KEYS` (`PATH`, `HOME`, `LANG`), никогда всё `os.environ` с ключом.
  Протокол построчный, каждый ответ заканчивается `\n`.
- `stop` посылает terminate всем процессам, затем через две секунды kill
  оставшимся; стеки `AsyncExitStack` закрываются строго LIFO. При коллизии
  оба имени получают `сервер__инструмент`, голое исчезает. API/интерфейс
  показывают вызываемое имя. Маршрутизация только по `ToolRef` реестра.
- Стартовавший с ошибкой сервер изолирован: другие работают, его инструменты
  не объявляются, статус в `/api/mcp` — down. Упавший во время сессии не
  перезапускается автоматически, остаётся в списке до рестарта; вызов даёт ошибку.
- Payload содержит описания/схемы всех живых инструментов из `server.view`
  только при непустом реестре. Без него ключа `tools` нет, даже пустого
  списка; `tool_choice` не отправляется. Инструмент и длинный флоу выбирает
  модель, скрытого конвейера между инструментами/серверами нет.
- Цикл `Agent.ask` ограничен `MAX_TOOL_ITER = 4`: стрим → tool_calls →
  последовательное исполнение в порядке кадра → SSE `tool_call`
  `{name, server, arguments, result, ms, ok}` → assistant с tool_calls и
  tool-сообщения в рабочий список → следующий стрим. Битый JSON/упавший
  сервер — результат с ошибкой и `ok: false`, а не падение обмена.
  При лимите отдаётся накопленный текст с `tool_iterations`.
- История сохраняет только итоговую пару user/assistant. Usage складывается
  по итерациям (`_summed_usage`); `metrics.tool_calls` хранит `{name, server,
  ms, ok}` и не входит в суммы как отдельная плата. Сжатию инструменты не объявляются.
- Git-сервер запускает git в корне без shell, с таймаутом (`git_log`,
  `git_status`, `git_diff_stat`). Пустой вывод честно пуст, неверный ref — ошибка.
- Напоминания принадлежат базе сервера `data/reminders.db`, отдельной от
  Store и таблицы очистки, id AUTOINCREMENT. «Сработало» вычисляется при
  чтении по due_at, без фонового цикла и записи; повтор задаёт следующий срок
  и счёт от первого. `reminders()` возвращает список и согласованные waiting/fired.
  В чат напоминания не пишутся. `/api/mcp` получает их только у живого
  сервера с таким инструментом; отсутствие поля у других не роняет ручку.
- Вкладка «Инструменты» только показывает, лениво запрашивает, на пустом
  менеджере говорит «MCP не подключён». Опрос раз в 2 секунды только пока
  открыта, уход всегда гасит таймер.
- Pipeline search — `git grep -n -i -F --untracked`: игнорируемые файлы не
  читаются, сортировка (файл, строка) до limit; пустой результат назван с
  запросом. summarize механический, без LLM: дедуп строк, группы по файлам,
  неразобранное в «(без файла)», max_items ограничивает группы с числом обрезки.
  save_file пишет только в `files/` (`PIPELINE_FILES_DIR`), имя непустое,
  без `/`, `\` и `..`; отказ не создаёт файл. Каталог игнорируется Git.

## Проверки

Источники: `checks/run_checks.py`, `checks/_stub.py`, `checks/dom.js`,
`checks/browser_check.js`. `make check` запускает полный набор один раз,
включая spawn_100, restart, two_processes и клиентскую проверку.

- Проверяйте поведение, не исходный текст. Клиентская проверка исполняет
  настоящий `app.js` под Node.js на минимальном DOM с настоящими SSE-кадрами.
  Не добавляйте таблицы запрещённых слов для исходников/документации,
  самопроверки стенда или проверки про проверки; объём проверок держите меньше продукта.
- Помощники сцены не содержат утверждений и не скрывают измеряемое:
  обмены, число вызовов и сравнения остаются в проверке. `_body_rules`
  возвращает нарушения, утверждение стоит снаружи. Для подмен используйте
  стандартные `patch.object`/`patch.dict`, без собственного аналога.
- Очистку проверяет одна `CLEANUP_TABLE`/`CLEANUP_PATHS` на заполненном
  `_filled_chat`: проверяйте и удаляемые, и оставляемые слои. Утверждение
  об очистке пустого слоя ничего не доказывает. Для разных слоёв выбирайте
  различающие типы, а не общее «решение».
- DOM-стенд не принимает больше, чем API: общий разбор тела памяти,
  обязательный тип, валидация, устойчивые id, живые записи рабочего слоя,
  те же ворота задачи. У него своя независимая, но единственная `promptHead`
  для промпта и start успешного/упавшего потока, включая системные блоки.
- Заглушка умеет reply/tool_calls как функцию `(messages, index)`.
  Проверка влияния слоя сравнивает пустой и заполненный, отличающиеся только
  вставкой, при равном числе вызовов: различаются ответы, причина — вставка,
  рабочая и долговременная память действуют одинаковым способом. Дополняйте
  зависимый от заглушки ответ утверждением о самом отправленном промпте.
- `_stub` сохраняет deep-copy payload: поздние tool-сообщения не меняют
  снимок прошлого запроса. Сквозные проверки читают результат инструмента
  из следующего запроса, как его увидела бы модель.
- MCP по умолчанию отключён; его проверки включают фикстурный конфиг и
  настоящие subprocess. Проверяйте маршрутизацию, порядок tool-сообщений,
  метрик/бейджей, полный список живых инструментов и изоляцию down-сервера.
  Офлайн-заглушки не доказывают выбор инструментов живой моделью; такой
  прогон делает человек отдельно, результаты не выдумываются.
