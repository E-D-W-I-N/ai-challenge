# Архитектура и действующие инварианты day-17

Эти правила обязательны при изменениях соответствующей области. Источники:
`app/agent.py`, `app/store.py`, `app/schema.py`, `app/main.py`, `app/llm.py`,
`app/mcp.py`, `app/static/app.js` и поведенческие проверки в `checks/`.
Стек: Python >= 3.11, FastAPI, Uvicorn, HTTPX, MCP SDK (`requirements.txt`),
SQLite стандартной библиотеки; клиент без сборки и сетевых ресурсов.

## Промпт и контекст

- Каждый вызов (`build_payload`, `app/llm.py`) требует поддержки параметров
  (`provider.require_parameters`), отключает `context-compression` и просит
  `usage: {"include": true}`. Токены и стоимость — от провайдера, без оценок.
- `Agent.context_cut` — единственная точка выбора среза: `full` сохраняет всю
  историю, `window` оставляет ровно последние `keep_last` сообщений, `summary`
  заменяет покрытое начало сводкой. Пустой `keep_last` не режет; без сводки
  summary отправляет всю историю. Незнакомая сохранённая стратегия читается
  как full; API её отвергает с 400. Числа без стратегии не включают обрезку.
- `strategy` — строка, не bool и не Literal: разбор полей отбрасывает bool,
  `_choice_field` отвергает чужие значения с допустимыми вариантами (400),
  тип сохраняет round-trip конфига по полям датакласса.
- Срез не меняет `self.history`. Под ответом `dropped` называет отброшенное
  окном, `summarized` — заменённое сводкой. Память добавляется при любой
  стратегии и не получает отметку обрезки; ветвление также независимо от неё.
- `summary_cover` зажимает `upto` длиной истории, учитывая перегенерацию;
  граница сжатия округляется вниз до чётного (полные пары user/assistant).
  Сжатие инкрементальное: прошлая сводка плюс новые сообщения, не вся история.
- Служебное сжатие не получает `response_format`, `stop`, инструменты,
  системный промпт чата, память, профиль, задачу или инварианты. Оно пересказывает
  разговор, не ведёт память. `compressing` отправляется только перед реальным
  вызовом, с его `strategy`; план определяет `Agent.service_plan`.
- Сборка (`system_message`, `Agent.prompt_head`): единственное system-сообщение
  из промпта чата, профиля, правила этапа, графа задачи, инвариантов →
  долговременная память → рабочая память → состояние задачи → сводка → хвост
  истории → вопрос. Распоряжения — system; сведения — user с явной подписью.
  Без всех системных слагаемых системного сообщения нет.
- `PROMPT_SLOTS` (`memory_at`, `working_at`, `task_at`, `summary_at`) берутся
  вместе из длины уже собранного начала, не вычисляются повторными формулами.
  `build_prompt` и `prompt_slots` используют одну сборку. Ноль — законный
  индекс; отсутствие — только None. Window не создаёт врезку и слот сводки.
  Кадр start передаёт strategy для подписи врезки; клиент не ищет её по тексту.
- Память, профиль и инварианты читаются один раз на обмен: те же снимки идут
  в промпт, слоты и сторож. Конкурирующая правка не должна развести их.

## Хранение и очистка

- `Store.tx()` начинает `BEGIN IMMEDIATE`, отдаёт обёртку соединения, применяет
  `redact()` ко всем строковым SQL-параметрам. Занятая база — HTTP 503.
- История (`messages`) и сводки (`summaries`) — снимки с PK `(session_id, seq)`:
  DELETE + executemany, одной транзакцией, номера от нуля без дыр. У сводок
  отдельные строки с метриками каждого сжатия. Перегенерация снимает пару
  user/assistant (`take_last_exchange`); restore проверяет длину.
- `usage_summary` суммирует метрики истории и отдельным проходом — сводок.
  Клиент показывает серверный `usage_total`; `history_len` считает только
  сообщения. Срезы, banned_hits и записи инструментов в суммы не входят.
- Миграция `Store._migrate` после init идемпотентна и проходит через tx,
  включая чтение колонок и DDL. Сохраняет записи при снятии author из обоих
  слоёв памяти, удаляет устаревшие facts/working_state. Не требовать удаления
  живой базы для обновления схемы.
- Очистка явная, без FK-каскада; сохранение данных столь же обязательно:

  | Слой | delete_session | Agent.forget | clear |
  | --- | --- | --- | --- |
  | messages, summaries, working_memory, task_state | удалить | удалить | удалить |
  | branches | удалить свою строку | сохранить | удалить |
  | memory, profile, invariants | сохранить | сохранить | удалить |

  `forget` очищает рабочую память через `Store.clear_working`. Удаление родителя
  не удаляет ветки по parent_id. `kill_all` использует clear для изоляции проверок.

## Память и профиль

- Краткосрочная память — история; рабочая — записи задачи данного session_id;
  долговременная — глобальная memory без session_id, переживает удаление чата.
  Сводки — производные истории, показанные рядом с краткосрочным слоем.
- Оба редактируемых слоя наполняет только человек. Агент не добавляет,
  не правит, не удаляет память и не делает служебного вызова для её ведения.
  Врезки не требуют дополнительного вызова LLM, но входят в токены запроса.
- Рабочая память: устойчивый seq AUTOINCREMENT, индекс session_id, kind,
  content, at; без курсора, author и метрик. Долговременная: устойчивый
  seq AUTOINCREMENT, без владельца и индекса session_id. Правка не меняет
  номера, удалённые номера не выдаются вновь.
- `WORKING_KINDS`/`WORKING_LABELS` и `MEMORY_KINDS`/`MEMORY_LABELS` — общие
  карты для промпта и UI. Термин — «тип записи»: рабочие цель, ограничение,
  решение, открытый вопрос; долговременные о собеседнике, решение, факт.
  Срок жизни определяет слой, совпадение типа «решение» допустимо.
- `/api/agents/{id}/working` и `/api/memory`: при добавлении тип обязателен,
  `_kind_field` без умолчания; непустой текст (`_content_field`); лишние поля
  и пустая правка — 400, чужой номер — 404. `_record_body` общий для слоёв.
- Врезки user: `[долговременная память]` с нейтральным закрытием, рабочая —
  `[факты о разговоре]`, строки «подпись типа: содержимое» (`working_lines`).
  Схема хранения не повод менять форму, видимую модели. Пустой слой или
  отсутствие хранилища не создаёт сообщения.
- Профиль — распоряжение о форме ответа, не слой памяти и не ограничение
  решения. Глобальная таблица profile: field PK, content, at; поля свободного
  текста из `PROFILE_FIELDS`, подписи `PROFILE_LABELS` (стиль, формат, контекст).
- Пишет только человек через GET/PATCH `/api/profile`. `_record_body` и
  `_profile_field`: лишнее поле, пустая правка, нестроковый текст — 400;
  пустая строка удаляет поле; неназванные поля сохраняются. Только заполненные
  поля входят в system-блок `[как отвечать]`; пустой профиль блока не создаёт.

## Ветвление

- Ветка — самостоятельная sessions с новым id из базы, копией конфига и
  первых ровно at сообщений под собственным session_id. PK messages остаётся
  двухчастным. Копия глубокая, владелец сессии один (`Agent.detach`).
- `carry_off` только читает родителя, даже занятого; `take_branch` пишет свою
  сессию. Родительская история и родство не меняются, в том числе в базе до
  следующего persist родителя. `_fork_point`: отсутствующее, нецелое, отрицательное
  или превышающее длину at — 400, без молчаливого зажима.
- branches — отдельная таблица, PK session_id, parent_id и forked_at, не config.
  Сводки копируются только с upto <= at, с метриками; рабочая память целиком
  с новыми номерами; task_state целиком, включая stage_at. Глобальные слои
  не копируются. Новые сообщения и сводки родителя не меняют копию.
- Сервер отдаёт parent_id, имя берёт клиент из списка чатов. Удалённый
  родитель назван «ветка от удалённого чата». «Ветка отсюда» есть на каждой
  карточке ответа, при любой стратегии, копирует index + 1 сообщений.

## Задачи и инварианты

- Задачу двигает только человек. task_state — единственный факт режима,
  строка на чат: stage, step, expects, paused_from, stage_at. Флага в config
  нет. Слеш-команды разбирает клиент, сервер принимает обычный text.
  `/task` включает режим; после успешных `/task`, `/task-next`, `/task-resume`
  клиент при наличии ключа отправляет обмен с описанием/репликой перехода.
  Пауза, правка шага/ожидания и выключение обмена не отправляют.
- `TRANSITIONS` — источник переходов; незаконный ход — 409 без изменения.
  Готово терминально; пауза с любого незавершённого этапа возвращается туда же;
  из проверки обратно в выполнение хода нет. `next` из пустого этапа закрыт
  (`GATED_MOVES`, `gate_shut`), считает записанные ответы после stage_at,
  не правку текста. Пауза/resume не ограничены воротами.
- stage/expectations хранятся; пустое expects использует `STAGE_EXPECTS`,
  смена этапа сбрасывает заданное. Память меняется только после успешной
  записи базы, включая stop_task. PATCH с необязательным from отвергает
  несовпадение этапов (409); без from сверки нет.
- `STAGE_RULES` и весь `[жизненный цикл задачи]` — в общем system-сообщении;
  граф, текущий этап, команды и запрет работы чужого этапа из TRANSITIONS,
  `moves_from`, `MOVE_LABELS`, `MOVE_COMMANDS`. Состояние — user-врезка
  `[задача]`. Выключенный/незнакомый режим не создаёт блоков или слота.
- Наружу состояние идёт только полем task у чата, без отдельной GET-ручки.
  `task_view` общий для поля, врезки и шапки; выгруженные чаты получают данные
  через LEFT JOIN task_state в list_sessions, без запроса на каждый чат.
- Инварианты — глобальная таблица invariants без session_id, seq AUTOINCREMENT;
  только ручные `/api/invariants`. Виды `INVARIANT_KINDS`/`INVARIANT_LABELS`
  не пересекаются с типами памяти: архитектура, техническое решение,
  ограничение стека, бизнес-правило. Общие валидаторы записи плюс `_banned_field`:
  список строк, пустой допустим; не-список или пустое слово — 400.
- В system-блок `[чего нельзя]` едут вид и текст, никогда banned; список
  запрещённых слов хранится JSON-массивом для сторожа. Пустой слой блока
  не создаёт, отдельного слота нет; сжатие инварианты не получает.
- `banned_hits` проверяет целый готовый ответ до commit по снимку инвариантов
  данного обмена. Границы — не буква/цифра (`_EDGE`), не подстрока и не `\b`,
  без регистра, включая C++/.NET; морфологии нет. В метриках — слово и правило
  в форме `invariant_line` именно на момент ответа, без отдельной таблицы.
- Сторож ставит отметку, не прячет, не режет, не переписывает и не повторяет
  ответ; не проверяет сжатие, не зовёт модель, не разбирает отрицания и не
  создаёт счётчик срабатываний. Отказ, цитата, имя пакета могут дать ложное
  срабатывание; словоформа может быть пропущена. Ограничения названы в UI и
  документации, banned необязателен: проза правила работает без него.

## MCP и инструменты

- Нет конфига или `MCP_DISABLED=1`: нет процессов, инструментов, ключа tools;
  `/api/mcp` возвращает servers: []. Набор проверок по умолчанию отключает MCP,
  специализированные сценарии включают фикстурный `MCP_CONFIG_PATH` через `_mcp_env`.
- Менеджер запускает процессы через `anyio.open_process`, протокол ведёт SDK
  `ClientSession` (initialize, tools/list, tools/call), не stdio_client.
  Дочерний env — только `CHILD_ENV_KEYS`: PATH, HOME, LANG, без ключа OpenRouter.
  Сообщения stdio оканчиваются переводом строки. stop: terminate всем,
  через две секунды kill оставшимся; AsyncExitStack серверов закрываются LIFO.
- Коллизия имён: оба инструмента получают server__tool, голое имя удаляется.
  API/UI показывают имя, по которому инструмент действительно вызывается.
- `declared_tools` берёт описания/схемы из server.view. Только непустой реестр
  добавляет tools; `tools: []` и tool_choice не посылаются. Решает модель.
- `Agent.ask`: стрим → tool_calls → MANAGER.call с замером → SSE tool_call
  `{name, server, arguments, result, ms, ok}` → assistant(tool_calls) и tool
  на каждый вызов в рабочем списке → повторный стрим. `MAX_TOOL_ITER = 4`;
  на лимите отдаётся накопленный текст и метрика tool_iterations.
- Неверный JSON аргументов/ошибка сервера возвращаются tool-сообщением и
  ok: false, обмен продолжается. Usage суммируется по всем итерациям
  (`_summed_usage`), `metrics.tool_calls` хранит name/server/ms/ok.
- Tool-сообщения не сохраняются в базу: `_commit` пишет только user/assistant,
  следующий обмен видит итоговый ответ. Сжатию инструменты не объявляются.
- Git-сервер (`app/mcp_servers/git.py`): git_log, git_status, git_diff_stat,
  subprocess git в корне репозитория, без shell, с таймаутом. Пустой вывод
  допустим, ошибки git не скрываются. echo в mcp.json сохраняется как стенд
  связи. Упавший сервер остаётся down до перезапуска, reconnect не реализован.

## Клиент

- `SERVICE_CALLS` — одна карта подписей ролей/статуса; `promptRole` следует
  порядку врезок. Сравнение слотов строгое, None не подписывает сообщение 0.
  Просмотр промпта есть у каждого committed обмена при любой стратегии,
  включая full/window; упавший start не перезаписывает промпт прошлого ответа.
  `state.prompts` живёт только до перезагрузки вкладки, без таблиц в базе.
- `CONTEXT_LABELS`/`syncStrategyFields`: full без чисел, window с keep_last,
  summary с двумя числами и подписью хвоста. Скрыты уже в исходной разметке,
  меняются сразу на выборе; скрытие не меняет config, API принимает оба числа.
- `PANEL_TABS` перечисляет все страницы. Память показывает краткосрочные
  реплики/сводки, рабочие записи задачи и долговременные записи навсегда.
  loadMemory, loadProfile, loadInvariants, инструменты загружаются на открытие;
  render не делает запросов. Обновление памяти при смене чата/после обмена
  молчит при закрытой вкладке. Поля этих страниц без f- (это только config).
- `startRecordEdit` общий для памяти/инвариантов: текст и тип на месте,
  Enter/focusout блока сохраняют, Escape отменяет, settled не даёт дублирования;
  пустой/неизменённый текст не отправляется, тип «— оставить тип —», PATCH
  только тронутых полей. `fillKinds` получает список типов параметром;
  добавление требует явного типа «— выберите тип —» и непустого текста.
- Рабочая форма скрывается с недоступным слоем. «Запомнить надолго» только
  заполняет общую форму строкой working_lines, снимает тип и ждёт выбора
  человека; не записывает сама. Добавленная запись берётся из ответа API
  (номер/редакция текста); дедупликации нет.
- Профиль: три свободных поля с подсказками, без объяснительных абзацев;
  change отправляет только тронутое поле и показывает сохранённое из ответа.
  Инварианты используют общий редактор с `{banned, redraw}`, без второй функции.
- Краткосрочное «уезжает дословно» повторяет context_cut/summary_cover по
  конфигу агента, не несохранённым полям. Если API отдаст готовый срез, копию убрать.
- runCommand фиксирует id чата до запроса и сверяет после; при смене чата
  не отправляет обмен в чужой. Замок исключает двойной Enter. Шапка задачи
  только при включённом режиме: этап, шаг, ожидается; управление командами,
  без кнопок; пауза различима словами. Некорректная команда ничего не шлёт.
- guardLine — отдельная строка, видна и без токенов, называет слово и правило:
  «задело запрет», не приговор. toolBadge/toolLine — отдельная строка из
  живого tool_call до конца обмена и из metrics.tool_calls после перерисовки;
  одна функция для обоих путей, ошибка помечена «ошибка вызова:».
- Вкладка инструментов только показывает серверы/схемы, без полей;
  пустое состояние названо «MCP не подключён».

## Проверки

- `make check` вызывает checks/run_checks.py один раз: включает spawn_100,
  restart, two_processes и Node-проверку. `checks/browser_check.js` исполняет
  настоящий app.js с минимальным DOM и SSE-сервером `checks/dom.js`, не grep.
- Стенд независим от сервера, но формула promptHead одна для промпта/start
  обоих потоков и включает системные блоки. recordBody не щедрее API:
  обязательный тип, ошибки тела, устойчивые номера; рабочие записи живут
  между запросами, не создаются заново. Ворота задачи не слабее серверных.
- CLEANUP_TABLE/CLEANUP_PATHS — одна таблица удаления и сохранения всех слоёв
  на непустом `_filled_chat`, включая вручную добавленную рабочую память.
- «Память меняет ответ»: заглушка reply(messages, index) читает врезку;
  сравнить пустой/непустой слой, разные ответы, равенство остальных сообщений
  и числа вызовов; оба слоя проверяются. Это не свидетельство живой модели.
- Заглушка tool_calls принимает список или функцию тем же путём, что reply;
  сквозной тест проверяет настоящий результат инструмента в tool-сообщении
  второго запроса (`CALLS[1].payload.messages`). MCP-процессы настоящие,
  остановка проверяется выходом, включая несколько серверов и LIFO.

Исторические объяснения прежних реализаций и повторные формулировки удалены;
