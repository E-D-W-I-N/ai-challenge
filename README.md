# День 21 — индексация документов

🔥 День 21. Индексация документов

Возьмите набор документов:

👉 README / статьи / код / pdf → текст
👉 минимум 20–30 страниц текста суммарно (или эквивалент в коде)

Реализуйте пайплайн индексации:

👉 разбиение на чанки (chunking)
👉 генерация эмбеддингов
👉 сохранение индекса (FAISS / SQLite / JSON)

Усиление:

👉 добавьте метаданные к каждому чанку (source, title/file, section, chunk_id)
👉 сделайте минимум 2 стратегии chunking и сравните их:

- по фиксированному размеру
- по структуре (заголовки/разделы/файлы)

Результат:

Локальный индекс документов с эмбеддингами + метаданные + сравнение 2 стратегий chunking

## Реализация

`rag` — самостоятельный пакет внутри проекта. Загрузчик принимает только явно
перечисленные HTML URL или локальные HTML; сохраняет очищенные документы,
источники, заголовки, время получения и хэши. Обрабатывает Windows-1251 и
legacy layout с вложенными таблицами, сохраняет разделы, абзацы, списки и
технические строки таблиц. Frameset без статьи и ошибки загрузки не считаются
успешными документами. OCR/PDF и автоматического обхода сайта нет.

Для одного корпуса доступны fixed (1200 символов/180 overlap) и structural
(разделы/абзацы до 1200, длинные блоки с overlap). Structural — активная
стратегия по умолчанию. Метаданные чанка включают source/title/section/chunk_id,
смещения и хэш. SQLite хранит документы, тексты и нормированные векторы;
поиск — точный cosine без FAISS. Чат и MCP продолжают работать как раньше.

Эмбеддинги предоставляет независимо запущенный **oMLX** с OpenAI-совместимым
`/v1/embeddings`. Кандидат модели — `mlx-community/Qwen3-Embedding-0.6B-8bit`;
base URL и model ID задаёт оператор. Приложение не устанавливает oMLX, не
скачивает веса и не меняет модель генерации чата. Кэш зависит от полного
endpoint/model/dimensions/revision и текста. Смена весов под тем же ID требует
нового `--revision`. Неверный count/index, NaN/zero или mismatch размерности
останавливает сборку. HTTP oMLX не наследует proxy окружения.

Корпус предназначен для технических/исторических HTML `buran.ru`. Список URL,
снимки, индексы, вопросы и отчёты — локальные данные оператора, не часть Git.
Репозиторий не содержит подготовленного снимка ≥15000 очищенных слов:
объём нужно проверить в ingest-report и инспекторе после собственного запуска.
Ориентир задания: ≥15000 слов ≈30 страниц по 500 слов. Эвристики legacy HTML
требуют просмотра очищенного текста; счётчик сам по себе не подтверждает качество.

## Запуск индексации

Нужны Python ≥3.11 и Node.js для проверок. Прямые зависимости закреплены в
`requirements.txt`; дополнительных ML-библиотек нет.

```sh
make setup
# При необходимости: make setup PYTHON=/path/to/python
make help
```

Подготовьте **локальный** JSON manifest, например `data/rag/inputs.json`:

```json
[
  {"url": "https://example.org/article.html"},
  {"path": "article.html", "source": "https://example.org/local-copy.html"}
]
```

Относительный path разрешается относительно manifest. Можно повторять `--url`
вместо manifest. CLI не импортирует конфигурацию чата и не читает `.env`.
Оператор задаёт один и тот же каталог CLI и приложению; умолчание `data/rag`:

```sh
export RAG_DIR="$PWD/data/rag"
.venv/bin/python -m rag ingest --manifest "$RAG_DIR/inputs.json"
.venv/bin/python -m rag index --base-url http://127.0.0.1:8001/v1 \
  --model mlx-community/Qwen3-Embedding-0.6B-8bit --batch-size 16
.venv/bin/python -m rag status
make run
```

Ingest сохраняет frozen corpus.json и ingest-report.json с ошибками/словами и
оценкой страниц; при любом отказе прежний корпус остаётся. Повторный index
использует кэш. Сборка пишет временную SQLite и атомарно заменяет index.sqlite
только после успеха; прежний индекс доступен при ошибке/остановке. Один OS lock
исключает конкурирующих писателей. Atomic replace — граница успеха; отказ записи
завершающего progress после replace оставляет новый индекс готовым и даёт
диагностическое предупреждение, без обещания отката опубликованной SQLite.
Изменённый корпус отмечает индекс как stale.

Сравнение выполняется отдельно в терминале на том же frozen corpus и конфиге:

```sh
.venv/bin/python -m rag compare --base-url http://127.0.0.1:8001/v1 \
  --model mlx-community/Qwen3-Embedding-0.6B-8bit
```

Оба индекса сохраняются в `comparisons/fixed` и `comparisons/structural`,
локальный comparison.json содержит число чанков, длины, перекрытие, разделы,
модель и fingerprint. Активный индекс не заменяется. Это сравнение разбиения;
качество ответа/поиска на контрольных вопросах здесь не измеряется.

## Просмотр и проверки

Откройте `http://127.0.0.1:8000` → «Настройки → Работа RAG». Страница работает
без чата/ключа, читает фактические стадии CLI `documents → chunks → embeddings → save`,
счётчики кэша/новых векторов, длительность, модель и размерность. После сохранения
видны объём корпуса, версия/байты/число строк SQLite, документы и чанки с
границами/текстом/метаданными. Раскрытие отдельно читает настоящий числовой
вектор выбранного чанка. Refresh открывает сохранённый индекс; missing/stale/
interrupted/error названы явно, предыдущий индекс при отказе виден отдельно.
UI не запускает сборку и не сравнивает стратегии.

```sh
make check
make check-browser
```

Проверки используют временный нейтральный CP1251 HTML, настоящий HTTP embedding
stub, отдельный CLI и SQLite, без живого инференса. Проверяются chunk slices,
cache fingerprint, cosine, валидация векторов, atomic failure, writer lock,
interrupted/stale, bounded API и настоящий клиент под Node с lazy vector/late GET.
Это проверка контрактов, не реальная оценка retrieval качества на архиве.
Сохраняется весь offline-набор предыдущих дней: чат, память, задачи, MCP и pipeline.
