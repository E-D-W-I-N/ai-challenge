# День 13 — состояние задачи: конечный автомат

## Задание

```
🔥 День 13. Состояние задачи
Реализуйте состояние задачи как конечный автомат: этап, текущий шаг, ожидаемое
действие. Пример: planning → execution → validation → done. Проверьте: паузу
на любом этапе; продолжение без повторных объяснений. Результат: агент
с формализованным состоянием задачи
```

## Вывод

* **Автомат целиком в коде.** Таблица переходов (`TRANSITIONS`) — один
  источник правды на команды и на ручки; перехода нет в таблице — отказ,
  состояние прежнее. Отсюда даром: `done` терминален, пауза берётся с любого
  незавершённого этапа и возвращает **туда же**, обратного хода нет.
* **Три оси задания — три поля.** Этап хранится; шаг пишет человек; у
  ожидаемого действия есть умолчание на этап, заданное перебивает его, смена
  этапа возвращает к умолчанию.
* **У модели нет ни одного рычага**: ни инструментов, ни вызова, определяющего
  этап, ни разбора её ответа. Двигает состояние человек, командой.
* **Ход называет вершину, из которой выходили** (поле `from`): не совпало
  с нынешней — 409, и две вкладки не перепрыгнут этап.
* **Состояние — в одном месте**: строка в своей таблице, поля конфига о режиме
  нет; отказала база — этап не сменился нигде.
* Правило этапа едет **системным** сообщением, врезка `[задача]` — ролью
  `user`. Каждый обмен везёт этап, шаг и ожидаемое действие: поэтому
  продолжение не требует повторных объяснений.

## Команды

| команда | что делает | шлёт обмен |
|---|---|---|
| `/task <описание>` | начать задачу, этап планирования | да |
| `/task-next` | следующий этап | да |
| `/task-step <текст>` | записать текущий шаг | нет |
| `/task-expect <текст>` | записать ожидаемое действие | нет |
| `/task-pause` | пауза | нет |
| `/task-resume` | снять паузу — вернуться туда же | да |
| `/task-off` | выйти из режима, состояние стереть | нет |

Текст обмена привязан к **переходу**, а не к целевому этапу: «Приступай
к работе» после планирования, «Проверь сделанное» после выполнения. Команда
не к месту или без текста не отправляет ничего, а под полем ввода сказано,
что не так; двойной Enter не проводит переход дважды.

## Что видно на экране

Шапка над лентой — при включённом режиме и только: этап словом, шаг,
«ожидается». Кнопок нет, управление командами; пауза различима не только
цветом — штриховая рамка поперёк ленты.

```
/task собрать ТЗ                → Задача · планирование
/task-step опрашиваю заказчика  → шаг: опрашиваю заказчика
/task-pause → /task-resume      → пауза → планирование
/task-next → next → next        → выполнение → проверка → готово
```

## Пауза и продолжение

Пауза законна на любом незавершённом этапе и возвращает **ровно туда же**,
откуда встали (`paused_from`). Правило паузы говорит модели «не продолжай, даже
если просят»; снимает её только человек. Состояние переживает перезапуск, и
продолжение не требует повторных объяснений: описание, этап, шаг и ожидаемое
действие уезжают врезкой в **каждом** обмене.

## Хранение и ручки

Таблица `task_state`: строка на чат, `session_id` первичным ключом, поля
`stage`, `step`, `expects`, `description`, `paused_from`. Пустой `expects`
значит «человек не задавал» — едет умолчание этапа. Строка чистится на всех
трёх путях очистки, а ветвление уносит её целиком: задача у ветки та же.

| Ручка | Что делает |
|---|---|
| `POST /api/agents/{id}/task` | включить режим: `{"description": ...}` |
| `PATCH /api/agents/{id}/task` | ход `{"move", "from"}` либо `{"step"}`, `{"expects"}` |
| `DELETE /api/agents/{id}/task` | выйти из режима, состояние стереть |
| `GET /api/agents/{id}` | чат целиком — состояние задачи полем `task` |
| `/api/profile`, `/api/memory`, `/api/agents/{id}/working` | профиль и слои памяти |
| `/api/agents/{id}/messages`, `/regenerate`, `/cancel`, `/fork` | обмен SSE, отмена, ветка |
| `/api/agents`, `/api/agents/{id}`, `/api/models`, `/api/health` | чаты, конфиг, каталог моделей, состояние сервера |

Ручки чтения состояния нет намеренно: наружу оно едет одним местом — полем
`task` самого чата. Второе совпадало бы с ним ровно пока за ним следят.

## Проверки

Живых вызовов к LLM нет — поток подменяется заглушкой. Бьют по поведению:
`browser_check.js` исполняет настоящий `app/static/app.js` под node на стенде
с минимальным DOM и настоящими кадрами SSE.

```bash
.venv/bin/python checks/run_checks.py    # 33 проверки, включая три ниже и клиентскую
.venv/bin/python checks/restart.py       # два процесса подряд на одном файле
.venv/bin/python checks/two_processes.py # сервер и консоль на одной базе
.venv/bin/python checks/spawn_100.py     # сто агентов в одном процессе
node checks/browser_check.js             # клиент под node, 315 утверждений
```

Про автомат — три проверки. Таблица переходов проходится **целиком**:
пятнадцать клеток «этап × ход», семь ведут дальше, восемь обязаны отказать,
оставив состояние прежним. Рядом: ход из чужой вершины — 409; отказ базы
не двигает этап и не прячет задачу; врезка и правило стоят в промпте на своих
номерах, а выключенный режим неотличим от невключавшегося; за состоянием
к модели не ходят ни разу; список слева называет ту же задачу, что сам чат.

## Как запустить

```bash
cp .env.example .env          # впишите OPENROUTER_API_KEY
python3.11 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn app.main:app --reload --port 8000
```

Откройте http://127.0.0.1:8000 и наберите `/task собрать ТЗ` — над лентой
встанет шапка. Дальше `/task-step`, `/task-pause`, `/task-resume`, `/task-next`;
кнопка **«Показать промпт запроса»** под ответом покажет и правило этапа
в системном сообщении, и врезку `[задача]`. Без браузера — консоль
`.venv/bin/python -m app.cli`, команд задачи в ней нет. `.env` и файлы базы —
в `.gitignore`; репозиторий публичный, не коммитьте через `git add -A`.
