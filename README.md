# День 18 — напоминания: инструмент с отложенным выполнением

```
🔥 День 18. Отложенное выполнение
MCP-инструмент с отложенным или периодическим выполнением: сохраняет
данные, выполняется по расписанию, возвращает агрегированный результат.
```

## Вывод

Сервер `remind` (`app/mcp_servers/remind.py`) ведёт напоминания: модель
заводит их из диалога инструментом `remind`, человек смотрит во вкладке
«Инструменты» — и видит, как «ждёт» само становится «сработало». Три
инструмента: `remind` (одноразовое или с `every` — повторяющееся),
`reminders` (агрегированный результат: список с состояниями и счётчики),
`cancel` (чужой номер — честный отказ текстом).

| | |
|---|---|
| «Сработало» | **вычисляется при чтении** из `due_at` (`now >= due_at`), а не пишется: фонового цикла у сервера нет — он был бы вторым живым процессом у того же файла. У повторяющегося `due_at` при чтении всегда следующее, счёт срабатываний отсчитывается от первого срока |
| Хранение | своя база **сервера** `data/reminders.db` (SQLite, номера AUTOINCREMENT): сервер — её единственный писатель, стор приложения и его таблица очистки не тронуты. Переживает перезапуск процесса |
| Агрегат | `reminders()` → JSON: `items` (состояние, счёт, срок) плюс счётчики `total` / `waiting` / `fired`, сходящиеся со списком |
| В чат | **никогда**: история строго попарная, одиночная реплика сломала бы перегенерацию и свёртку. Человек видит напоминания во вкладке |
| Ручка | `GET /api/mcp` дотягивает `reminders` вызовом инструмента — только у живого сервера, у которого он есть; у лежачего поля нет, и ручка жива |

## Клиент

Во вкладке «Инструменты» у сервера с полем `reminders` — блок под его
инструментами: счётчики по состояниям и каждая запись с текстом и
временем. Пока вкладка открыта, следующий запрос идёт через 2 секунды после
завершения предыдущего:
переворот «ждёт → сработало» виден живьём, без единого действия.
Уход из настроек/раздела, скрытый документ и pagehide останавливают
опрос и отменяют GET; поздний ответ отвергается. Повторный вход сразу
обновляет агрегат, раскрытые схемы сохраняются.

«Чат» и «Настройки» используют центральную рабочую область. Светлый интерфейс
рассчитан на компьютер и ноутбук: шесть страниц с вертикальной навигацией,
гибкие формы и сворачиваемый список чатов. Переключение сохраняет выбранный чат, черновик сообщения,
прокрутку, активный ответ и шапку задачи. Все шесть метрик доступны снизу;
в компактном окне строка прокручивается горизонтально. Длинный текст
переносится, код и JSON прокручиваются; при zoom можно свернуть список чатов.

Аватар справа в шапке открывает настоящий глобальный профиль: стиль, формат
и контекст ответа. Меню показывает записанные значения и ведёт в тот же
редактор «Профиль». Поля сохраняются при уходе фокуса; ошибка оставляет текст
для повторной попытки. Профиль, долговременная память и инварианты действуют
во всех чатах, модель, промпт и рабочая память — в выбранном чате.

Стрелки, Home и End переключают вкладки. Escape закрывает меню профиля
или подтверждение; фокус возвращается к открывшей
кнопке. В редакторе записи Enter сохраняет, Shift+Enter добавляет строку,
Escape отменяет. В обоих слоях памяти остаются ручное добавление, правка
и удаление с явным выбором типа записи. Поиск названий, копирование ответа
кнопкой и перенос рабочей записи кнопкой убраны; текст можно выделить
и перенести в форму долговременной памяти вручную.

Клиент загружает обычные локальные скрипты `text.js` → `records.js` → `app.js`,
без сборки и новых зависимостей. Карта файлов и чтения по задаче — в
[руководстве клиента](docs/client-guide.md).



## Проверки

Живых вызовов к LLM нет; механика сервера — in-process (функции модуля
обычные, REMIND_DB_PATH во временный каталог), связь — настоящими
процессами через тот же McpManager. Subprocess-фикстура задаёт временный
путь серверной SQLite до запуска настоящего stdio; data/reminders.db
и окружение production-процессов проверки не меняют. Клиент исполняется
под Node обоими путями (aggregate и классические HTML-скрипты) с явными
API/SSE-ответами; геометрия — по [списку](docs/client-guide.md#ручной-прогон).

```bash
make check                             # весь набор, включая процессы и клиент
.venv/bin/python checks/restart.py       # два процесса подряд на одном файле
.venv/bin/python checks/two_processes.py # сервер и консоль на одной базе
make check-browser                     # только клиент под Node.js
```

Новые: одноразовое срабатывает к сроку (статус вычисляется, а не пишется);
повторяющееся — несколько срабатываний и следующий `due_at`; `cancel`
снимает, чужой номер — отказ текстом, номер снятого не выдаётся заново;
агрегат сходится со списком; переживает перезапуск процесса (два
менеджера подряд на одном файле); у `/api/mcp` поле `reminders` только у
живого remind, у лежачего его нет — и ручка жива; сквозной (заглушка
зовёт `remind`, вызов доезжает до настоящего сервера, история остаётся
попарной). Клиентская: блок со счётчиками и временем, переворот виден
перезапросом, закрытая вкладка не опрашивается.

## Как запустить

```bash
make help
make setup
# Только если .env ещё нет; впишите OPENROUTER_API_KEY вручную.
test -e .env || cp .env.example .env
make run
```

Нужны Python >= 3.11 и Node.js для клиентских проверок. `make setup`
по умолчанию создаёт `.venv` через `python3.11`. Другой интерпретатор:

```bash
make setup PYTHON=/path/to/python
```

`PYTHON` выбирает только интерпретатор создания окружения. Повторный
`setup` использует существующую `.venv`, проверяет её Python >= 3.11 и
устанавливает `requirements.txt`; окружение не пересоздаёт, `.env` не
трогает. `run` и `check` всегда используют `.venv/bin/python`.
`make run` запускает uvicorn с reload на порту 8000:
http://127.0.0.1:8000. `make check` требует `node` в PATH и один раз
вызывает `checks/run_checks.py`, который уже включает проверки отдельных
процессов и браузерную. Любая ошибка завершает цель ненулевым кодом.

В `mcp.json` три сервера: `echo` (стенд связи), `git` и `remind`.
Спросите «напомни через минуту про чай» — под ответом будет бейдж
`remind · remind · N мс`, а во вкладке «Инструменты» запись перевернётся
в «сработало» на глазах. Репозиторий публичный: используйте git add с явными именами файлов,
не включайте секреты и базы в коммиты.

## Работа с OpenCode и Pi

Запускайте установленный инструмент из корня этого worktree:

```bash
cd /path/to/ai-challenge-9-week-01
opencode
# Или:
pi
```

Корневой [AGENTS.md](AGENTS.md) автоматически попадает в контекст
[OpenCode](https://opencode.ai/docs/rules/) и
[Pi](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/configuration.md).
Он требует перед изменениями прочитать нужные разделы
[архитектуры](docs/architecture.md): ссылка сама по себе не загружает их
содержимое. Модель и авторизацию настраивайте лично в выбранном инструменте
(OpenCode — пользовательские настройки/подключение провайдера;
Pi — `/login`, `/model`, настройки в `~/.pi/agent`). Эти настройки и
учётные данные не переносите в репозиторий или `.env` приложения.
`mcp.json` настраивает MCP-серверы самого чат-приложения, а не OpenCode/Pi.

## Что осталось честно назвать

* **Сработавшее молчит до вопроса**: уведомления в чат нет — история
  попарная. Человек узнаёт о срабатывании из вкладки или спросив модель
  («какие напоминания сработали?» — та позовёт `reminders`).
* **Точность — до перезапроса**: следующее чтение идёт через 2 секунды после
  предыдущего ответа. Сервер считает состояние при чтении; задержка запроса
  добавляется к интервалу, параллельных запросов нет.
* **Часы — серверные**: `due_at` считается по часам процесса сервера;
  вкладка лишь показывает его ответ, сама по своим часам ничего не
  досчитывает.
* _Живой прогон на ключе:_ **место под числа оставлено пустым — впишет человек.**
