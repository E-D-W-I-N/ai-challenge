# День 02 — свободный ответ vs. формат + `max_tokens` + `stop`

## Задание

```
🔥 День 2. Формат ответа

Отправьте один и тот же запрос, но:
👉 добавьте явное описание формата ответа
👉 добавьте ограничение на длину ответа
👉 добавьте условие завершения ответа (stop sequence или явную инструкцию)

Сравните ответы:
👉 без ограничений
👉 с ограничениями

Результат:
Один и тот же запрос с разным уровнем контроля ответа через API
```

## Промпт

Три сценария, по одному на параметр, и один и тот же вопрос на все шесть колонок
дня — дословно. Системного сообщения нет, весь промпт уходит сообщением `user`:

```text
Сравни три канала доставки уведомлений: push, email и SMS.
По каждому каналу назови ровно пять величин: стоимость за 1000 сообщений, типичную задержку доставки, долю прочтений, главный риск и когда этот канал стоит выбирать.
Если ответ запрошен в формате JSON, верни объект с единственным ключом channels — массивом из трёх объектов с ключами channel, cost_per_1000, latency, read_rate, main_risk, when_to_use. Иначе отвечай обычным текстом: абзац на канал, каждая величина с подписью, что это.
Разбирай каналы в порядке push, email, SMS. Не пиши вступления и не перечисляй каналы заранее — начинай сразу с разбора push.
Закончив очередной канал — и только после того, как назвал по нему все пять величин, — выведи отдельной строкой маркер <<<КОНЕЦ БЛОКА>>>. Копируй его посимвольно, без кавычек и без markdown-разметки. Перед первым каналом маркера быть не должно.
```

Модель — `openai/gpt-4o-mini`, одна на все шесть колонок.

Два условия, без которых день ломается молча. **Слово «JSON» обязано быть
в тексте промпта:** без него `response_format={"type": "json_object"}` возвращает
**400** на моделях семейства OpenAI. **Стоп-строка обязана быть достижимой:**
маркер `<<<КОНЕЦ БЛОКА>>>` модель печатает по прямой инструкции, а не по случайности
форматирования, — иначе `stop` не на чем сработать и третий сценарий ничего не покажет.

## Вывод

В каждом сценарии левая колонка не задаёт ни одного параметра, правая меняет ровно
один — поэтому разницу можно честно приписать параметру, а не промпту и не модели.

**1. «Формат ответа», справа `response_format={"type": "json_object"}`.** Слева проза
абзацами, справа JSON-объект с массивом `channels`. Содержание одно и то же — те же
пять величин по тем же трём каналам, — а `finish_reason: stop` в обеих колонках:
формат меняет форму ответа и только её. Лимита здесь нет специально, чтобы JSON
пришёл целым и валидным.

**2. «Ограничение длины», справа `max_tokens=80`.** Самый явный сигнал дня:
`finish_reason` слева `stop`, справа `length`, `completion_tokens` упирается ровно
в 80, а текст обрывается на полуслове внутри первого канала — до email и SMS дело
не доходит. Три независимых подтверждения одного ограничения: статус, счётчик и сам текст.

**3. «Условие завершения», справа `stop=["<<<КОНЕЦ БЛОКА>>>"]`.** Слева все три
канала, каждый закрыт маркером; справа только push, а самого маркера в выводе **нет** —
обрыв происходит перед стоп-строкой. При этом `finish_reason` — `stop` в обеих
колонках: параметр отработал и не оставил следа в статусе.

Разница между вторым и третьим сценариями — суть дня. `max_tokens` устроен как внешний
обрыв, и API сообщает о нём отдельным значением `finish_reason: length`. `stop` устроен
как штатное завершение: `finish_reason` тот же `stop`, поля `stop_sequence` в ответе нет,
и понять, что параметр сработал, можно только по длине и содержанию.

Внизу — сводка по прогону, под колонками — вердикт модели-судьи: чем ответы отличаются
по форме и содержанию, что показывает `finish_reason` и хватает ли его одного.

## Как запустить

```bash
cp .env.example .env          # впишите OPENROUTER_API_KEY
python3.11 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn app.main:app --reload --port 8000
```

Откройте http://127.0.0.1:8000, выберите сценарий в списке слева и нажмите «Старт».

`.env` в `.gitignore`. Репозиторий публичный: ключ, попавший в коммит, отозвать
уже нельзя — никогда не коммитьте через `git add -A`.
