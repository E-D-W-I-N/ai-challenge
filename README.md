# День 33. Ассистент поддержки пользователей

```text
🔥 День 33. Ассистент поддержки пользователей

Сделайте мини-сервис для поддержки пользователей.

Ассистент должен:

👉 отвечать на вопросы о продукте
👉 использовать RAG (FAQ, документация)
👉 учитывать контекст пользователя или тикета

Через MCP:

👉 подключите CRM
👉 или JSON с пользователями / тикетами

Пример:

👉 «Почему не работает авторизация?»
👉 ассистент отвечает с учётом данных тикета

Результат:

AI-ассистент для поддержки пользователей
```

## Вывод

Консольный ассистент поддержки для произвольной папки Markdown-документации,
FAQ и руководств. Перед каждым ответом он получает свежий контекст выбранного
тикета и его пользователя через отдельный read-only HTTP MCP-сервис. RAG ищет
документацию с учётом вопроса, тикета и последних успешных пар разговора.
Ответ должен различать сведения тикета и документации, приводить источники
и запрашивать уточнение при недостатке данных. Качество этих выводов проверяет
человек; автоматического доказательства утверждений или цитат нет.

Приложение только предлагает текст оператору. Оно не меняет статусы, не отправляет
ответы, не реализует CRM, публичную регистрацию или авторизацию. MCP использует
явный JSON пользователей/тикетов. Старые сценарии, workflow и базы не используются.
Корпус, JSON, настройки, ключи и индекс остаются вне Git.

## Установка

Python >=3.11 и совместимый HTTP endpoint с Chat Completions, `/models` и
`/embeddings`. Git для папки знаний не требуется. Прямые зависимости закреплены,
включая MCP 1.30.0.

```sh
make setup
# Или: make setup PYTHON=/path/to/python
make check
```

После setup все Python-команды выполняйте через `.venv/bin/python`.
System HTTP/HTTPS proxy сохраняется для модельного HTTP, loopback идёт напрямую.
Нет скрытого direct fallback, retries и пробных inference-вызовов.
Совместимость и качество живой модели здесь не проверялись.

## Запуск

В первом терминале оператор вручную запускает MCP, привязанный к одному тикету:

```sh
.venv/bin/python -m support.context \
  --data /private/path/support.json --ticket T-1
```

Во втором терминале — новую консольную сессию с тем же тикетом:

```sh
.venv/bin/python -m support \
  --knowledge /private/path/knowledge --ticket T-1 \
  --mcp-url http://127.0.0.1:8010/mcp
```

MCP по умолчанию слушает только `127.0.0.1:8010`, путь `/mcp`; порт меняется
через `--port` и соответствующий `--mcp-url`. Это локальный сервис без auth:
не публикуйте его наружу. Ассистент проверяет совпадение ID при старте и каждом
ответе. Весь JSON в модель не попадает: MCP возвращает только выбранный тикет
и связанного владельца. Модель не выбирает ни ID пользователя, ни ID тикета,
не имеет инструмента просмотра остальных записей. JSON перечитывается на каждый
вызов. Ошибка MCP/JSON останавливает ответ без использования старого контекста
или прямого чтения JSON клиентом.

Для переключения: завершите CLI через `/exit`, остановите MCP и запустите его с
новым `--ticket`, затем запустите новую CLI-сессию с тем же ID. История хранится
только в памяти одного процесса; `/new` очищает её. Это выбор контекста оператором,
а не система доступа для недоверенных пользователей.

## Команды и модели

Сначала выполните `/settings`: URL модели, скрытый ввод ключа через getpass,
затем выбор двух независимых model IDs из `/models` — generation и embedding.
Каталог не угадывает назначение модели. IDs изначально пусты, скрытого выбора нет.
Пустой ввод ключа сохраняет его; `-` удаляет. Reasoning по умолчанию OFF,
`temperature=0.2`, `max_tokens=1024`; в настройках можно явно задать reasoning,
неотрицательную конечную температуру и положительный целый max_tokens.
Введите `null` в поле max_tokens, чтобы не передавать этот параметр. Верхних
ограничений этих параметров в клиенте нет; их совместимость проверяет сервер модели. Смена настроек очищает разговор.
Подключение и параметры фиксируются на один обмен; `.env`/environment keys не читаются.

- `/settings` — изменить URL, ключ, модели и параметры генерации.
- `/models` — заново показать каталог и выбрать generation/embedding IDs.
- `/index` — явно построить/обновить индекс; это единственная команда,
  отправляющая документы embedding-модели. Неизменившиеся чанки кэшируются.
- `/status` — проверить наличие и свежесть индекса, показать безопасное подключение.
- `/new` — очистить последние успешные пары текущего разговора.
- `/help`, `/exit` — помощь и завершение. Остальной текст — вопрос поддержки.

Перед вопросами выполните `/index`. Отсутствующий индекс даёт явную ошибку;
изменившийся корпус — предупреждение `STALE`, используется опубликованный снимок,
пока оператор явно не вызовет `/index`. Новая embedding model требует `/index`.
Пустой корпус публикует пустой индекс, удаляя старые чанки; query embeddings тогда
не вызываются, модель получает пустую документацию и должна попросить уточнение.
Каждый обычный ответ с непустым индексом делает один query embedding и один
Chat Completions. Нет автоматического платного reindex/retry/fallback.

Settings JSON и SQLite хранятся вне папки знаний в
`~/.local/state/support-assistant/<hash-absolute-knowledge-path>/`.
`--state /private/path/state` явно заменяет этот каталог; каталог не может лежать
внутри корпуса. Индекс проверяет knowledge path и embedding ID. Настройки и индекс
публикуются атомарно с правами 0600, новый state-каталог — 0700. Настройки содержат
ключ, индекс — документацию: ограничьте доступ и не коммитьте их. Чаты на диск не пишутся.

## JSON MCP

Файл UTF-8 содержит ровно `users` и `tickets`. Синтетический пример структуры:

```json
{
  "users": [{"id": "U-1", "context": "Тариф и особенности окружения"}],
  "tickets": [{
    "id": "T-1",
    "user_id": "U-1",
    "title": "Краткая тема",
    "description": "Наблюдение пользователя",
    "status": "open",
    "messages": [{"author": "user", "text": "Дополнительные сведения"}]
  }]
}
```

Все указанные строковые поля обязательны, `messages` — массив объектов с
`author`/`text` (может быть пустым). IDs непустые и уникальны внутри своей группы;
каждый `user_id` обязан ссылаться на существующего пользователя. Лишние поля и
неверные типы отклоняются. Формат не описывает настоящую CRM-интеграцию.

## Границы контекста

Сканер включает только UTF-8 `.md`; hidden paths, symlinks, известные secret/key
имена во всех компонентах пути, data/files, vendor/build/dist/node_modules и бинарные файлы исключаются.
Индексируются только документы, код не индексируется. Фильтр не обнаруживает
любой секрет в обычном Markdown: выбирайте допустимую папку знаний.
Чанки — последовательные окна до 40 LF-строк / 12000 bytes; путь, строки и SHA256
показываются рядом с ответом. Retrieval выбирает до трёх чанков по cosine, без
rerank, cutoff или автоматической проверки смысла. История — последние три
успешные пары одного тикета. Ticket/docs/history передаются как недоверенные
данные; prompt injection и правильность вывода остаются ограничениями модели.

Явные лимиты: до 10000 файлов, подходящий документ 128 KiB, корпус 4 MiB / 2000
чанков; исходный support JSON 1 MiB, выбранный контекст 24000 bytes; вопрос 8000,
retrieval query вместе с контекстом/историей 48000, final data 96000, ответ 24000
bytes. Превышение даёт отказ, текст не обрезается. Ошибка чтения подкаталога отменяет обновление, сохраняя прежний
индекс. Модельный HTTP timeout 60s,
ответ до 16 MiB, redirects OFF; MCP timeout 15s. OFF отправляет
`reasoning_effort=none`, ON — `medium`; reported reasoning при OFF даёт ошибку
без paid retry. Это не доказательство отсутствия скрытого внутреннего reasoning
произвольного совместимого сервера. Неподдерживаемые параметры дают отказ upstream.

## Проверки

`make check` — один компактный offline сценарий: временные Markdown и JSON,
модельный HTTP mock, настоящие локальные HTTP MCP процессы для двух тикетов.
Проверяются различающийся retrieval, отсутствие чужого пользователя в prompt,
свежесть JSON, неизвестный тикет/невалидный JSON/ссылка владельца, index cache,
empty-index, Unicode LF lines, SQLite URI, скрытие ключа, reasoning OFF,
отсутствие retries и запуск CLI. Корпус и вопросы для оценки качества здесь
не хранятся. Живой inference, удалённая CRM и качество ответов не проверялись.
