# День 06 — агент как отдельная сущность: список агентов, чат, настройки

## Задание

```
🔥 День 6. Первый агент

Реализуйте простого агента, который:
👉 принимает запрос пользователя
👉 отправляет его в LLM через API
👉 получает ответ
👉 выводит результат в вашем интерфейсе

(простой чат, CLI или web, запросы через HTTP-клиент)

Важно:
👉 агент должен быть отдельной сущностью, а не просто один вызов API
👉 логика запроса и ответа должна быть инкапсулирована в агенте

Результат:
Агент принимает запрос и корректно вызывает LLM через API
```

Критерий проверки от организатора челленджа, дословно:

> Если тебе нужно будет моментально заспавнить 100 агентов с разными конфигами,
> у тебя это можно сделать? … Лучше чтобы инстанс был один, а уже внутри было
> поднято сто инстансов агента.

## Промпт

Промпта дня как такового нет: интерфейс — чат, и вопрос задаёт пользователь.
Зато в списке слева лежат **агенты заданий дней 1–5** — по агенту на каждую
колонку тех дней, двадцать один штука. Их конфиги перенесены из веток дней
дословно, вместе с промптами:

| Группа | Агентов | Что в них |
|---|---|---|
| День 1 | 1 | `mistral-small-3.2-24b`, без параметров: день был про панель метрик |
| День 2 | 6 | три пары «без параметра / с параметром»: `response_format`, `max_tokens=80`, `stop` |
| День 3 | 8 | четыре техники промптинга, включая панель из трёх ролей |
| День 4 | 3 | `temperature` 0.0 / 0.7 / 1.2 с закреплённым провайдером |
| День 5 | 3 | одна задача на трёх ступенях моделей |
| День 6 | 1 | собственный ассистент стенда |

**Вопрос дня сам не отправляется.** Системная часть колонки уехала агенту
в системный промпт, а вопрос — в черновик: при открытии агента он подставляется
в поле ввода. Его видно, можно поправить и отправить — отправка всегда решение
пользователя, а не стенда.

Перенос сверяется программно, а не глазами: `checks/run_checks.py` читает
`day.py` каждой ветки через `git show`, раскладывает колонки и сравнивает
с ростером поле за полем — модель, `temperature`, `max_tokens`, `stop`,
`response_format`, `extra_body` вместе с `provider.order`, системный промпт
и текст вопроса.

## Вывод

### Интерфейс

Клиент сделан по образцу oMLX Chat, о котором просил заказчик:

- **слева** — заголовок стенда с кнопкой свернуть, крупная кнопка «Новый чат»,
  список: сначала чаты пользователя, ниже группы «День 1»…«День 6»; внизу
  светлая/тёмная тема, автоимя чата и «Очистить все чаты» — с подтверждением,
  которое закрывается кнопкой, кликом мимо и по Escape;
- **по центру** — лента: сообщения пользователя справа компактным пузырём,
  ответ — карточкой с рамкой, в шапке имя модели и провайдер, справа иконки
  «метрики», «копировать», «перегенерировать», «сырой текст». Справа от ленты
  рельс с точками по сообщениям. Внизу — поле ввода с подсказкой
  «Shift+Enter — новая строка»; во время генерации кнопка становится «Стоп»
  и действительно отменяет вызов;
- **справа** — две вкладки. «Модель»: выбор модели из каталога, `temperature`,
  `max_tokens`, `top_p`, `top_k`, `min_p`, три штрафа и окно памяти. «Агент»:
  имя и системный промпт. Ниже кнопка сохранения, ещё ниже — плитки метрик.

Оба борта сворачиваются, состояние переживает перезагрузку. На узком окне
(до 940 px) они сворачиваются сами и открываются поверх ленты как ящики —
кнопками в углах, а закрываются кликом мимо и по Escape: иначе на ноутбучном
окне от чата осталась бы полоска посередине.

**Про ключ в интерфейсе нет ничего.** В oMLX внизу есть «Change API Key» —
у нас такого пункта нет и быть не может: репозиторий публичный, ключ живёт
в `.env` и остаётся делом того, кто поднял стенд.

**Из сети клиент не тянет ничего**: ни шрифтов, ни библиотек, ни иконок.
Шрифт системный, иконки — inline SVG, markdown разбирается своими силами
(заголовки, списки, цитаты, код, жирный, ссылки только на `http(s)`).
Текст ответа экранируется до разбора, поэтому разметка из ответа модели
не может стать разметкой страницы.

**Рассуждение.** Если модель прислала `reasoning` отдельным полем дельты,
оно показывается свёрнутым блоком «Рассуждение» над ответом — как «Thinking»
в oMLX. В контекст следующего запроса рассуждение не возвращается: модель
видит свой ответ, а не то, как она к нему шла.

**Плитки метрик** — настоящие, из `app/llm.py`: ток/с, время до первого
токена, токены запроса и ответа, стоимость, время, провайдер, заполнение
контекста. Обновляются по последнему ответу; кнопка «метрики» на карточке
показывает цифры именно того ответа.

Плитка «первый токен» показывает момент, когда модель **заговорила**, а не
когда пошёл ответ. На думающей модели это разные вещи: `ttft_ms` ставится
на первом токене ответа, и токены рассуждения его не двигают — на плитке
оказалось бы время вместе со всем размышлением. Поэтому рядом с `ttft_ms`
считается `first_token_ms` — первый токен от модели вообще; насколько ответ
отстал от рассуждения, видно подписью справа на той же плитке. Сам `ttft_ms`
считается ровно как раньше.

### Агент

**Агент — класс** (`app/agent.py`). Публичный метод принимает **текст
пользователя**, а не готовую ленту: агент сам склеивает системный промпт,
стартовые сообщения, окно истории и новый вопрос, зовёт `stream_completion`
и дописывает ответ себе в историю. Веб-слой ему не нужен — тот же класс
работает из консоли (`python -m app.cli`).

- **в истории лежит исходный текст вопроса**, а не собранный промпт;
- **кап двойной**: окно `history_limit` ограничивает то, что уезжает в модель,
  `MAX_STORED_MESSAGES` — то, что живёт в памяти процесса. Ноль в окне — агент
  отвечает каждый вопрос как первый;
- **откат по построению**: история не трогается до конца обмена. Ответа
  не случилось — не записано ничего, вопрос возвращается в поле ввода.
  Ответ частичный — записаны обе реплики, у ответа проставлена ошибка;
- **один обмен на агента одновременно** (`asyncio.Lock` плюс синхронная бронь
  до первого `await`): второй параллельный запрос получает `409`;
- **перегенерация заменяет последний ответ**: пара «вопрос — ответ» снимается
  с истории до вызова, поэтому модель видит тот же контекст, а в ленте
  остаётся один ответ, а не два. Если вызов не отдал ни одного токена, снятое
  возвращается на место: неудачная перегенерация иначе уносила бы и прошлый
  ответ, и сам вопрос, а восстановить их было бы неоткуда — историю хранит
  сервер, а не браузер.

**Реестр** (`app/registry.py`) — словарь `id → Agent`. Сто агентов с разными
конфигами — это сто объектов в одном процессе: ни потоков, ни подпроцессов,
ни единого вызова к модели. Есть потолок живых агентов (`AGENT_MAX_LIVE`,
по умолчанию 1000): при переполнении уходят самые старые простаивающие,
занятый не вытесняется никогда. За один запрос можно создать не больше
250 агентов.

Ответ на критерий организатора воспроизводится одной командой:

```bash
.venv/bin/python checks/spawn_100.py
```

```
[1] реестр: 100 агентов за 0.4 мс, живых 100
[2] POST /api/agents: 100 агентов за 2.2 мс (спавн внутри 0.51 мс), живых 122
[3] GET /api/agents: 122 живых, потолок 1000
[4] вызовов к модели за спавн: 0
[5] процесс один: pid=…, потоков 2, агентов 122
```

**Незаданный параметр не отправляется вовсе** — ни как `null`, ни как ноль.
Пустое поле в панели значит «пусть решает провайдер», а заданный ноль — это
заданный ноль. Разница не косметическая: на каждом вызове стоит
`provider.require_parameters: true`, и каждый заданный параметр сужает список
провайдеров, готовых обслужить запрос. Если после сохранения выбор параметров
делает модель недоступной, это видно понятной ошибкой в карточке ответа.

**Клиент ленту не хранит.** Тело `POST /api/agents/{id}/messages` — это
`{"text": "…"}` и больше ничего; лишнее поле в теле получает `400`, а не
молчаливое игнорирование. Обрыв клиента гасит вызов: брошенная вкладка иначе
жгла бы токены. Один `httpx.AsyncClient` на процесс, число одновременных
вызовов ограничено семафором (`LLM_MAX_CONCURRENCY`, по умолчанию 16).

### Чего в стенде больше нет

Сценарии как концепция удалены целиком: `Scenario`, `SCENARIOS`, `/api/run`,
команда `/прогон`, модель-судья, `depends_on` и серии `repeats`. Заказчик
попросил их убрать, и они убраны, а не спрятаны за флагом: мёртвый код
в демо-репозитории хуже отсутствующего. Вместе с ними ушли родительские связи
агентов: детей больше некому спавнить, и каскадное убийство с каскадным
вытеснением остались бы кодом, до которого не дотянуться из приложения.

`Session` остался — но уже не алиасом, а тонкой обёрткой: `day.py` дней 1–5
объявляет колонки через него вместе с `repeats` и `depends_on`, которых
в конфиге больше нет, и эти два поля молча отбрасываются. Полной
совместимости это не даёт: те же файлы импортируют и `Scenario`, а сценарии
удалены по постановке. Настоящее чтение старых дней живёт в
`checks/_daysrc.py` со своим шимом — и на каждом прогоне проверок сверяет
ростер с ветками.

### Что помнит стенд между запусками

Ничего. Реестр живёт в памяти процесса: перезапуск стирает и чаты, и всю
переписку, а агенты дней 1–5 поднимаются заново из ростера. Это не недоделка,
а ровно постановка задачи Дня 7.

### API

| Ручка | Что делает |
|---|---|
| `GET /api/agents` | список агентов, группы и наличие ключа — всё для списка слева |
| `POST /api/agents` | «Новый чат» (пустое тело), один агент или пачка |
| `POST /api/agents/reset` | «Очистить все чаты»: сносит чаты, ростер оставляет |
| `GET /api/agents/{id}` | конфиг со стенограммой |
| `PATCH /api/agents/{id}` | панель справа: имя, промпт, модель, память, сэмплирование |
| `DELETE /api/agents/{id}` | убить агента |
| `POST /api/agents/{id}/messages` | сообщение агенту, тело — только `text`; SSE-поток |
| `POST /api/agents/{id}/regenerate` | перегенерировать последний ответ |
| `POST /api/agents/{id}/cancel` | погасить текущую генерацию |
| `GET /api/models` | каталог моделей для дропдауна |
| `GET /api/health` | ключ, реестр, потолок одновременных вызовов |

### Проверки

Живых вызовов к LLM в проверках нет ни одного — стрим подменяется заглушкой.

```bash
.venv/bin/python checks/spawn_100.py     # главный критерий дня
.venv/bin/python checks/run_checks.py    # все проверки, включая спавн сотни
node checks/browser_check.js             # клиент: markdown и раскладка
```

`run_checks.py` проверяет спавн сотни, дословность переноса дней 1–5, подъём
ростера и группировку, черновик вопроса, отсутствие сценариев в коде и ручках,
память диалога и окно, `409` на параллельных запросах, откат несостоявшегося
обмена, гашение вызова при обрыве, новые параметры сэмплирования (и то, что
незаданные не отправляются), правку живого агента, `reasoning` и честное время
до первого токена, перегенерацию — удачную и провалившуюся, — сохранность
ростера при очистке чатов, отсутствие ключа в интерфейсе и в ответах ручек,
отсутствие обращений в сеть из клиента, глубину копии конфига, вытеснение
по потолку, потолок пачки, общий httpx-клиент, совместимость `Session` и CLI.

Клиентский код проверяется **исполнением, а не чтением**: `checks/browser_check.js`
подключает `app/static/app.js` под node и гоняет разбор markdown настоящими
payload'ами — экранирование, схемы ссылок, разметку внутри кода — плюс решение
о раскладке узкого окна. Для этой части нужен `node`; без него проверка честно
падает, а не проходит молча.

## Как запустить

```bash
cp .env.example .env          # впишите OPENROUTER_API_KEY
python3.11 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn app.main:app --reload --port 8000
```

Откройте http://127.0.0.1:8000. Слева выберите агента — например «День 4 ·
t = 1.2»; вопрос того дня уже подставлен в поле ввода, останется нажать Enter.
Своя переписка начинается с кнопки «Новый чат».

Без браузера, из консоли:

```bash
.venv/bin/python -m app.cli
.venv/bin/python -m app.cli --history-limit 0     # тот же агент без памяти
echo "привет" | .venv/bin/python -m app.cli --once
```

Переменные окружения: `LLM_MAX_CONCURRENCY` — потолок одновременных вызовов
к модели, `AGENT_MAX_LIVE` — потолок живых агентов в реестре.

`.env` в `.gitignore`. Репозиторий публичный: ключ, попавший в коммит, отозвать
уже нельзя — никогда не коммитьте через `git add -A`.
