# День 07 — память агента: SQLite, сессии, восстановление

## Задание

```
🔥 День 7. Память агента

Добавьте агенту память:
👉 сохраняйте историю диалога
👉 передавайте её в следующий запрос
👉 храните историю между запусками программы

Результат:
Агент помнит предыдущие сообщения. После перезапуска диалог можно продолжить,
как будто агент не выключался.
```

День 6 закрыл первые два пункта: история жила в объекте `Agent` и уезжала
в следующий запрос окном. Третий пункт — «между запусками» — в README Дня 6
записан честно: «Ничего. Реестр живёт в памяти процесса: перезапуск стирает
и агентов, и все диалоги». Сегодня чинится ровно это.

## Промпт

Показать перезапуск на split-screen нельзя: обе колонки живут в одном процессе.
Поэтому день собран из двух сценариев — каждый показывает свою половину
постановки.

**Сценарий 1 — «Диалог, который переживает перезапуск»**, одна колонка.

| Колонка | Модель | `history_limit` | Что показывает |
|---|---|---|---|
| Планировщик · сессия в базе | [`openai/gpt-4o-mini`](https://openrouter.ai/openai/gpt-4o-mini) | 20 | разговор, который продолжают после `Ctrl+C` |

Системное сообщение (общее для обоих сценариев):

```
Ты — помощник по планированию поездок. Отвечай по-русски, коротко,
обычным текстом без markdown-разметки: без звёздочек, решёток и таблиц.
Если тебе не хватает данных о поездке, не выдумывай их — прямо скажи,
чего ты не знаешь, и спроси об этом.
```

Первый вопрос задаёт «Старт»:

```
Меня зовут Нина. Еду в Казань на три дня в середине октября,
бюджет на всё — 20 000 рублей, я вегетарианка и не вожу машину.
Набросай план поездки по дням.
```

Дальше руками: остановить `uvicorn` (`Ctrl+C`), поднять снова, обновить
страницу, открыть ту же сессию и спросить:

```
Что мне взять из одежды?
Где поужинать в первый вечер и сколько это будет стоить?
```

Ни города, ни дат, ни бюджета в этих вопросах нет.

**Сценарий 2 — «Две сессии в базе не смешиваются»**, две колонки. Один и тот же
агент, одна модель, `temperature=0.3`, `max_tokens=700`, один системный промпт;
различаются только сессии.

| Колонка | Первый вопрос | Что показывает |
|---|---|---|
| Сессия А · здесь представились | вводная про Нину и Казань | обычный разговор |
| Сессия Б · чужой разговор | «Как меня зовут и куда я еду?» | не знает и переспрашивает |

Судья во втором сценарии отвечает на один вопрос по существу: назвала ли правая
колонка имя, город или даты. Если назвала — истории двух сессий слились в одну
ленту, и это самая частая ошибка задания.

## Вывод

### Что демонстрируем

**Память между запусками.** После `Ctrl+C` и повторного `uvicorn` страница
открывается на той же сессии: лента на месте, и следующий вопрос уходит
в модель вместе со всей прошлой историей. Процесс, который слышал про поездку,
уже мёртв — историю вернули из файла:

```
до перезапуска:  [system] [«Меня зовут Нина. Еду в Казань…»] [план]
после:           [system] [«Меня зовут Нина. Еду в Казань…»] [план] [«Что мне взять из одежды?»]
```

**Изоляция сессий.** Правая колонка второго сценария отвечает «не знаю» — потому
что её реплики лежат в базе под своим `session_id`. Без него после перезапуска
все чаты слились бы в одну историю; в схеме это закрыто составным первичным
ключом, а не соглашением (см. ниже).

Самая короткая демонстрация — без браузера, двумя запусками подряд:

```bash
.venv/bin/python -m app.cli                     # «меня зовут Нина», запомнить id
.venv/bin/python -m app.cli --session ag_00001  # «как меня зовут?»
```

Второй запуск печатает `[продолжаем] в базе 2 реплик` и отвечает по существу.

### Как это устроено

**Хранилище** (`app/store.py`) — SQLite из стандартной библиотеки, ни одной
новой зависимости. Путь задаётся переменной `AGENT_DB_PATH`, по умолчанию
`data/agents.db`; проверки уводят его во временный каталог, чтобы не писать
в рабочий файл. Две таблицы, потому что восстанавливать надо сессию целиком,
а не только текст:

```sql
CREATE TABLE sessions (
    id TEXT PRIMARY KEY, parent_id TEXT, label TEXT,
    config TEXT,      -- конфиг агента одним JSON-полем
    seed TEXT, overrides TEXT, seed_used INTEGER,
    created_at REAL, updated_at REAL
);

CREATE TABLE messages (
    session_id TEXT NOT NULL, seq INTEGER NOT NULL,
    role TEXT NOT NULL, content TEXT NOT NULL, error TEXT, at REAL NOT NULL,
    PRIMARY KEY (session_id, seq)          -- ключевая строчка дня
);
CREATE INDEX messages_by_session ON messages(session_id);
```

**`session_id` в таблице сообщений — то, на чём спотыкаются.** Без него после
перезапуска два чата, поднятые из базы, читали бы одни и те же строки, и все
диалоги слились бы в один. Здесь это не соглашение, а первичный ключ: строку
сообщения физически нельзя записать, не сказав, чья она.

Ещё четыре детали, каждая из которых иначе всплывает:

- **`Store.init()` создаёт каталог** (`mkdir(parents=True)`), а не падает
  на пустом пути с «unable to open database file»;
- **`.gitignore` ловит `*.db`, `*.db-wal` и `*.db-shm`.** Режим WAL кладёт рядом
  с базой ещё два файла, и без двух последних строк половина истории уехала бы
  в публичный репозиторий. Это проверяется не глазами, а `git check-ignore`;
- **история пишется целиком, одной транзакцией**: `DELETE` реплик сессии плюс
  `INSERT` заново с номерами от нуля. Поэтому `seq` не получает дыр после отката
  несостоявшегося обмена и после кап-а хранимого, а оборванная запись
  откатывается вся — вопроса без ответа в базе не остаётся;
- **ключ вырезается на входе.** `OPENROUTER_API_KEY` живёт только в заголовке
  запроса (`app/llm.py`), но `extra_body` приходит от клиента, и вписать ключ
  туда — или в реплику диалога — можно руками. Всё, что уезжает в базу,
  проходит через `redact()`.

**Восстановление — в конструкторе агента**, а не отдельным вызовом из UI:
`Agent(spec, agent_id=…, store=…)` сам достаёт из базы конфиг, стартовые
сообщения, `overrides` и всю историю. Метода `restore()` нет намеренно — его
можно забыть позвать, и проверка следит, чтобы он не появился.

Запись идёт после каждого завершённого обмена, тем же правилом, что уже
действовало в памяти: несостоявшийся обмен не пишется вовсе, частичный ответ
пишется парой с вопросом и с пометкой ошибки. Кап окна остаётся каким был:
**в базу пишется вся история, в модель уезжает окно** `history_limit`.

**Счётчик id сдвигается по базе.** `ag_00001` выдаётся счётчиком процесса,
и после перезапуска он начинается с нуля. Без поправки второй запуск выдал бы
`ag_00001` заново, а конструктор поднял бы под этим id чужую историю: свежий
агент молча унаследовал бы прошлый диалог. Реестр сдвигает счётчик за
наибольший сохранённый id.

**Реестр стал реестром сессий** (`app/registry.py`). В памяти живут те агенты,
с которыми говорят сейчас; в базе лежат все. Отсюда главное различие дня:

- **вытеснение по потолку — это выгрузка**: агент уходит из памяти, строка
  в базе остаётся, и следующее обращение поднимает разговор с того же места;
- **удаление — это удаление**: `kill()` стирает из памяти и из базы, каскадом
  по детям в обоих слоях. Каскад в базе нужен отдельно: ребёнок, выгруженный
  из памяти раньше родителя, иначе остался бы в базе сиротой навсегда.

Поднятая из базы сессия честно встаёт в общую очередь на вытеснение, а не живёт
сверх потолка. Субагенты прогона — тоже сессии: `parent_id` лежит в таблице
и переживает перезапуск, иначе после рестарта дорожки прогона рассыпались бы.

**Клиент хранит один id.** В `localStorage` лежит только `ui.chat.session`;
ленту клиент по-прежнему не держит — она приезжает стенограммой сессии. Слева
список сохранённых сессий: живые помечены, остальные откроются из базы. «Новый
агент» больше не удаляет предыдущего собеседника — его сессия остаётся в списке,
а память процесса бережёт потолок реестра, который выгружает, а не стирает.

**Что осталось от Дня 6 без изменений.** Агент — по-прежнему класс, который
принимает текст, а не ленту; `messages` делятся на обстановку и первый ход;
откат по построению; `409` на двух параллельных запросах к одному агенту;
серия `repeats` коммитит только последний удачный прогон; сто агентов
спавнятся в одном процессе без единого вызова к модели; судья спавнится свежим
на каждый прогон; обрыв клиента гасит вызов; один `httpx`-клиент на процесс.
Имена SSE-событий не менялись.

**Починен один хвост Дня 6.** Вводная колонки уезжала в промпт, только пока
история пуста: после первого же ручного обмена стартовый вопрос молча исчезал
из промпта, хотя колонка продолжала показывать его в ленте. Признак теперь —
не «история пуста», а «стартовый вопрос уже стал ходом» (`seed_used`), и флаг
этот тоже лежит в базе.

### Что помнит стенд между запусками

Всё, что нужно, чтобы продолжить разговор: сессии с конфигом (модель,
семплирование, системный промпт, `history_limit`, `extra_body`), выбор модели,
сделанный руками, стартовые сообщения после подстановки `depends_on`, связь
`parent_id` и полную историю реплик с ролями, ошибками и временем.

Не помнит: метрики прогонов, вердикты как отдельную сущность (вердикт судьи —
обычная реплика в его сессии) и содержимое `.env`.

### API

| Ручка | Что делает |
|---|---|
| `POST /api/agents` | создать агента (`{"agent": …}`) или пачку (`{"agents": […]}`) |
| `GET /api/agents` | список живых агентов процесса |
| `GET /api/sessions` | **новое:** список сохранённых сессий, с пометкой `live` |
| `GET /api/agents/{id}` | конфиг со стенограммой; сессию из базы поднимает сам |
| `PATCH /api/agents/{id}` | сменить модель / `temperature` / `max_tokens` |
| `DELETE /api/agents/{id}` | удалить сессию каскадом — из памяти и из базы |
| `POST /api/agents/{id}/messages` | сообщение агенту, тело — только `text`; SSE-поток |
| `POST /api/agents/{id}/cancel` | погасить текущую генерацию |
| `POST /api/scenarios/{i}/agents` | спавн колонок сценария до «Старта» |
| `GET /api/run/{i}` | прогон сценария, контракт событий прежний |
| `GET /api/health` | ключ, реестр, число сохранённых сессий |

### Проверки

Живых вызовов к LLM в проверках нет ни одного — стрим подменяется заглушкой.

```bash
.venv/bin/python checks/restart.py       # главный критерий дня
.venv/bin/python checks/spawn_100.py     # главный критерий Дня 6
.venv/bin/python checks/run_checks.py    # все 45 проверок, включая обе выше
```

`checks/restart.py` — не «тот же объект в памяти»: скрипт запускает **два
отдельных процесса** питона и даёт им один файл базы. Первый знакомится
с агентом и умирает, второй поднимается с нуля и продолжает ту же сессию:

```
[1] процесс #1 (pid уже мёртв): сессия ag_00001, история ['user', 'assistant']
[2] процесс #1 закрыт, база на диске: 28672 байт
[3] процесс #2: поднято 2 реплик, в промпте 4 сообщений
[4] в промпте после перезапуска есть: Нина, Казань, вегетарианка
[5] новая сессия ag_00002 в той же базе не видит чужой истории
```

Всё, что проверяет `checks/run_checks.py`, — 31 проверка Дня 6 без послаблений
плюс 14 новых: перезапуск на уровне файла (закрыть, открыть заново, прочитать),
перезапуск на уровне процесса, восстановление в конструкторе, изоляция сессий
вместе со схемой таблицы, нумерация `seq` без дыр после отката и кап-а,
частичный ответ с пометкой ошибки, «вытеснение ≠ удаление», сохранность всех
сессий прогона вместе с `parent_id` и подстановкой `depends_on`, одновременная
запись из восьми сессий, отсутствие ключа в файлах базы, `git check-ignore`
на `*.db`/`*.db-wal`/`*.db-shm`, ручка сессий, `--session` в CLI и починенный
хвост с вводной колонки.

## Как запустить

```bash
cp .env.example .env          # впишите OPENROUTER_API_KEY
python3.11 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn app.main:app --reload --port 8000
```

Откройте http://127.0.0.1:8000. Главный экран — чат, слева список сохранённых
сессий. Сценарий дня: выберите первый сценарий, нажмите «Старт», дождитесь
ответа — затем остановите `uvicorn` через `Ctrl+C`, поднимите снова, обновите
страницу и задайте колонке следующий вопрос.

Без браузера, из консоли:

```bash
.venv/bin/python -m app.cli                     # новая сессия, id печатается сразу
.venv/bin/python -m app.cli --session ag_00001  # продолжить сохранённую
.venv/bin/python -m app.cli --history-limit 0   # тот же агент без памяти
echo "привет" | .venv/bin/python -m app.cli --once
```

Внутри диалога: `/выход`, `/история`, `/забыть`, `/агенты`, `/сессии`.

Переменные окружения: `AGENT_DB_PATH` — путь к базе (по умолчанию
`data/agents.db`), `LLM_MAX_CONCURRENCY` — потолок одновременных вызовов
к модели, `AGENT_MAX_LIVE` — потолок живых агентов в памяти.

`.env` и файлы базы — в `.gitignore`. Репозиторий публичный: ключ, попавший
в коммит, отозвать уже нельзя — никогда не коммитьте через `git add -A`.
