# День 06 — агент как отдельная сущность: чат-клиент со списком чатов

## Задание

```
🔥 День 6. Первый агент

Реализуйте простого агента, который:
👉 принимает запрос пользователя
👉 отправляет его в LLM через API
👉 получает ответ
👉 выводит результат в вашем интерфейсе

(простой чат, CLI или web, запросы через HTTP-клиент)

Важно:
👉 агент должен быть отдельной сущностью, а не просто один вызов API
👉 логика запроса и ответа должна быть инкапсулирована в агенте

Результат:
Агент принимает запрос и корректно вызывает LLM через API
```

Критерий проверки от организатора челленджа, дословно:

> Если тебе нужно будет моментально заспавнить 100 агентов с разными конфигами,
> у тебя это можно сделать? … Лучше чтобы инстанс был один, а уже внутри было
> поднято сто инстансов агента.

## Промпт

Промпта дня как такового нет: это чат, и вопрос задаёт пользователь.
Заготовок в стенде тоже нет — список чатов начинается пустым, у свежего чата
задана одна только модель, без неё запрос некуда отправить. Всё остальное —
промпт, параметры, формат ответа, окно памяти — пишет пользователь в панели.

## Вывод

### Интерфейс

Обычный чат-клиент. **Слева** — плоский список чатов: все чаты равны, у строки
карандаш (переименовать на месте) и корзина с подтверждением, внизу
переключатель темы. **По центру** — лента: вопрос компактным пузырём, ответ
карточкой с рамкой, в шапке модель и провайдер, справа «метрики», «копировать»,
«перегенерировать», «сырой текст». Поле ввода закреплено у нижнего края,
прокручивается лента; новый ответ доматывает её вниз, только если читатель
и так внизу. **Справа** — две вкладки: «Модель» (выбор модели, `temperature`,
`max_tokens`, `top_p`, `top_k`, `min_p`, три штрафа, окно памяти, формат ответа
и стоп-строки) и «Агент» (системный промпт), ниже строка состояния и плитки
метрик. Оба борта сворачиваются; на окне уже 940 px они становятся ящиками
поверх ленты.

**Инвариант чата: сообщение уходит только тогда, когда конфиг агента равен
тому, что показывает панель.** Перед каждой отправкой панель проливается
в агента, и если пролить не вышло — сообщение не уходит вовсе, с объяснением
под полем ввода. Держит инвариант `exchange` в `app/static/app.js` —
единственное место, через которое проходит всякая отправка, и своя,
и перегенерация. Строка «Применено» появляется не на каждый пролив, а только
когда правка действительно что-то изменила в конфиге.

**Панель предупреждает до отправки, а не после ошибки.** На каждом вызове
стоит `provider.require_parameters: true`, и заданный параметр, которого модель
не заявляет в `supported_parameters`, выкашивает провайдеров: `top_k` не
заявляют 215 моделей из 430. Отдельно ловится случай, по `supported_parameters`
не видный: 27 моделей `anthropic/*` честно перечисляют `temperature`
и всё равно возвращают 400 выше 1.0. Ещё панель предупреждает при смене
модели, если у чата в `extra_body` закреплён `provider.order`. Ничего из этого
не запрещает отправку — но вслепую упереться в ошибку провайдера уже
не получится.

**Из сети клиент не тянет ничего**: ни шрифтов, ни библиотек, ни иконок.
Иконки — inline SVG, markdown разбирается своими силами, и текст ответа
экранируется **до** разбора, поэтому разметка из ответа модели не может стать
разметкой страницы. Про ключ в интерфейсе нет ничего: он живёт в `.env`
и остаётся делом того, кто поднял сервер.

### Агент

**Агент — класс** (`app/agent.py`). Публичный метод принимает **текст
пользователя**, а не готовую ленту: агент сам склеивает системный промпт, окно
истории и новый вопрос, зовёт `stream_completion` и дописывает ответ себе
в историю. Веб-слой ему не нужен — тот же класс работает из консоли
(`python -m app.cli`).

- **системный промпт живёт ровно в одном месте** — `spec.system` — и читается
  оттуда на каждом обращении, поэтому правка в панели видна со следующего
  сообщения;
- **обмен идёт целиком на одном конфиге**: `ask()` снимает слепок в начале
  и собирает из него и промпт, и тело запроса. Править панель можно и во время
  генерации — текущий ответ правка исказить не может;
- **кап двойной**: окно `history_limit` ограничивает то, что уезжает в модель,
  `MAX_STORED_MESSAGES` — то, что живёт в памяти процесса. Ноль в окне — чат
  отвечает каждый вопрос как первый;
- **откат по построению**: история не трогается до конца обмена. Ответа
  не случилось — не записано ничего, вопрос возвращается в поле ввода;
- **один обмен на чат одновременно**: второй параллельный запрос получает `409`;
- **перегенерация заменяет последний ответ**: пара «вопрос — ответ» снимается
  с истории до вызова, а если вызов не отдал ни токена — возвращается на место.

**Реестр** (`app/registry.py`) — словарь `id → Agent`. Сто чатов с разными
конфигами — это сто объектов в одном процессе: ни потоков, ни подпроцессов,
ни единого вызова к модели. Есть потолок живых (`AGENT_MAX_LIVE`, по умолчанию
1000): при переполнении уходят самые старые простаивающие, занятый не
вытесняется никогда. За один запрос можно создать не больше 250 чатов.

Ответ на критерий организатора воспроизводится одной командой:

```bash
.venv/bin/python checks/spawn_100.py
```

```
[1] реестр: 100 агентов за 0.4 мс, живых 100
[2] POST /api/agents: 100 агентов за 2.1 мс (спавн внутри 0.93 мс), живых 100
[3] GET /api/agents: 100 живых, потолок 1000
[4] вызовов к модели за спавн: 0
[5] процесс один: pid=…, потоков 2, агентов 100
```

### Что помнит сервер между запусками

Ничего. Реестр живёт в памяти процесса: перезапуск стирает все чаты и всю
переписку. Это не недоделка, а ровно постановка задачи следующего дня.

### API

| Ручка | Что делает |
|---|---|
| `GET /api/agents` | плоский список чатов и наличие ключа |
| `POST /api/agents` | «Новый чат» (пустое тело), один чат или пачка |
| `GET /api/agents/{id}` | конфиг со стенограммой |
| `PATCH /api/agents/{id}` | имя, промпт, модель, память, сэмплирование, `stop`, `response_format` |
| `DELETE /api/agents/{id}` | удалить чат |
| `POST /api/agents/{id}/messages` | сообщение, тело — только `text`; SSE-поток |
| `POST /api/agents/{id}/regenerate` | перегенерировать последний ответ |
| `POST /api/agents/{id}/cancel` | погасить текущую генерацию |
| `GET /api/models` | каталог моделей для дропдауна |
| `GET /api/health` | ключ, реестр, потолок одновременных вызовов |

### Проверки

Живых вызовов к LLM в проверках нет ни одного — стрим подменяется заглушкой.

```bash
.venv/bin/python checks/spawn_100.py     # главный критерий дня
.venv/bin/python checks/run_checks.py    # все проверки, включая спавн сотни
node checks/browser_check.js             # клиент под node
```

`run_checks.py` гоняет сервер и агента: память и окно, откат, `409`, обрыв,
перегенерацию, реестр, каталог, CLI — и смотрит на то, что ушло бы в модель,
а не на ответ ручки.

Клиентский код проверяется **исполнением, а не чтением**: `checks/browser_check.js`
подключает настоящий `app/static/app.js` под node, а `checks/dom.js` даёт
минимальный DOM и минимальный сервер, который записывает, с каким конфигом
ушло каждое сообщение. Так проверяется весь маршрут — правка в поле панели,
отправка, тело запроса, — и положение ленты, и переименование чата. Для этого
нужен `node`; без него проверка честно падает, а не проходит молча.

## Как запустить

```bash
cp .env.example .env          # впишите OPENROUTER_API_KEY
python3.11 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn app.main:app --reload --port 8000
```

Откройте http://127.0.0.1:8000. Слева — список чатов, на чистом старте в нём
один пустой чат: пишите сразу. Следующие заводятся кнопкой «Новый чат».

Без браузера, из консоли:

```bash
.venv/bin/python -m app.cli
.venv/bin/python -m app.cli --history-limit 0     # тот же агент без памяти
echo "привет" | .venv/bin/python -m app.cli --once
```

Переменные окружения: `LLM_MAX_CONCURRENCY` — потолок одновременных вызовов
к модели, `AGENT_MAX_LIVE` — потолок живых агентов в реестре.

`.env` в `.gitignore`. Репозиторий публичный: ключ, попавший в коммит, отозвать
уже нельзя — никогда не коммитьте через `git add -A`.
