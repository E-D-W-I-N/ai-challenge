# День 07 — память чата: SQLite под обычным чат-клиентом

## Задание

```
🔥 День 7. Память агента

Добавьте агенту память:
👉 сохраняйте историю диалога
👉 передавайте её в следующий запрос
👉 храните историю между запусками программы

Результат:
Агент помнит предыдущие сообщения. После перезапуска диалог можно продолжить,
как будто агент не выключался.
```

Первые два пункта закрыл День 6: история жила в объекте `Agent` и уезжала
в следующий запрос окном. Третий — «между запусками» — чинится здесь, под тем
же интерфейсом: клиент Дня 6 переехал сюда целиком, а память легла под него.

## Промпт

Промпта дня как такового нет: это чат, и вопрос задаёт пользователь.
Заготовок в стенде тоже нет — список чатов начинается пустым, у свежего чата
задана одна только модель, без неё запрос некуда отправить. Всё остальное —
промпт, параметры, формат ответа, окно памяти — пишет пользователь в панели.

## Вывод

### Интерфейс

Обычный чат-клиент. **Слева** — плоский список чатов: все чаты равны, у строки
карандаш (переименовать на месте) и корзина с подтверждением, внизу
переключатель темы. **По центру** — лента: вопрос компактным пузырём, ответ
карточкой с рамкой, в шапке модель и провайдер, справа «метрики», «копировать»,
«перегенерировать», «сырой текст». Поле ввода закреплено у нижнего края,
прокручивается лента; новый ответ доматывает её вниз, только если читатель
и так внизу. **Справа** — две вкладки: «Модель» (выбор модели, `temperature`,
`max_tokens`, `top_p`, `top_k`, `min_p`, три штрафа, окно памяти, формат ответа
и стоп-строки) и «Агент» (системный промпт), ниже строка состояния и плитки
метрик. Оба борта сворачиваются; на окне уже 940 px они становятся ящиками
поверх ленты.

**Инвариант чата: сообщение уходит только тогда, когда конфиг агента равен
тому, что показывает панель.** Перед каждой отправкой панель проливается
в агента, и если пролить не вышло — сообщение не уходит вовсе, с объяснением
под полем ввода. Держит инвариант `exchange` в `app/static/app.js` —
единственное место, через которое проходит всякая отправка, и своя,
и перегенерация. Строка «Применено» появляется не на каждый пролив, а только
когда правка действительно что-то изменила в конфиге.

**Панель предупреждает до отправки, а не после ошибки.** На каждом вызове
стоит `provider.require_parameters: true`, и заданный параметр, которого модель
не заявляет в `supported_parameters`, выкашивает провайдеров: `top_k` не
заявляют 215 моделей из 430. Отдельно ловится случай, по `supported_parameters`
не видный: 27 моделей `anthropic/*` честно перечисляют `temperature`
и всё равно возвращают 400 выше 1.0. Ещё панель предупреждает при смене
модели, если у чата в `extra_body` закреплён `provider.order`. Ничего из этого
не запрещает отправку — но вслепую упереться в ошибку провайдера уже
не получится.

**Из сети клиент не тянет ничего**: ни шрифтов, ни библиотек, ни иконок.
Иконки — inline SVG, markdown разбирается своими силами, и текст ответа
экранируется **до** разбора, поэтому разметка из ответа модели не может стать
разметкой страницы. Про ключ в интерфейсе нет ничего: он живёт в `.env`
и остаётся делом того, кто поднял сервер.

### Агент

**Агент — класс** (`app/agent.py`). Публичный метод принимает **текст
пользователя**, а не готовую ленту: агент сам склеивает системный промпт, окно
истории и новый вопрос, зовёт `stream_completion` и дописывает ответ себе
в историю. Веб-слой ему не нужен — тот же класс работает из консоли
(`python -m app.cli`).

- **системный промпт живёт ровно в одном месте** — `spec.system` — и читается
  оттуда на каждом обращении, поэтому правка в панели видна со следующего
  сообщения;
- **обмен идёт целиком на одном конфиге**: `ask()` снимает слепок в начале
  и собирает из него и промпт, и тело запроса. Править панель можно и во время
  генерации — текущий ответ правка исказить не может;
- **кап двойной**: окно `history_limit` ограничивает то, что уезжает в модель,
  `MAX_STORED_MESSAGES` — то, что живёт в памяти процесса. Ноль в окне — чат
  отвечает каждый вопрос как первый;
- **откат по построению**: история не трогается до конца обмена. Ответа
  не случилось — не записано ничего, вопрос возвращается в поле ввода;
- **один обмен на чат одновременно**: второй параллельный запрос получает `409`;
- **перегенерация заменяет последний ответ**: пара «вопрос — ответ» снимается
  с истории до вызова, а если вызов не отдал ни токена — возвращается на место.

**Реестр** (`app/registry.py`) — словарь `id → Agent` поверх хранилища. Сто
чатов с разными конфигами — это сто объектов в одном процессе: ни потоков,
ни подпроцессов, ни единого вызова к модели. Есть потолок живых
(`AGENT_MAX_LIVE`, по умолчанию 1000): при переполнении самые старые
простаивающие **выгружаются** — строка в базе остаётся, из списка запись
не исчезает, открытие поднимает разговор с того же места. Занятый не
вытесняется никогда. За один запрос можно создать не больше 250 чатов.

Ответ на критерий организатора прошлого дня воспроизводится одной командой:

```bash
.venv/bin/python checks/spawn_100.py
```

### Память между запусками

**Хранилище** (`app/store.py`) — SQLite из стандартной библиотеки, ни одной
новой зависимости. Путь задаётся переменной `AGENT_DB_PATH`, по умолчанию
`data/agents.db`. Три таблицы:

```sql
CREATE TABLE sessions (
    id TEXT PRIMARY KEY, label TEXT,
    config TEXT,                 -- конфиг чата одним JSON-полем
    context_length INTEGER,
    created_at REAL, updated_at REAL
);

CREATE TABLE messages (
    session_id TEXT NOT NULL, seq INTEGER NOT NULL,
    role TEXT NOT NULL, content TEXT NOT NULL, error TEXT, metrics TEXT,
    at REAL NOT NULL,
    PRIMARY KEY (session_id, seq)          -- ключевая строчка дня
);
CREATE INDEX messages_by_session ON messages(session_id);

CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);
```

- **`session_id` в первичном ключе сообщений** — то, на чём спотыкаются: без
  него два чата, поднятые из базы, читали бы одни и те же строки, и список
  слева слился бы в один диалог. Здесь это не соглашение, а ключ;
- **конфиг — одним JSON-полем**, а не колонкой на параметр: в базе сами собой
  оказываются имя, системный промпт, стоп-строки, формат ответа, окно памяти
  и все шесть параметров сэмплирования, потому что сохраняется `asdict(spec)`;
- **история пишется целиком, одной транзакцией**: `DELETE` реплик чата плюс
  `INSERT` заново с номерами от нуля, поэтому `seq` не получает дыр,
  а оборванная запись откатывается вся — вопроса без ответа не остаётся;
- **`meta` — счётчики, общие на всю базу.** Сейчас один: номер, из которого
  собирается имя нового чата. В памяти процесса ему мало — после перезапуска
  счёт начался бы с единицы и выдал бы занятое имя;
- **id чата выдаёт база, а не процесс**: консоль запускают рядом с поднятым
  сервером, база у них общая, и два процесса выдали бы один `ag_00004`.
  Поэтому id занимается `INSERT`-ом строки, а арбитр — первичный ключ.
  Транзакции берут `BEGIN IMMEDIATE`; не дождались блокировки — ручка
  отвечает `503` с объяснением, а не голым `500`;
- **ключ вырезается на входе**: транзакция отдаёт не соединение, а обёртку,
  которая чистит через `redact()` строковый параметр **любого** запроса, —
  чистить список колонок, который надо помнить, не приходится;
- **восстановление — в конструкторе агента**: `Agent(spec, agent_id=…, store=…)`
  сам достаёт конфиг и историю; отдельного метода, который можно забыть
  позвать, нет. Список слева строится по базе и не обрезается: обрезка резала
  бы по времени последней записи, то есть по чатам, с которыми ещё не говорили.

Не пишется в базу только рассуждение модели: в контекст оно не возвращается,
а места занимает больше ответа. Метрики пишутся — по ним клиент рисует плитки,
и после рестарта лента выглядит так же.

### API

| Ручка | Что делает |
|---|---|
| `GET /api/agents` | плоский список чатов и наличие ключа |
| `POST /api/agents` | «Новый чат» (пустое тело), один чат или пачка |
| `GET /api/agents/{id}` | конфиг со стенограммой |
| `PATCH /api/agents/{id}` | имя, промпт, модель, память, сэмплирование, `stop`, `response_format` |
| `DELETE /api/agents/{id}` | удалить чат |
| `POST /api/agents/{id}/messages` | сообщение, тело — только `text`; SSE-поток |
| `POST /api/agents/{id}/regenerate` | перегенерировать последний ответ |
| `POST /api/agents/{id}/cancel` | погасить текущую генерацию |
| `GET /api/models` | каталог моделей для дропдауна |
| `GET /api/health` | ключ, реестр, число сохранённых чатов |

### Проверки

Живых вызовов к LLM в проверках нет ни одного — стрим подменяется заглушкой.

```bash
.venv/bin/python checks/restart.py       # главный критерий дня: два процесса подряд
.venv/bin/python checks/two_processes.py # сервер и консоль на одной базе
.venv/bin/python checks/spawn_100.py     # критерий прошлого дня
.venv/bin/python checks/run_checks.py    # все проверки, включая три выше
node checks/browser_check.js             # клиент под node
```

`checks/restart.py` — не «тот же объект в памяти»: скрипт запускает **два
отдельных процесса** питона и даёт им один файл базы; `two_processes.py` берёт
то, чего последовательные процессы поймать не могут, — двух живых писателей
сразу. `run_checks.py` гоняет сервер, агента и память и смотрит на то, что ушло
бы в модель и что легло в колонки, а не на ответ ручки.

Клиентский код проверяется **исполнением, а не чтением**: `checks/browser_check.js`
подключает настоящий `app/static/app.js` под node, а `checks/dom.js` даёт
минимальный DOM и минимальный сервер, который записывает, с каким конфигом
ушло каждое сообщение. Так проверяется весь маршрут — правка в поле панели,
отправка, тело запроса, — и положение ленты, и переименование чата. Для этого
нужен `node`; без него проверка честно падает, а не проходит молча.

## Как запустить

```bash
cp .env.example .env          # впишите OPENROUTER_API_KEY
python3.11 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn app.main:app --reload --port 8000
```

Откройте http://127.0.0.1:8000. Слева — список чатов, на чистом старте в нём
один пустой чат: пишите сразу. Следующие заводятся кнопкой «Новый чат».

Сценарий дня: поговорите в любом чате, остановите `uvicorn` через `Ctrl+C`,
поднимите снова и обновите страницу. Список, лента и все поля панели на месте,
а следующий вопрос уходит вместе со всей прошлой историей.

Без браузера, из консоли:

```bash
.venv/bin/python -m app.cli                     # новый чат, id печатается сразу
.venv/bin/python -m app.cli --session ag_00001  # продолжить сохранённый
echo "привет" | .venv/bin/python -m app.cli --once
```

Внутри диалога: `/выход`, `/история`, `/забыть`, `/агенты`, `/сессии`. Консоль
можно запускать и при поднятом сервере: база у них одна, и это штатный режим —
id чатов и номера имён выдаёт она, а не процесс.

Переменные окружения: `AGENT_DB_PATH` — путь к базе (по умолчанию
`data/agents.db`), `LLM_MAX_CONCURRENCY` — потолок одновременных вызовов
к модели, `AGENT_MAX_LIVE` — потолок живых агентов в памяти.

`.env` и файлы базы — в `.gitignore`. Репозиторий публичный: ключ, попавший
в коммит, отозвать уже нельзя — никогда не коммитьте через `git add -A`.
