# День 20 — оркестрация: несколько серверов, длинный флоу

```
🔥 День 20. Оркестрация
Несколько MCP-серверов. Агент выбирает нужный инструмент, корректно
маршрутизирует запросы, выполняет длинный флоу.
```

## Вывод

Кода день почти не добавил: оркестрация уже есть. В `mcp.json` живут четыре
сервера — `echo` (стенд связи), `git`, `remind`, `pipeline`; реестр разруливает
имена и коллизии (`сервер__инструмент`, день 16), цикл вызовов исполняет и
показывает каждый вызов (день 17), цепочку ведёт модель (день 19). Выбор
инструмента — тоже модели: в payload уезжает полный список инструментов всех
живых серверов, с описанием и схемой от каждого.

День добавляет **проверки** двум обещаниям оркестрации:

* **маршрутизация реестром, и только**: вызов уезжает в сервер по записи
  реестра (`ToolRef`), порядок вызовов в кадре — порядок исполнения и
  tool-сообщений в рабочем списке. Один обмен с вызовами двух разных серверов
  (git_log из git, ping из echo, одним кадром и в обратном конфигу порядке)
  проверен сквозным сценарием: каждый результат — от своего сервера,
  tool-сообщения легли в порядке просьбы, метрики обмена называют сервер
  каждого вызова;
* **упавший на старте сервер изолирован**: остальные стартуют, обмен идёт,
  его инструментов нет в объявленных `tools` (модель про них не знает), а в
  ручке `/api/mcp` он виден со статусом `down` — пропажа не молчит.

## Клиент

Во вкладке «Инструменты» у сервера с полем `reminders` — блок под его
инструментами: счётчики по состояниям и каждая запись с текстом и
временем. Пока вкладка открыта, следующий запрос идёт через 2 секунды после
завершения предыдущего:
переворот «ждёт → сработало» виден живьём, без единого действия.
Уход из настроек/раздела, скрытый документ и pagehide останавливают
опрос и отменяют GET; поздний ответ отвергается. Повторный вход сразу
обновляет агрегат, раскрытые схемы сохраняются.

«Чат» и «Настройки» используют центральную рабочую область. Светлый интерфейс
рассчитан на компьютер и ноутбук: шесть страниц с вертикальной навигацией,
гибкие формы и сворачиваемый список чатов. Переключение сохраняет выбранный чат, черновик сообщения,
прокрутку, активный ответ и шапку задачи. Все шесть метрик доступны снизу;
в компактном окне строка прокручивается горизонтально. Длинный текст
переносится, код и JSON прокручиваются; при zoom можно свернуть список чатов.

Аватар справа в шапке открывает настоящий глобальный профиль: стиль, формат
и контекст ответа. Меню показывает записанные значения и ведёт в тот же
редактор «Профиль». Поля сохраняются при уходе фокуса; ошибка оставляет текст
для повторной попытки. Профиль, долговременная память и инварианты действуют
во всех чатах, модель, промпт и рабочая память — в выбранном чате.

Стрелки, Home и End переключают вкладки. Escape закрывает меню профиля
или подтверждение; фокус возвращается к открывшей
кнопке. В редакторе записи Enter сохраняет, Shift+Enter добавляет строку,
Escape отменяет. В обоих слоях памяти остаются ручное добавление, правка
и удаление с явным выбором типа записи. Поиск названий, копирование ответа
кнопкой и перенос рабочей записи кнопкой убраны; текст можно выделить
и перенести в форму долговременной памяти вручную.

Клиент загружает обычные локальные скрипты `text.js` → `records.js` → `app.js`,
без сборки и новых зависимостей. Карта файлов и чтения по задаче — в
[руководстве клиента](docs/client-guide.md).

## Проверки

```bash
make check          # весь офлайн-набор: сервер, subprocess и клиент
make check-browser  # отдельно настоящий клиент под Node.js
```

Нужны Python >= 3.11 и Node.js. `make check` проверяет наличие Node.js и
запускает `checks/run_checks.py` один раз: он уже включает `restart.py`,
`two_processes.py` и `browser_check.js`. Клиент исполняется как CommonJS aggregate
и как три классических скрипта из HTML с явными API/SSE-фикстурами. Ошибки завершают
команду ненулевым кодом; живых вызовов модели и настоящего ключа проверки не требуют.

Новые три: сквозной обмен с вызовами двух серверов одним кадром — каждый
уехал в свой (по содержимому tool-сообщений: настоящий коммит от git, эхо-ответ
от echo), порядок сохранён в рабочем списке, бейджах и метриках; полный список
инструментов трёх живых серверов в теле запроса (сверен с тем, что сами
серверы отдали в `/api/mcp`, — без захардкоженного эталона); упавший на
initialize зонд не роняет старт: обмен проходит, в `tools` только живые, в
ручке — статус down. Описания и схемы каждого объявленного инструмента
сравниваются с живым списком серверов. Pipeline и remind запускаются через
test-only модули с временными ROOT/output/SQLite внутри настоящего дочернего
процесса; пользовательские файлы и базы не затрагиваются, whitelist env сохранён.

## Как запустить

```bash
make help
make setup
# Только если .env ещё нет; ключ впишите локально, файл в .gitignore:
if [ ! -e .env ] && [ ! -L .env ]; then cp .env.example .env; fi
make run                # http://127.0.0.1:8000
```

`make setup` создаёт `.venv` через `python3.11` и устанавливает зависимости
из `requirements.txt`. Если интерпретатор лежит в другом месте:
`make setup PYTHON=/path/to/python`. `PYTHON` выбирает только создание новой
среды; существующая `.venv` переиспользуется и тоже должна иметь Python >= 3.11.
Повторный setup не пересоздаёт среду и не создаёт/перезаписывает `.env`.
`make run` запускает `.venv/bin/python -m uvicorn app.main:app --reload --port 8000`.

## Работа через OpenCode и Pi

Запускайте установленный инструмент **из корня этого checkout/worktree**:

```bash
opencode
# или
pi
```

Оба инструмента автоматически включают корневой `AGENTS.md` в контекст
([правила OpenCode](https://opencode.ai/docs/rules/),
[контекст Pi](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/README.md)).
Ссылка на `docs/architecture.md` не загружает файл сама: агент обязан прочитать
нужные разделы перед изменениями, как требует `AGENTS.md`.

Модель и авторизация — личные настройки каждого инструмента; задавайте их
в его интерфейсе/пользовательском конфиге, не в отслеживаемых файлах проекта
и не в `.env` приложения. Ключ OpenRouter приложения не настраивает
OpenCode/Pi. Корневой `mcp.json` управляет серверами **приложения**, а не
MCP coding-агентов; переносить его в настройки инструментов не нужно.
Общие команды проекта одинаковы: `make setup`, `make run`, `make check`.

## Пример длинного флоу

Модель может обработать просьбу «собери отчёт, сохрани и напомни проверить
через минуту» в пределах четырёх запросов модели: `git_log` (git) и `search`
(pipeline) одним кадром, затем `summarize` с реальной выдачей, затем
`save_file` (pipeline) и `remind` (remind) одним кадром; четвёртый запрос
даёт финальный ответ. Независимые вызовы внутри кадра исполняются последовательно.
Клиент показывает вызовы под ответом, файл лежит в `files/`, состояние
напоминания видно во вкладке «Инструменты». Выбор кадров принадлежит модели;
проверки измеряют офлайн-контракт, результаты живого прогона не выдумываются.

## Что осталось честно назвать

* **Выбор и порядок вызовов — у модели**: проверки стерегут маршрутизацию
  и изоляцию, но не то, что живая модель выберет правильный инструмент, —
  это показывает живой прогон.
* **Вызовы внутри кадра исполняются по очереди**, не параллельно: порядок
  важнее скорости — модель читает tool-сообщения позиционно.
* **Упавший посреди сессии сервер не перезапускается**: его вызовы кончаются
  tool-сообщением с ошибкой (день 17), сам он остаётся в списке до рестарта.
* **Сторож инвариантов отмечает совпавшие слова, а не выносит приговор**:
  законный отказ, цитата вопроса или имя пакета могут дать ложную отметку;
  словоформы не распознаются. Ответ остаётся целым, решение принимает человек.
* _Живой прогон на ключе:_ **место под числа оставлено пустым — впишет человек.**
