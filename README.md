```
🔥 День 20. Оркестрация
Несколько MCP-серверов. Агент выбирает нужный инструмент, корректно
```

## Вывод

Кода день почти не добавил: оркестрация уже есть. В `mcp.json` живут четыре
сервера — `echo` (стенд связи), `git`, `remind`, `pipeline`; реестр разруливает
имена и коллизии (`сервер__инструмент`, день 16), цикл вызовов исполняет и
показывает каждый вызов (день 17), цепочку ведёт модель (день 19). Выбор
инструмента — тоже модели: в payload уезжает полный список инструментов всех
живых серверов, с описанием и схемой от каждого.

День добавляет **проверки** двум обещаниям оркестрации:

* **маршрутизация реестром, и только**: вызов уезжает в сервер по записи
  реестра (`ToolRef`), порядок вызовов в кадре — порядок исполнения и
  tool-сообщений в рабочем списке. Один обмен с вызовами двух разных серверов
  (git_log из git, ping из echo, одним кадром и в обратном конфигу порядке)
  проверен сквозным сценарием: каждый результат — от своего сервера,
  tool-сообщения легли в порядке просьбы, метрики обмена называют сервер
  каждого вызова;
* **упавший на старте сервер изолирован**: остальные стартуют, обмен идёт,
  его инструментов нет в объявленных `tools` (модель про них не знает), а в
  ручке `/api/mcp` он виден со статусом `down` — пропажа не молчит.

## Проверки

```bash
make check          # весь офлайн-набор: сервер, subprocess и клиент
make check-browser  # отдельно настоящий клиент под Node.js
```

Нужны Python >= 3.11 и Node.js. `make check` проверяет наличие Node.js и
запускает `checks/run_checks.py` один раз: он уже включает `restart.py`,
`two_processes.py`, `spawn_100.py` и `browser_check.js`. Ошибки завершают
команду ненулевым кодом; живых вызовов модели и настоящего ключа проверки не требуют.

Новые три: сквозной обмен с вызовами двух серверов одним кадром — каждый
уехал в свой (по содержимому tool-сообщений: настоящий коммит от git, эхо-ответ
от echo), порядок сохранён в рабочем списке, бейджах и метриках; полный список
инструментов трёх живых серверов в теле запроса (сверен с тем, что сами
серверы отдали в `/api/mcp`, — без захардкоженного эталона); упавший на
initialize зонд не роняет старт: обмен проходит, в `tools` только живые, в
ручке — статус down.

## Как запустить

```bash
make help
make setup
# Только если .env ещё нет; ключ впишите локально, файл в .gitignore:
test -e .env || cp .env.example .env
make run                # http://127.0.0.1:8000
```

`make setup` создаёт `.venv` через `python3.11` и устанавливает зависимости
из `requirements.txt`. Если интерпретатор лежит в другом месте:
`make setup PYTHON=/path/to/python`. `PYTHON` выбирает только создание новой
среды; существующая `.venv` переиспользуется и тоже должна иметь Python >= 3.11.
Повторный setup не пересоздаёт среду и не создаёт/перезаписывает `.env`.
`make run` запускает `.venv/bin/python -m uvicorn app.main:app --reload --port 8000`.

Запускайте установленный инструмент из корня этого worktree:

Оба инструмента автоматически включают корневой `AGENTS.md` в контекст

В нём агенту предписано перед изменениями читать относящиеся к ним разделы
[архитектуры](docs/architecture.md); ссылка сама по себе не загружает весь документ.
Модель и авторизация инструмента — личный выбор: настройте их в пользовательских
настройках OpenCode/Pi вне репозитория (в Pi — `/model` и `/login`).
Ключ приложения в `.env` и модели приложения от этого не меняются.
Корневой `mcp.json` принадлежит приложению и описывает его MCP-серверы;
это не конфигурация инструментов разработки.

## Пример длинного флоу

Длинный флоу для живого прогона (снимается на видео): одна просьба «собери
отчёт по TODO за неделю, сохрани и напомни проверить через минуту». Модель
ведёт цепочку через четыре сервера в одном обмене: `git_log` (git) → `search`
(pipeline) → `summarize` (pipeline) → `save_file` (pipeline) → `remind`
(remind); под ответом — пять бейджей подряд, файл лежит в `files/`, а через
минуту напоминание переворачивается в «сработало» во вкладке «Инструменты»
(она перезапрашивается раз в 2 секунды, пока открыта).

## Что осталось честно назвать

* **Выбор и порядок вызовов — у модели**: проверки стерегут маршрутизацию
  и изоляцию, но не то, что живая модель выберет правильный инструмент, —
  это показывает живой прогон.
* **Вызовы внутри кадра исполняются по очереди**, не параллельно: порядок
  важнее скорости — модель читает tool-сообщения позиционно.
* **Упавший посреди сессии сервер не перезапускается**: его вызовы кончаются
  tool-сообщением с ошибкой (день 17), сам он остаётся в списке до рестарта.
* **Сторож инвариантов отмечает совпавшие слова, а не выносит приговор**:
  законный отказ, цитата вопроса или имя пакета могут дать ложную отметку;
  словоформы не распознаются. Ответ остаётся целым, решение принимает человек.
* _Живой прогон на ключе:_ **место под числа оставлено пустым — впишет человек.**
