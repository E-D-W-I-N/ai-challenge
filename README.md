# День 08 — подсчёт токенов: вход, выход, всего

## Задание

```
🔥 День 8. Работа с токенами

Добавьте в код агента подсчёт токенов:
👉 для текущего запроса
👉 для всей истории диалога
👉 для ответа модели

Сравните:

👉 короткий диалог
👉 длинный диалог
👉 диалог, который превышает лимит модели

Покажите:

👉 как растёт стоимость/токены по мере диалога
👉 что ломается при переполнении

Результат:

Код, который считает токены и показывает, как они влияют на поведение агента
```

Половина задания досталась в наследство: в каждом запросе стоит
`"usage": {"include": true}`, и OpenRouter присылает последним чанком **точные**
`prompt_tokens`, `completion_tokens`, `total_tokens`, `reasoning_tokens` и
`cost` — свои оценки токенизатором были бы враньём. Не хватало всего по обмену
в одном месте рядом с входом и выходом и суммы по диалогу: «токены для всей
истории» брать было неоткуда.

Заказчик сузил день до подсчёта: **вход, выход, всего**. Переполнение контекста
— задача следующего дня, и здесь агент от него не защищается: окно памяти
режется по числу сообщений, а ошибка провайдера показывается как есть.

## Промпт

Промпта дня как такового нет: это чат, и вопрос задаёт пользователь. Заготовок
в стенде тоже нет — список чатов начинается пустым, у свежего чата задана одна
только модель. Всё остальное — промпт, параметры, формат ответа, окно памяти —
пишет пользователь в панели.

## Вывод

### Что видно на экране

**Четыре плитки внизу справа показывают два числа сразу.** Крупное — последний
обмен, мелкое рядом со знаком «Σ» — накопленное по всему чату:

| Плитка | Крупно | Подпись |
|---|---|---|
| **Вход** | `prompt_tokens` обмена | Σ вход по чату |
| **Выход** | `completion_tokens` обмена | Σ выход по чату, либо токены рассуждения |
| **Всего** | `total_tokens` обмена | Σ всего по чату |
| **Стоимость** | цена обмена | Σ цена чата |

Сетка осталась 2×4: новых строк не добавилось, «Промпт, ток» и «Ответ, ток»
переименованы во «Вход» и «Выход». Подпись «Выхода» занята рассуждением, когда
оно есть: на думающей модели выход без него необъясним.

**Под каждым ответом в ленте — своя строка:**

```
вход 1 240 · выход 312 · всего 1 552 · $0.000186
```

Это и есть ответ на «как растёт по мере диалога»: плитки показывают итог,
а прокрутка ленты — каждый обмен по отдельности, и видно, как вход пухнет
от реплики к реплике, пока выход остаётся прежним. Строки нет вовсе, если чисел
нет или ответ оборвался: у оборванного они неполные, и место им в плитках
по кнопке «метрики», а не мелким шрифтом над текстом ошибки.

**Ноль и «неизвестно» выглядят по-разному**: прочерк значит «не знаем», ноль
значит «ноль». Тысячи разделяются, от десяти тысяч число сокращается:
`1 240`, `12.4k`, `128.6k`.

### Как считается

**Сумма по чату считается на сервере** — `Agent.usage_summary()` в
`app/agent.py`, рядом со стенограммой. В браузере её считать нельзя: тогда итог
в плитках и числа в ленте — два источника правды, и разъезжаются они молча.
Клиент получает готовое поле `usage_total` тем же путём, что и длину истории.

Отдельной колонки в базе у суммы нет: она выводится из `messages.metrics`,
которые и так лежат в базе у каждой реплики. Значит, она переживает перезапуск
сама собой и не может разойтись со слагаемыми.

Правила счёта, каждое закреплено проверкой:

- **реплика без метрик и поле `None` пропускаются, а не считаются нулём**:
  провайдер вправе смолчать о цене, и «$0.000000» тут было бы неправдой;
- **чат без единого ответа с числами даёт `None`, а не сводку из нулей** —
  в интерфейсе это прочерк;
- **суммируются только ответы модели**: вопрос пользователя метрик не имеет;
- **перегенерация заменяет обмен, а не добавляет**: пара «вопрос — ответ»
  снимается с истории до вызова, и сумма после неё не удваивается;
- **неудачный вызов в сумму не попадает**: не отдал ни токена — не записан
  в историю. Оборванный на середине записан и посчитан — он оплачен.

### Агент

**Агент — класс** (`app/agent.py`). Публичный метод принимает **текст
пользователя**, а не готовую ленту: агент сам склеивает системный промпт, окно
истории и новый вопрос, зовёт `stream_completion` и дописывает ответ себе
в историю. Веб-слой ему не нужен — тот же класс работает из консоли
(`python -m app.cli`).

- **системный промпт живёт ровно в одном месте** — `spec.system` — и читается
  оттуда на каждом обращении: правка в панели видна со следующего сообщения;
- **обмен идёт целиком на одном конфиге**: `ask()` снимает слепок в начале
  и собирает из него и промпт, и тело запроса;
- **кап двойной**: окно `history_limit` режет то, что уезжает в модель,
  `MAX_STORED_MESSAGES` — то, что живёт в памяти процесса;
- **откат по построению**: история не трогается до конца обмена;
- **один обмен на чат одновременно**: второй параллельный запрос получает `409`.

**Инвариант чата держится в клиенте**: сообщение уходит только тогда, когда
конфиг агента равен тому, что показывает панель, — иначе не уходит вовсе,
с объяснением под полем ввода.

**Реестр** (`app/registry.py`) — словарь `id → Agent` поверх хранилища; сто
чатов с разными конфигами живут в одном процессе. При переполнении потолка
(`AGENT_MAX_LIVE`) старые простаивающие **выгружаются**: строка в базе
остаётся, открытие поднимает разговор с того же места.

### Память между запусками

**Хранилище** (`app/store.py`) — SQLite из стандартной библиотеки, ни одной
новой зависимости; путь задаётся `AGENT_DB_PATH`.

```sql
CREATE TABLE sessions (                    -- чат: конфиг одним JSON-полем
    id TEXT PRIMARY KEY, label TEXT, config TEXT, context_length INTEGER,
    created_at REAL, updated_at REAL
);
CREATE TABLE messages (
    session_id TEXT NOT NULL, seq INTEGER NOT NULL,
    role TEXT NOT NULL, content TEXT NOT NULL, error TEXT, metrics TEXT,
    at REAL NOT NULL,
    PRIMARY KEY (session_id, seq)          -- ключевая строчка Дня 07
);
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);   -- счётчик имён
```

- **`session_id` в первичном ключе сообщений**: без него два чата, поднятые
  из базы, читали бы одни и те же строки;
- **конфиг — `asdict(spec)`**, новое поле оказывается в базе само;
  **`metrics` у реплики** — то, из чего этот день собирает сумму;
- **история пишется целиком, одной транзакцией**, номера от нуля, без дыр;
- **id чата выдаёт база**: консоль и сервер работают на одном файле, и два
  процесса выдали бы один `ag_00004`. Не дождались блокировки — `503`
  с объяснением, а не голый `500`;
- **ключ вырезается на входе**: транзакция отдаёт обёртку, которая чистит
  строковый параметр любого запроса.

### API

| Ручка | Что делает |
|---|---|
| `GET /api/agents` | плоский список чатов и наличие ключа |
| `POST /api/agents` | «Новый чат» (пустое тело), один чат или пачка |
| `GET /api/agents/{id}` | конфиг, стенограмма и `usage_total` — сумма по чату |
| `PATCH /api/agents/{id}` | имя, промпт, модель, память, сэмплирование, `stop`, `response_format` |
| `DELETE /api/agents/{id}` | удалить чат |
| `POST /api/agents/{id}/messages` | сообщение, тело — только `text`; SSE-поток |
| `POST /api/agents/{id}/regenerate` | перегенерировать последний ответ |
| `POST /api/agents/{id}/cancel` | погасить текущую генерацию |
| `GET /api/models` | каталог моделей для дропдауна |
| `GET /api/health` | ключ, реестр, число сохранённых чатов |

### Проверки

Живых вызовов к LLM нет ни одного — стрим подменяется заглушкой, и usage у неё
**задаётся**: с одинаковыми числами у всех ответов сумма трёх обменов сошлась
бы и при правильном сложении, и при `100 × длина истории`.

```bash
.venv/bin/python checks/run_checks.py    # все проверки, включая три ниже
.venv/bin/python checks/restart.py       # два процесса подряд на одном файле
.venv/bin/python checks/two_processes.py # сервер и консоль на одной базе
.venv/bin/python checks/spawn_100.py     # сто агентов в одном процессе
node checks/browser_check.js             # клиент под node
```

Клиентский код проверяется **исполнением, а не чтением**: `browser_check.js`
подключает настоящий `app/static/app.js` под node, а `checks/dom.js` даёт
минимальный DOM и минимальный сервер, отдающий настоящие кадры SSE с числами.
Про плитки здесь утверждается то, что видно глазами: какое число стоит крупно,
какое подписью и совпадает ли подпись с суммой строк в ленте.

Каждая проверка этого дня доказана откатом: то, что она стережёт, ломали
и смотрели, что она краснеет.

## Как запустить

```bash
cp .env.example .env          # впишите OPENROUTER_API_KEY
python3.11 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn app.main:app --reload --port 8000
```

Откройте http://127.0.0.1:8000. Слева — список чатов, на чистом старте в нём
один пустой чат: пишите сразу.
Что смотреть: задайте в одном чате три-четыре вопроса подряд и следите
за плитками «Вход», «Выход», «Всего», «Стоимость» и за строкой под каждым
ответом. Вход растёт от обмена к обмену — в модель уезжает вся история, — Σ
растёт быстрее всего, а выход остаётся примерно прежним; короткий диалог
от длинного этим и отличается. Переполнение видно на модели с маленьким
контекстом: ответ провайдера показывается как есть, обмен в историю
не пишется и в сумму не попадает.

Без браузера, из консоли:

```bash
.venv/bin/python -m app.cli                     # новый чат, id печатается сразу
.venv/bin/python -m app.cli --session ag_00001  # продолжить сохранённый
echo "привет" | .venv/bin/python -m app.cli --once
```

Внутри диалога: `/выход`, `/история`, `/забыть`, `/агенты`, `/сессии`. Консоль
можно запускать и при поднятом сервере: база у них одна, и это штатный режим.

Переменные окружения: `AGENT_DB_PATH` — путь к базе (по умолчанию
`data/agents.db`), `LLM_MAX_CONCURRENCY` — потолок одновременных вызовов,
`AGENT_MAX_LIVE` — потолок живых агентов в памяти.

`.env` и файлы базы — в `.gitignore`. Репозиторий публичный: ключ, попавший
в коммит, отозвать уже нельзя — никогда не коммитьте через `git add -A`.
