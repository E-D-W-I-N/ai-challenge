# День 19 — пайплайн из трёх инструментов

```
🔥 День 19. Пайплайн из инструментов
Несколько MCP-инструментов (search, summarize, saveToFile): первый получает
данные, второй обрабатывает, третий сохраняет. Автоматическое выполнение
цепочки, корректность передачи данных.
```

## Вывод

Сервер `pipeline` (`app/mcp_servers/pipeline.py`) несёт три инструмента:

| инструмент | что делает |
|---|---|
| `search(query, limit=20)` | подстрока по репозиторию: `git grep -n -i -F --untracked`. Выдача отсортирована по (файл, строка) и только потом обрезана до `limit` — git свой порядок не обещает. Пустая выдача — честное «ничего не найдено», а не выдумка |
| `summarize(text, max_items=10)` | **механический** конденсат выдачи search: дедуп строк, группировка по файлам, обрезка до `max_items` групп — и обрезка названа числом. Без LLM принципиально: ключа у процесса нет |
| `save_file(name, content)` | пишет в `files/` — единственное файловое место записи. Имя санитизируется: непустое, без «/», «\\» и «..»; отказ — текстом, и файла не появляется |

Цепочку ведёт **модель**: цикл вызовов дня 17 сам доводит её до конца без
участия человека — search, видит результат, зовёт summarize с ним в
аргументе, затем save_file с выводом summarize. «Автоматическое выполнение»
— это «без человека», а не «мимо модели»: кода, передающего результат
одного инструмента в другой, нет. Передача данных — через tool-сообщения
рабочего списка, и на видео это три бейджа подряд под ответом
(`search · pipeline · N мс` и т.д., день 17), а файл появляется в `files/`.

## Проверки

```bash
.venv/bin/python checks/run_checks.py    # 69 проверок, включая семь новых и клиентскую
.venv/bin/python checks/restart.py       # два процесса подряд на одном файле
.venv/bin/python checks/two_processes.py # сервер и консоль на одной базе
.venv/bin/python checks/spawn_100.py     # сто агентов в одном процессе
node checks/browser_check.js             # клиент под node, 377 утверждений
```

Новые семь: search детерминирован (повтор совпадает, top-N, перемешанный
вход отсортирован); пустая выдача — честный отказ; summarize на
фиксированном входе даёт эталонный выход побайтово (дедуп, группы, лимит);
save_file пишет в каталог из `PIPELINE_FILES_DIR` побайтово; пять форм
нечестного имени — пять отказов, каталог пуст; настоящий процесс через
McpManager отдаёт три инструмента, и search находит известную строку в коде;
сквозная цепочка из трёх вызовов — аргумент summarize содержит результат
search, аргумент save_file — вывод summarize (читается из
`CALLS[n].payload["messages"]`, там же, где увидела бы модель).

Заодно починен регистратор заглушки: `build_payload` ссылается на живой
рабочий список, и цикл вызовов дописывал tool-сообщения в тело уже
записанного, давнего вызова — теперь записывается снимок (deepcopy).

## Как запустить

```bash
cp .env.example .env    # впишите OPENROUTER_API_KEY; он в .gitignore
python3.11 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn app.main:app --reload --port 8000
```

В `mcp.json` четыре сервера: `echo` (стенд связи), `git`, `remind` и
`pipeline`. Спросите «найди упоминания require_parameters, сожми выдачу и
сохрани в файл» — под ответом будут три бейджа подряд, а файл ляжет в
`files/` (каталог в `.gitignore`: репозиторий публичный, не коммитьте
`git add -A`).

## Что осталось честно назвать

* **summarize не понимает текст**: группировка держится на форме строки
  «файл:номер: текст»; строка другой формы уезжает в группу «(без файла)»
  как есть.
* **Цепочка из трёх звеньев — четыре обращения к модели**: каждое оплачено,
  и их сумму показывает панель (usage складывается по итерациям, день 17).
* **Сортировка search — страховка**: на практике git отдаёт выдачу уже
  упорядоченной, но порядок не обещан, и проверка бьёт по перемешанному
  входу.
* _Живой прогон на ключе:_ **место под числа оставлено пустым — впишет человек.**
