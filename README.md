# День 05 — слабая / средняя / сильная модель: latency, токены, cost

Локальный стенд для заданий AI-челленджа: прогоняет сценарии дня и показывает их
результаты рядом, колонка к колонке, а под каждой на ходу считает метрики.

**Ветка — это день.** В этой ветке лежит День 05: стенд, его сценарий и этот
README. Остальные дни живут в своих ветках — `day-01`, `day-02` и дальше, — и
каждая заморожена целиком, вместе с той версией стенда, на которой день снимали.

К моделям стенд ходит через [OpenRouter](https://openrouter.ai): API совместим
с OpenAI, каждая колонка спрашивает свою модель, а `usage.cost` приходит в ответе.

## Запуск

```bash
cp .env.example .env          # впишите OPENROUTER_API_KEY
python3.11 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn app.main:app --reload --port 8000
```

Откройте http://127.0.0.1:8000. Сценарий в этом дне один, поэтому стенд открывает
его сразу — жмите «Старт».

`.env` в `.gitignore`. Репозиторий публичный: ключ, попавший в коммит, отозвать уже
нельзя. Никогда не коммитьте через `git add -A`.

Дропдаун моделей работает и без ключа: каталог `/api/v1/models` авторизации не требует.

## Структура

```
app/              стенд
  main.py         FastAPI: сценарии, прогон, ручной чат, SSE-потоки
  schema.py       Scenario / Session — датаклассы сценария
  llm.py          стриминг OpenRouter и сбор метрик
  catalog.py      /api/v1/models с кэшем и фильтрами
  config.py       поиск ключа
  static/         index.html, app.js, style.css
day.py            колонки этого дня: промпты и параметры
```

`day.py` объявляет `SCENARIOS` — список сценариев дня; порядок в списке задаёт
и порядок в сайдбаре, и индекс, по которому стенд адресует сценарий
(`GET /api/run/0`). Стенд импортирует день напрямую, поэтому сломанный `day.py`
роняет приложение на старте с объяснением: прятать ошибку не от кого, день
в ветке один.

## Задание дня

Формулировка пользователя, дословно:

> **День 05 — split ×3: слабая / средняя / сильная модель.**
> Колонки latency, токенов и `cost` рядом.
> Сравните: качество ответов, скорость, ресурсоёмкость.
> Короткий вывод о различиях между моделями.

## Решение

Один сценарий, три колонки, `layout="split"`. Одна и та же задача уходит в три
модели разной силы одновременно, и колонки отличаются **ровно одним полем —
`model`**: промпт, `temperature=0.2` и `max_tokens=8000` одинаковы во всех трёх,
поэтому разницу в ответах и в цифрах можно приписать модели, а не настройкам.
Каждая колонка делает ровно один вызов: это сравнительный анализ качества
и цены, а не бенчмарк задержки.

| Ступень | Модель | in, $/1M | out, $/1M |
|---|---|---|---|
| Слабая | `meta-llama/llama-3.1-8b-instruct` | 0.05 | 0.08 |
| Средняя | `mistralai/mistral-small-3.2-24b-instruct` | 0.075 | 0.20 |
| Сильная | `google/gemini-3.1-flash-lite` | 0.25 | 1.50 |

Выход сильной ступени дороже выхода слабой примерно в 19 раз. Это дефолт
сценария — ступени можно поменять в дропдауне UI на каждой колонке.

Пример подобран так, чтобы ступени разошлись: курьерская служба набирает смену
из шести заказов под лимиты веса и времени. Посчитать такую задачу в лоб нельзя,
максимум ищется перебором сочетаний, а обе естественные жадные стратегии дают
неверный ответ. Слабая ступень сортирует по одному признаку и останавливается,
сильная перебирает — и это видно по её же разбору.

Отвечает модель тремя частями: рассмотренные наборы по строке на каждый,
рекомендация диспетчеру простым языком и четыре машиночитаемые строки в хвосте.
Хвост — ось проверки правильности, разбор — материал, по которому видна сила
модели: на трёх голых числах о качестве судить нечего.

Судью день спрашивает ровно о том, о чём просит задание: качество разборов
и понятность рекомендации, скорость с ресурсоёмкостью по метрикам и короткий
вывод о различиях моделей.

## Промпт

Промпт один на все три колонки.

Системное сообщение:

```
Ты — планировщик смены в курьерской службе. Ты показываешь ход разбора
с промежуточными числами и заканчиваешь короткой рекомендацией диспетчеру.
Пишешь обычным текстом без markdown-разметки и строго соблюдаешь структуру
ответа, заданную пользователем.
```

Сообщение пользователя:

```
Курьерская служба формирует смену. Есть шесть заказов:

Заказ A: вес 30 кг, время 90 мин, оплата 5000 ₽
Заказ B: вес 25 кг, время 60 мин, оплата 4200 ₽
Заказ C: вес 40 кг, время 80 мин, оплата 6000 ₽
Заказ D: вес 20 кг, время 50 мин, оплата 3300 ₽
Заказ E: вес 35 кг, время 70 мин, оплата 5200 ₽
Заказ F: вес 15 кг, время 40 мин, оплата 2400 ₽

Машина везёт не больше 100 кг, смена длится не больше 240 минут.
Заказы берутся целиком — часть заказа взять нельзя.

Какой набор заказов даёт максимальную выручку?

Отвечай обычным текстом, без markdown: без звёздочек, решёток, маркеров списка
и таблиц из вертикальных палочек. Структура ответа — ровно такая и в таком порядке:

РАЗБОР
Наборы, которые ты рассматривал, по одной строке на набор, каждая в таком виде:
<буквы заказов через запятую>: вес <кг>; время <мин>; выручка <руб>; <вердикт>
В вердикте — либо почему набор отброшен (какой лимит нарушен или чем он хуже
другого), либо что он остаётся кандидатом. Наборы, нарушающие лимиты, тоже
показывай.

РЕКОМЕНДАЦИЯ
Одно-два предложения простым языком для диспетчера, без формул: что ставить
в смену.

Последними — ровно четыре строки, каждая с начала строки, и ничего после них:
НАБОР: <буквы заказов через запятую>
ВЫРУЧКА: <число>
ВЕС: <число>
ВРЕМЯ: <число>

В этих четырёх строках — только буквы заказов и целые числа: без единиц
измерения, без знака рубля и без пробелов внутри чисел.
```

## Ожидаемый результат

Эталонный ответ:

```
НАБОР: B, C, D, F
ВЫРУЧКА: 15900
ВЕС: 100
ВРЕМЯ: 230
```

**Решение единственное** — второго набора с выручкой 15 900 ₽ нет. Вес забит
ровно под завязку: 100 из 100 кг, время 230 из 240 минут. Допустимых непустых
наборов — 43 из 63.

Оптимум не совпадает ни с одной жадной выборкой, поэтому колонка, которая
сортирует вместо перебора, промахивается — и промах виден по её же разбору:

| Стратегия | Набор | Выручка | Недобор |
|---|---|---:|---:|
| **Оптимум** | B, C, D, F | **15 900** | — |
| Брать по убыванию оплаты | C, E, B | 15 400 | −500 |
| Брать по убыванию оплаты за килограмм | B, A, D, F | 14 900 | −1000 |

Жадность «по оплате за минуту» даёт тот же `C, E, B` — то есть **две из трёх**
естественных жадных стратегий садятся ровно в первую ловушку. Ответ `15400` —
не случайная ошибка в арифметике, а выбранный метод.

Ближайшие к оптимуму допустимые наборы, для полноты картины:

| Набор | Выручка | Вес | Время |
|---|---:|---:|---:|
| B, C, D, F | 15 900 | 100 | 230 |
| B, C, E | 15 400 | 100 | 210 |
| A, B, C | 15 200 | 95 | 230 |
| B, D, E, F | 15 100 | 95 | 220 |
| A, B, D, F | 14 900 | 90 | 240 |

**Чем колонки отличаются друг от друга.** По четырём итоговым строкам сразу
видно, какая колонка попала в эталон, а какая — в жадную ловушку. Колонка ещё
обязана сходиться сама с собой: сумма весов и времён названного ею набора должна
давать её же `ВЕС` и `ВРЕМЯ` и укладываться в 100 кг и 240 минут. Выше хвоста
различия видны в разборе: сколько наборов колонка вообще рассмотрела (одна
строка — это не перебор, а жадность с оформлением), честно ли посчитаны вес
и время в каждой строке и каким методом она выбирала. Отдельный сорт ошибки —
когда набор `B, C, D, F` в разборе встречается, а в хвост уходит другой.

Рядом с текстом стенд показывает три числа на колонку — задержку, токены
и `usage.cost`, — а внизу сводку: суммарную стоимость, суммарно токенов,
wall-clock, самую быструю и самую дешёвую колонку. Главное наблюдение дня:
**самая быстрая и самая дешёвая колонки не совпадают с самой правильной.**

После колонок стенд делает один дополнительный вызов к модели-судье (дефолт
стенда — `openai/gpt-4o`, `judge_model` в сценарии не задан) и стримит её ответ
в блок «Вердикт». Судья сравнивает качество разборов, понятность рекомендации,
скорость с ресурсоёмкостью и делает короткий вывод о различиях моделей.
Эталона он не знает и правильную колонку определяет сам, так что его вердикт
тоже может разойтись с ответом выше. Стоимость судьи попадает в сводку отдельной
строкой и не смешивается с суммой по колонкам.

## Что показывает стенд

Колонка устроена как чат: сверху лента сообщений, под ней метрики, внизу поле
ввода. Промпт из `Session.messages` стенд показывает **до** старта: `system` идёт
приглушённым блоком и сворачивается по клику, `user` — заметным пузырём. Ответ
модели стримится под ними как `assistant`.

Колонки занимают всю высоту экрана, и высоту у них не отбирают ни блок
«Вердикт», ни сводка: оба встают **под** экраном колонок — к ним прокручиваются,
а ленты стенд не сжимает. Три колонки делят ширину поровну, на узком экране
встают друг под друга; горизонтального скролла нет ни при какой ширине, внутри
колонки скроллится только лента. Список сценариев сворачивает кнопка в его
шапке, и свёрнутым он останется после перезагрузки. В шапке сценария стенд
держит одну строку: название, селекторы моделей и «Старт». `description` он
на экран не показывает — тот уходит модели-судье.

В поле под лентой можно **писать модели руками** — до прогона и после
(`POST /api/chat`). В модель уходит вся накопленная лента колонки, поэтому
диалог продолжается; параметры стенд берёт из `Session`, модель — из селектора
в шапке. Enter отправляет, Shift+Enter переносит строку. Без ключа поле
недоступно и говорит, чего не хватает.

Когда все колонки отработали, под ними появляется блок **«Вердикт»**. Отдельная
модель-судья отвечает на вопросы задания дня — их день перечисляет
в `judge_questions`, — и её ответ стримится так же, как ответы колонок. Судью
стенд зовёт один раз за прогон и только там, где вопросы заданы: день, которому
нечего сравнивать, за судью не платит. Судье уходят `description` сценария, эти
вопросы, а по каждой колонке — `label`, `note`, отличающие параметры, метрики
и полный текст ответа. Промпты колонок и этот README ему не уходят: разбор
показал бы ответ до того, как судья посмотрит на данные.

Колонку можно прогнать не один раз, а серией: `Session.repeats` говорит, сколько
раз подряд отправить тот же запрос. Каждый прогон встаёт в ленте отдельным
блоком со своей строкой метрик, а над панелью метрик стенд считает долю
уникальных ответов. День 05 повторов не просит: серия утроила бы стоимость ради
задержки, а сравниваем мы качество разбора.

Под колонкой стенд на ходу считает время до первого токена (TTFT), скорость
в ток/с, сгенерированные токены и прошедшее время, а из ответа берёт токены
`prompt`/`completion`/`total`, reasoning-токены, стоимость в долларах,
`finish_reason`, модель, фактического провайдера и заполнение контекста.
В сводке он складывает стоимость и токены всего прогона, показывает wall-clock
и стоимость судьи, а когда колонок больше одной — называет самую быструю
и самую дешёвую.

Сам стенд делает ещё несколько вещей, о которых день не просит:

- шлёт `provider: {"require_parameters": true}` на **каждом** вызове. Без него
  OpenRouter вправе увести запрос к провайдеру, который молча проигнорирует
  `temperature` или `stop`, и день покажет неправду;
- шлёт `usage: {"include": true}` — стоимость и reasoning-токены приходят
  в финальном чанке;
- обрывает вызовы, когда клиент ушёл: закрытая вкладка, перезагрузка страницы
  или оборванный SSE гасят все сессии прогона, а не дают им дожечь токены
  в пустоту.

## Подводные камни

Каждый пункт проверен, и каждый ломает день молча.

- **Эталон лежит только в этом файле.** `description` и `note` колонок стенд
  отдаёт судье дословно, поэтому чисел `B, C, D, F` / `15900` в `day.py` нет
  нигде, кроме комментария к модулю. А вот **условие задачи в `description`
  лежит намеренно**: промпты колонок судье не отправляются, и без шести заказов
  с числами и обоих лимитов судья не смог бы ни пересчитать набор, ни поймать
  колонку на выдуманном весе.
- **`finish_reason` проверяйте до сравнения.** Если у колонки он оказался
  `length`, а не `stop`, ответ обрезан по `max_tokens`: у неё нет ни
  машиночитаемого хвоста, ни хвоста разбора, и ни разбор, ни токены со
  стоимостью по такой колонке сравнивать нельзя. `max_tokens=8000` взят
  с запасом на самую многословную ступень — добросовестная колонка выписывает
  десятки наборов по строке на каждый, а сильная докладывает сверху reasoning,
  который тоже считается в лимит.
- **`extra_body={"provider": {"allow_fallbacks": False}}`** стоит в каждой
  колонке. Без него OpenRouter вправе увести запрос к другому провайдеру,
  и станет непонятно, чью задержку и чью цену мы измерили.
  `provider.require_parameters` стенд шлёт сам — дублировать не нужно.
- **Сравнение задержек здесь грубое.** При одном вызове на колонку первый запрос
  платит за установление соединения — DNS, TLS, холодный коннект, — и три
  колонки делят эту плату по-разному; TTFT в панели это включает и не отделяет.
  Для сравнительного анализа порядка величин достаточно, для замера
  производительности — нет: нужны повторные прогоны с отброшенным прогревочным
  и медиана.
- **Ни `:free`, ни `:batch` вариантов тут нет намеренно:** у `:free` стоимость
  всегда 0 (сравнивать нечего), у `:batch` другая семантика задержки. Оба
  варианта стенд отфильтровал из каталога.
- **`usage.cost_details.upstream_inference_cost` без BYOK всегда 0**, поэтому
  его нет в таблицах выше. Смотрим только `usage.cost`.
- **Ответ требуется обычным текстом, без markdown:** стенд рисует сообщения
  через `textContent` с `white-space: pre-wrap`, переносы строк сохраняются,
  а звёздочки и палочки таблиц остались бы мусором.

## Как это устроено

**Стенд.** Весь его код лежит в `app/`. Внутри у каждого файла своё дело:
`main.py` держит HTTP и гонит в браузер поток событий, `schema.py` описывает
сценарий датаклассами, `llm.py` разговаривает с OpenRouter и попутно считает
метрики, `catalog.py` приносит список моделей, а интерфейс живёт в `static/`.

**Сценарий ничего не выполняет — он только описывает.** `day.py` объявляет
`SCENARIOS`: сценарий собран из колонок, а колонка говорит, какую модель
спросить, каким промптом и с какими параметрами запроса. Дальше работает стенд.

**Прогон.** Открываете стенд, жмёте «Старт» — колонки уходят к моделям и печатают
ответы по мере генерации. Обычно все разом, но если колонке нужен ответ соседней,
она дождётся его и пойдёт следом. Под каждой на ходу считаются метрики: время
до первого токена, скорость, токены, стоимость. Когда все колонки договорили,
стенд одним запросом спрашивает модель-судью и разворачивает её ответ в блоке
«Вердикт», а ниже подводит сводку по прогону.
