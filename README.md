# День 23 — фильтрация RAG и query rewrite

```
🔥 День 23. Реранкинг и фильтрация

Добавьте второй этап после поиска:

👉 reranker или фильтр релевантности (порог similarity / отдельная модель / heuristic)

Настройте:

👉 порог отсечения нерелевантных результатов
👉 топ-K до и после фильтрации

Сравните:

👉 качество без фильтра/rewriting
👉 качество с фильтром

Результат:

Улучшенный RAG: фильтрация/реранкинг + query rewrite + сравнение режимов
```

## Вывод

RAG включается отдельно для каждого чата и по умолчанию выключен. При включении доступны
независимые переключатели «Уточнение запроса (Rewrite)» и «Отбор по релевантности (Filtering)»;
в новых чатах они включены, в старых без этих полей сохраняется прежнее поведение.
Параметры поиска видны при включённом отборе; скрытие сохраняет введённые значения.
Стандартные параметры: 20 кандидатов, 5 итоговых фрагментов, порог cosine 0.3.
Оба K — целые от 1 до 100, итоговое K не больше числа кандидатов; порог от -1 до 1,
граница включительна. Фильтр не вызывает модель и не требует переиндексации.

Query rewrite делает один дополнительный вызов текущей модели чата с отдельным
служебным промптом: текущий вопрос и последние три полные успешные пары истории.
Результат используется только для поиска; итоговая генерация получает исходный
вопрос. Лимит ожидания — 60 секунд, автоматических повторов нет. Пустой/невалидный
JSON, незавершённый ответ или отказ модели дают явную ошибку и возвращают ввод.
Настройки чата, MCP-инструменты и инструкции не передаются служебному вызову.

Поиск берёт кандидатов и identity индекса из одного закреплённого SQLite чтения,
фильтрует по порогу и ограничивает итоговое K. При выключенном фильтре остаётся
обычный cosine порядок; при обоих выключенных этапах поиск сразу берёт итоговое K.
Если после отбора источников нет, приложение сохраняет ответ
«В базе не найдена подходящая информация» без генерации по общим знаниям.
При RAG OFF поиск и rewrite не выполняются.

Полноширинный инспектор ответа показывает исходный и поисковый запрос, использованную
историю, параметры, кандидатов с причинами исключения, итоговые полные фрагменты,
точный контекст, время и фактическую стоимость rewrite. JSON содержит все реально
отправленные запросы, включая rewrite. Успешные метрики учитывают его один раз;
неизвестная стоимость остаётся неизвестной. Интерактивная ошибка до записи обмена
показывает полученные метрики и JSON временно, но не создаёт запись в истории или
отдельный долговременный счётчик неудачных вызовов. Ошибка отложенного напоминания
сохраняет доступные метрики вместе с его сообщением об ошибке.

`rag` остаётся самостоятельным пакетом внутри проекта. Используется существующий
HTML-корпус и опубликованный индекс; эмбеддинги предоставляет отдельный oMLX.
Новых сервисов, ключей и переменных окружения не требуется. Корпус, приватные кэши,
вопросы и отчёты остаются локальными данными оператора.

## Сравнение ответов

На одном опубликованном индексе задайте одинаковый вопрос в двух новых чатах
с одинаковой моделью и прочими настройками. В обоих включите RAG; в первом
отключите rewrite и фильтр, во втором включите оба. Сравните полноту и фактическую
точность ответа, найденные источники, исключённые кандидаты, токены и стоимость.
Используйте сохранённые снимки, чтобы видеть точные условия каждого ответа.
Порог и оба K можно менять отдельно; отдельного compare UI нет.

Живое сравнение на пользовательском корпусе здесь не проведено. Offline-проверки
подтверждают контракты приложения, а не улучшение качества конкретной модели.

## Общие команды

Из корня репозитория, с Python >=3.11, `make` и Node.js в PATH:

```bash
make help
make setup
# Если python3.11 не в PATH или нужен другой интерпретатор >=3.11:
make setup PYTHON=/path/to/python
make run             # http://127.0.0.1:8000, автоматическая перезагрузка
make check           # весь offline-набор, включая subprocess и клиент
make check-browser   # только клиентские проверки под Node.js
```

`PYTHON` выбирает интерпретатор только для создания `.venv`. Setup проверяет
версию, создаёт окружение при отсутствии или использует существующее и
устанавливает `requirements.txt`; повторный запуск сохраняет окружение.
Он не создаёт и не перезаписывает `.env`. Все последующие Python-команды
выполняются через `.venv/bin/python`; ошибки команд дают ненулевой exit code.

Приложение читает из окружения и `.env` только `OPENROUTER_API_KEY` и
`RAG_EMBEDDING_API_KEY`. Модель генерации по умолчанию в чате, CLI и RAG —
`openai/gpt-6-luna`; сохраняемые настройки чатов продолжают определять их модель.
База чатов — `data/agents.db`, корпус/индекс — `data/rag`, начальный MCP конфиг —
`mcp.json`. Другие прикладные env настройки не поддерживаются; адреса, модели
и параметры задаются в существующих формах или явных CLI аргументах сервисов.
Стандартные PATH/HOME/LANG и HTTP proxy окружение сохраняют своё назначение.

Для ручного диалога создайте `.env` из `.env.example`, только если его ещё
нет, и задайте `OPENROUTER_API_KEY` локально. Ключ не нужен offline-проверкам.
Секреты не выводите и не коммитьте; используйте только точечный `git add`,
никогда `git add -A` или `git add .`.

## Проверки

Проверки используют временный нейтральный CP1251 HTML, настоящий HTTP embedding
stub, отдельный CLI и SQLite, без живого инференса. Проверяются chunk slices,
cache fingerprint, cosine, валидация векторов, atomic failure, writer lock,
interrupted/stale, bounded API и настоящий клиент под Node с lazy vector/late GET.
День 22 проверяется на нейтральных временных снимках и HTTP-заглушках: ON/OFF,
согласованность контекста и сохранённого снимка, ошибки поиска до генерации,
история после изменения индекса и переключение настройки текущего чата.
День 23: включительный порог/cap, три пары rewrite, strict stop и JSON, отмена/timeout,
пустой отбор без генерации, реальные JSON/usage, legacy/restart/ветвление и напоминания.
Сохраняется весь offline-набор предыдущих дней: чат, память, задачи, MCP и pipeline.

Подробности: [архитектура](docs/architecture.md), [карта клиента и ручной просмотр](docs/client-guide.md).

## Как запустить

### Чат с RAG

Сначала опубликуйте индекс через этапы ниже. Откройте чат → «Настройки → Агент»
и включите «Использовать RAG в этом чате». Вернитесь в «Чат» и задайте вопрос.
Просмотрите источники под ответом и сохранённый контекст. Кнопка «К текущему
индексу» возвращает к существующим этапам индексации, не меняя историю ответа.
Отключение checkbox возвращает обычную генерацию для следующих вопросов.
Для сравнения режимов включите RAG и настройте rewrite/фильтр и оба K рядом.

### Индексация из терминала

Подготовьте **локальный** JSON manifest, например `data/rag/inputs.json`:

```json
[
  {"path": "article.html"}
]
```

Относительный path разрешается относительно manifest. Для HTTP-входов
добавьте объект с полем `url`; для локальной копии можно задать `source`.
Можно повторять `--url` вместо manifest. CLI не импортирует конфигурацию чата
и не читает `.env`.
Приложение использует фиксированный каталог `data/rag`; CLI использует его по умолчанию,
а `--root` позволяет оператору работать с отдельным каталогом:

Примеры ниже используют oMLX на порту 8005, как начальное поле UI;
укажите фактический адрес и ID модели своего сервера.

```sh
.venv/bin/python -m rag ingest --manifest data/rag/inputs.json
.venv/bin/python -m rag index --base-url http://127.0.0.1:8005/v1 \
  --model Qwen3-Embedding-0.6B-8bit --batch-size 16
.venv/bin/python -m rag status
make run
```

Для уже запущенного oMLX с авторизацией на порту 8005 в zsh введите ключ
скрыто и укажите точный embedding model ID из списка моделей этого сервера:

```zsh
read -rs 'RAG_EMBEDDING_API_KEY?Ключ oMLX: '; print
export RAG_EMBEDDING_API_KEY
read -r 'RAG_EMBEDDING_MODEL?Embedding model ID сервера: '
.venv/bin/python -m rag index --base-url http://127.0.0.1:8005/v1 \
  --model "$RAG_EMBEDDING_MODEL" --batch-size 16
unset RAG_EMBEDDING_API_KEY
```

Ключ вводится в prompt, без аргумента CLI и записи в историю команд;
авторизация сервера остаётся включённой. CLI по-прежнему не читает `.env`.

Ingest сохраняет frozen corpus.json и ingest-report.json с ошибками/словами и
оценкой страниц; при любом отказе прежний корпус остаётся. Повторный index
использует кэш. Сборка пишет временную SQLite и атомарно заменяет index.sqlite
только после успеха; прежний индекс доступен при ошибке/остановке. Один OS lock
исключает конкурирующих писателей. Atomic replace — граница успеха; отказ записи
завершающего progress после replace оставляет новый индекс готовым и даёт
диагностическое предупреждение, без обещания отката опубликованной SQLite.
Изменённый корпус отмечает индекс как stale.

Сравнение выполняется отдельно в терминале на том же frozen corpus и конфиге:

```sh
.venv/bin/python -m rag compare --base-url http://127.0.0.1:8005/v1 \
  --model Qwen3-Embedding-0.6B-8bit
```

Оба индекса сохраняются в `comparisons/fixed` и `comparisons/structural`,
локальный comparison.json содержит число чанков, длины, перекрытие, разделы,
модель и fingerprint. Активный индекс не заменяется. Это сравнение разбиения;
качество ответа/поиска на контрольных вопросах здесь не измеряется.

### Отдельные этапы CLI

Отдельные CLI этапы (прежний `index` также поддерживается):

```sh
.venv/bin/python -m rag chunks --strategy fixed --size 1200 --overlap 180
.venv/bin/python -m rag chunks --strategy semantic --size 1200 --overlap 180 \
  --semantic-base-url https://openrouter.ai/api/v1 --semantic-model openai/gpt-6-luna
.venv/bin/python -m rag embed --base-url http://127.0.0.1:8005/v1 --model YOUR_MODEL
.venv/bin/python -m rag save
.venv/bin/python -m rag clear index  # сохраняет все предыдущие этапы и кэши
.venv/bin/python -m rag clear embeddings
.venv/bin/python -m rag clear chunks
```

### Просмотр и запуск этапов в UI

Откройте `http://127.0.0.1:8000` → «Настройки → Работа RAG». Страница работает
без чата/ключа, читает фактические стадии CLI `documents → chunks → embeddings → save`,
счётчики кэша/новых векторов, длительность, модель и размерность. После сохранения
видны объём корпуса, версия/байты/число строк SQLite, документы и чанки с
границами/текстом/метаданными. Раскрытие отдельно читает настоящий числовой
вектор выбранного чанка. Refresh открывает сохранённый индекс; missing/stale/
interrupted/error названы явно, предыдущий индекс при отказе виден отдельно.
UI запускает отдельные этапы «Загрузить документы» → «Разбить на чанки» →
«Создать эмбеддинги» → «Сохранить индекс». Укажите явные URL; локальный HTML
доступен только из фиксированного manifest `data/rag/inputs.json`, без ввода путей в HTTP.
На этапе «Документы» выберите подготовку «Кодом» (по умолчанию) или
«Полностью через LLM»: генеративная модель получает HTML, очищает его и
восстанавливает структуру без пересказа. Для LLM доступны OpenRouter/oMLX,
редактируемый URL и список моделей сервера — как при семантическом разбиении.
Настройки подготовки, разбиения и эмбеддингов независимы; переключение
провайдера сохраняет черновик каждого этапа. Модель подготовки, токены и
фактическая стоимость доступны в «Фактическое состояние операции».
Для медленной локальной модели увеличьте «Ожидание ответа, с»: по умолчанию
600 секунд, допустимо 1–3600; настройка относится только к подготовке документов.
Размер и перекрытие задаются в символах. Для LLM поле называется
«Максимальный размер чанка»: модель выбирает смысловые границы, код ограничивает
размер групп и добавляет заданное перекрытие. В UI доступны «По размеру» и
«Семантическое · LLM». Для semantic по умолчанию OpenRouter /
`openai/gpt-6-luna`; endpoint редактируется, модель выбирается из каталога
сервера; auth берётся из
`OPENROUTER_API_KEY` процесса (тот же ключ, что в чате). Для локальной
генеративной модели выберите oMLX в UI или передайте CLI
`--semantic-auth-mode omlx --semantic-base-url http://127.0.0.1:8005/v1`
и `--semantic-model <generative-model>`: используется `RAG_EMBEDDING_API_KEY`.
Модель разбиения выбирается отдельно от модели эмбеддингов; URL можно изменить.
OpenRouter использует общий каталог чата с ценами, oMLX — ID своего сервера.
«Обновить модели» перечитывает каталог; отсутствующий ID остаётся доступным.
`RAG_CHUNKING_API_KEY` больше не выбирает авторизацию. LLM возвращает
границы абзацев, а приложение сохраняет точные исходные срезы. Проверенный
кэш исключает повторные вызовы на том же корпусе/конфиге; в разделе
«Фактическое состояние операции» доступны
фактические вызовы, модель, токены и стоимость провайдера; trace остаётся
приватным. Компактные строки документов/чанков отмечают выбранный ID синим;
смена документа сразу очищает старый чанк и вектор. Документ и чанки можно
проверить до публикации; создание эмбеддингов не заменяет индекс. Авторизация
oMLX берётся
из окружения процесса приложения `RAG_EMBEDDING_API_KEY`. Открытые details,
выбор, черновик и фокус сохраняются при опросе. Удаление эмбеддингов сохраняет
документы/чанки, удаление чанков сохраняет документы; оба удаляют downstream
индекс и кэш. UI не сравнивает стратегии.

## Что осталось честно назвать

* **Локальный корпус и объём**: репозиторий не содержит подготовленного снимка
  ≥15000 очищенных слов; объём нужно проверить в ingest-report и инспекторе
  после собственного запуска. Ориентир задания: ≥15000 слов ≈30 страниц
  по 500 слов. Эвристики legacy HTML требуют просмотра очищенного текста;
  счётчик сам по себе не подтверждает качество.
* **Только явные HTML-входы**: загрузчик не обходит сайт, не читает PDF
  и не делает OCR.
* **Сравнение разбиения**: CLI сравнивает fixed и structural на одном frozen
  корпусе; UI сравнения нет. Отчёт описывает чанки, не качество ответов.
* **Оценка качества**: набор из 10 вопросов, ожидания и сравнение ответов нужно
  подготовить и провести локально. Автоматической оценки, отдельной reranker-модели
  и проверки цитат пока нет; найденный источник не гарантирует верный ответ.
* **Offline-проверки — проверка контрактов**: живой инференс и качество поиска
  на архиве здесь не измеряются. Модель и сервер запускает оператор;
  приложение не скачивает веса.
