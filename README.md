# День 19 — пайплайн из трёх инструментов

```
🔥 День 19. Пайплайн из инструментов
Несколько MCP-инструментов (search, summarize, saveToFile): первый получает
данные, второй обрабатывает, третий сохраняет. Автоматическое выполнение
цепочки, корректность передачи данных.
```

## Вывод

Сервер `pipeline` (`app/mcp_servers/pipeline.py`) несёт три инструмента:

| инструмент | что делает |
|---|---|
| `search(query, limit=20)` | подстрока по репозиторию: `git grep -n -i -F --untracked`. Выдача отсортирована по (файл, строка) и только потом обрезана до `limit` — git свой порядок не обещает. Пустая выдача — честное «ничего не найдено», а не выдумка |
| `summarize(text, max_items=10)` | **механический** конденсат выдачи search: дедуп строк, группировка по файлам, обрезка до `max_items` групп — и обрезка названа числом. Без LLM принципиально: ключа у процесса нет |
| `save_file(name, content)` | пишет в `files/` — единственное файловое место записи. Имя санитизируется: непустое, без «/», «\\» и «..»; отказ — текстом, и файла не появляется |

Цепочку ведёт **модель**: цикл вызовов дня 17 сам доводит её до конца без
участия человека — search, видит результат, зовёт summarize с ним в
аргументе, затем save_file с выводом summarize. «Автоматическое выполнение»
— это «без человека», а не «мимо модели»: кода, передающего результат
одного инструмента в другой, нет. Передача данных — через tool-сообщения
рабочего списка, и на видео это три бейджа подряд под ответом
(`search · pipeline · N мс` и т.д., день 17), а файл появляется в `files/`.

## Клиент

Во вкладке «Инструменты» у сервера с полем `reminders` — блок под его
инструментами: счётчики по состояниям и каждая запись с текстом и
временем. Пока вкладка открыта, следующий запрос идёт через 2 секунды после
завершения предыдущего:
переворот «ждёт → сработало» виден живьём, без единого действия.
Уход из настроек/раздела, скрытый документ и pagehide останавливают
опрос и отменяют GET; поздний ответ отвергается. Повторный вход сразу
обновляет агрегат, раскрытые схемы сохраняются.

«Чат» и «Настройки» используют центральную рабочую область. Светлый интерфейс
рассчитан на компьютер и ноутбук: шесть страниц с вертикальной навигацией,
гибкие формы и сворачиваемый список чатов. Переключение сохраняет выбранный чат, черновик сообщения,
прокрутку, активный ответ и шапку задачи. Все шесть метрик доступны снизу;
в компактном окне строка прокручивается горизонтально. Длинный текст
переносится, код и JSON прокручиваются; при zoom можно свернуть список чатов.

Аватар справа в шапке открывает настоящий глобальный профиль: стиль, формат
и контекст ответа. Меню показывает записанные значения и ведёт в тот же
редактор «Профиль». Поля сохраняются при уходе фокуса; ошибка оставляет текст
для повторной попытки. Профиль, долговременная память и инварианты действуют
во всех чатах, модель, промпт и рабочая память — в выбранном чате.

Стрелки, Home и End переключают вкладки. Escape закрывает меню профиля
или подтверждение; фокус возвращается к открывшей
кнопке. В редакторе записи Enter сохраняет, Shift+Enter добавляет строку,
Escape отменяет. В обоих слоях памяти остаются ручное добавление, правка
и удаление с явным выбором типа записи. Поиск названий, копирование ответа
кнопкой и перенос рабочей записи кнопкой убраны; текст можно выделить
и перенести в форму долговременной памяти вручную.

Клиент загружает обычные локальные скрипты `text.js` → `records.js` → `app.js`,
без сборки и новых зависимостей. Карта файлов и чтения по задаче — в
[руководстве клиента](docs/client-guide.md).

## Проверки

Живых вызовов к LLM нет; механика сервера — in-process (функции модуля
обычные, REMIND_DB_PATH во временный каталог), связь — настоящими
процессами через тот же McpManager. Subprocess-фикстура задаёт временный
путь серверной SQLite до запуска настоящего stdio; data/reminders.db
и окружение production-процессов проверки не меняют. Клиент исполняется
под Node обоими путями (aggregate и классические HTML-скрипты) с явными
API/SSE-ответами; геометрия — по [списку](docs/client-guide.md#ручной-прогон).

```bash
make check          # весь офлайн-набор: Python, subprocess и клиент под Node.js
make check-browser  # только клиентский набор
```

Проверки пайплайна: search детерминирован (повтор совпадает, top-N, перемешанный
вход отсортирован); пустая выдача — честный отказ; summarize на
фиксированном входе даёт эталонный выход побайтово (дедуп, группы, лимит);
save_file пишет в каталог из `PIPELINE_FILES_DIR` побайтово; недопустимые
имена — отказы, каталог пуст. Настоящий процесс через McpManager отдаёт
три инструмента, и search находит известные строки во временном Git-репозитории.
Subprocess-фикстура задаёт ROOT и PIPELINE_FILES_DIR внутри дочернего сервера:
поиск не читает рабочий checkout, запись не касается его files/.
Сквозная цепочка из трёх вызовов — аргумент summarize содержит результат
search, аргумент save_file — вывод summarize (читается из
`CALLS[n].payload["messages"]`, там же, где увидела бы модель).

Заодно починен регистратор заглушки: `build_payload` ссылается на живой
рабочий список, и цикл вызовов дописывал tool-сообщения в тело уже
записанного, давнего вызова — теперь записывается снимок (deepcopy).

## Как запустить

Из корня репозитория, с Python >= 3.11, Node.js, git и make:

```bash
make help
make setup
make run             # http://127.0.0.1:8000
```

`setup` создаёт `.venv` либо повторно использует существующее окружение,
проверяет Python >= 3.11 и устанавливает `requirements.txt`; `.env` не трогает.
По умолчанию для создания выбран `python3.11`; другой путь задаётся так:

```bash
make setup PYTHON=/path/to/python
```

`PYTHON` используется только при создании окружения. Остальные цели всегда
используют `.venv/bin/python`. Существующее окружение не пересоздаётся;
несовместимое нужно исправить явно. `run` выполняет
`.venv/bin/python -m uvicorn app.main:app --reload --port 8000`.
`check` требует Node.js и единожды запускает `checks/run_checks.py`, который
сам включает subprocess и браузерные проверки; ошибка любой цели даёт
ненулевой код завершения.

Для ручного общения с моделью человек создаёт `.env`, только если файла ещё
нет, и вписывает `OPENROUTER_API_KEY` локально (файл в `.gitignore`):

```bash
if [ ! -e .env ] && [ ! -L .env ]; then cp .env.example .env; fi
```

Проверкам ключ не нужен: они используют заглушку без живых вызовов LLM.
Smoke запускайте с временным `AGENT_DB_PATH` и `MCP_DISABLED=1`.
Не читайте и не выводите секреты; для коммита перечисляйте файлы явно,
не используйте `git add -A` или `git add .`.

В `mcp.json` четыре сервера: `echo` (стенд связи), `git`, `remind` и
`pipeline`. Спросите «найди упоминания require_parameters, сожми выдачу и
сохрани в файл» — под ответом будут три бейджа подряд, а файл ляжет в
`files/` (каталог в `.gitignore`: репозиторий публичный, не коммитьте
`git add -A`).

## Работа через OpenCode и Pi

Запускайте установленный инструмент **из корня этого checkout/worktree**:

```bash
opencode
# или
pi
```

Оба инструмента автоматически включают корневой `AGENTS.md` в контекст
([правила OpenCode](https://opencode.ai/docs/rules/),
[контекст Pi](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/README.md)).
Ссылка на `docs/architecture.md` не загружает файл сама: агент обязан прочитать
нужные разделы перед изменениями, как требует `AGENTS.md`.

Модель и авторизация — личные настройки каждого инструмента; задавайте их
в его интерфейсе/пользовательском конфиге, не в отслеживаемых файлах проекта
и не в `.env` приложения. Ключ OpenRouter приложения не настраивает
OpenCode/Pi. Корневой `mcp.json` управляет серверами **приложения**, а не
MCP coding-агентов; переносить его в настройки инструментов не нужно.
Общие команды проекта одинаковы: `make setup`, `make run`, `make check`.

## Что осталось честно назвать

* **summarize не понимает текст**: группировка держится на форме строки
  «файл:номер: текст»; строка другой формы уезжает в группу «(без файла)»
  как есть.
* **Цепочка из трёх звеньев — четыре обращения к модели**: каждое оплачено,
  и их сумму показывает панель (usage складывается по итерациям, день 17).
* **Сортировка search — страховка**: на практике git отдаёт выдачу уже
  упорядоченной, но порядок не обещан, и проверка бьёт по перемешанному
  входу.
* **Сработавшее молчит до вопроса**: уведомления в чат нет — история
  попарная. Человек узнаёт о срабатывании из вкладки или спросив модель
  («какие напоминания сработали?» — та позовёт `reminders`).
* **Точность — до перезапроса**: следующее чтение идёт через 2 секунды после
  предыдущего ответа. Сервер считает состояние при чтении; задержка запроса
  добавляется к интервалу, параллельных запросов нет.
* **Часы — серверные**: `due_at` считается по часам процесса сервера;
  вкладка лишь показывает его ответ, сама по своим часам ничего не
  досчитывает.
* _Живой прогон на ключе:_ **место под числа оставлено пустым — впишет человек.**
