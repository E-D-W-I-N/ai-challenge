# День 25 — мини-чат с RAG и памятью

```
🔥 День 25. Мини-чат с RAG + памятью (production-like)

Реализуйте мини-чат (CLI/веб), который:

👉 хранит историю диалога
👉 при каждом новом вопросе ищет контекст в базе через RAG
👉 отвечает с учётом найденной информации
👉 всегда выводит источники

Усиление:

👉 добавьте “память задачи” (task state):

- что пользователь уже уточнил
- какие ограничения/термины зафиксированы
- что является целью диалога

Проверьте:

👉 на 2 длинных сценариях по 10–15 сообщений
👉 что ассистент не теряет цель и продолжает выдавать ответы с источниками

Результат:

Мини-чат с RAG + источниками + памятью задачи
```

## Вывод

Существующая рабочая память чата теперь передаётся в Rewrite отдельным массивом
`working_memory` с полями `kind` и `content`. Записи по-прежнему добавляет,
редактирует и удаляет человек; автоматического ведения памяти и нового слоя нет.
Текущий вопрос приоритетен: память помогает разрешить ссылки, цель и ограничения,
но не считается инструкциями или подтверждёнными фактами источников. Стиль и формат
ответа не должны попадать в поисковый запрос. Глобальная память, профиль, инварианты
и машина этапов задачи в Rewrite не передаются.

Глубокий снимок рабочей памяти фиксируется до первого ожидания обмена и используется
также основной генерацией и номерами врезок. Правки во время Rewrite действуют
со следующего вопроса. Actual JSON служебного вызова виден в существующем инспекторе,
сохраняется с ответом и копируется в ветку. Дополнительных вызовов нет; при RAG OFF
или Rewrite OFF переформулировка не запускается. История, источники и защитные
проверки RAG сохраняются. Проверены offline-контракты на нейтральных данных;
живые два сценария по 10–15 сообщений не выполнялись, качество памяти и модели
в таком диалоге здесь не подтверждается.

При RAG ON содержательный ответ содержит карточки источников
с `source`, `section`, `chunk_id` и цитатой модели. Ссылки `[1]`, `[2]` в тексте
предпочтительны, но не обязательны: ответ без них показывается без изменения. Номер соответствует позиции
полного фрагмента в сохранённом снимке поиска. Сервер проверяет структуру ответа,
соответствие ID выбранным источникам и, если ссылки в тексте есть, точное совпадение
их набора со списком цитат; метаданные
берёт из этого же снимка. Ответ публикуется после проверки. Несовпадающие ссылки или
некорректные/отсутствующие цитаты дают явную ошибку без платного повторного вызова:
ввод возвращается, перегенерация восстанавливает прежний ответ. Причина ошибки
различает незавершённый ответ, некорректный JSON/повторяющиеся ключи, поля и типы,
ID источников, пустую цитату, метаданные и несовпадение ссылок. Сообщение не включает
сырой ответ модели или значения полей. Отсутствие ссылок в тексте допускается
при корректном непустом списке цитат; ссылки автоматически не вставляются. Отмена не сохраняет
непроверенный черновик. Рассуждения, вызовы инструментов и метрики остаются видимыми.

Порог слабого контекста действует всегда при RAG ON.
Если выбранных источников нет или их максимальный cosine меньше порога, финальная модель не
запускается: «Не знаю: в базе не найдена достаточно релевантная информация.
Уточните вопрос.» Порог не исключает отдельных кандидатов до реранкинга.
После его прохождения модель отвечает на подтверждённые части составного вопроса
и явно указывает, для каких частей в источниках нет данных. Пробел в одной части
не превращается в отказ по всему вопросу. Отдельный модельный JSON-отказ не принимается. Подтверждение планирования
напоминания также не требует цитат; содержательный результат напоминания требует.

Cosine — единственная автоматическая проверка релевантности содержания.
Дословное совпадение цитаты и смысловая поддержка ответа автоматически не проверяются.
Новые ответы подписаны «Источники и цитаты»; старые снимки сохраняют прежние статусы.
Проверку на 10 вопросах своего корпуса оператор проводит локально: для каждого
содержательного ответа отмечает наличие источников, цитат и поддержку всех
утверждений приведёнными фрагментами; отдельно фиксирует корректность отказов.
Вопросы и результаты остаются приватными. Здесь проверены offline-контракты,
а не качество живой модели на пользовательском корпусе.

RAG включается отдельно для каждого чата через шестерёнку в его строке →
«Настройки чата → Поиск RAG» и по умолчанию выключен. Rewrite и реранкинг
включаются независимо; rewrite по умолчанию включён в новых чатах, реранкинг
выключен. В старых чатах отсутствующие переключатели остаются выключенными.

Два количества задаются отдельно: «Кандидатов для поиска» — по умолчанию 10,
«Чанков для ответа» — 3. Оба целые от 1 до 100, итоговое количество не больше
кандидатного. Поиск находит до 10 кандидатов; включённый реранкинг переставляет
весь найденный набор, затем первые 3 передаются модели ответа. Без реранкинга
берутся первые 3 по cosine. Предварительного cosine-фильтра нет:
кандидат с низким cosine может попасть в итоговый контекст после реранкинга.
Модель ответа получает выбранные чанки, но не обязана использовать каждый из них.

Во всех селекторах моделей есть независимый переключатель «Рассуждения (если
модель поддерживает)», по умолчанию OFF, включая старые настройки. В чате выбор
применяется также к сжатию и Rewrite; подготовка, чанкинг, реранкинг и эмбеддинги
не наследуют его. OpenRouter получает явный reasoning OFF/ON, совместимый сервер —
reasoning_effort none/medium. Дополнительные параметры не обходят OFF; неподдерживаемый
режим даёт ошибку без автоматического повтора. Совместимый сервер может игнорировать
параметр: обнаруженные reasoning-текст или положительные reasoning_tokens при OFF
дают явную ошибку с фактическими метриками. Отсутствие этих данных не доказывает,
что сервер не рассуждал внутренне. Стандартный /embeddings не имеет reasoning-параметра:
его переключатель сохраняет локальный выбор, не меняя запрос, identity или кэш индекса.
Сохранённые явные количества RAG не заменяются новыми значениями 10/3.

Query rewrite делает один дополнительный вызов текущей модели чата с отдельным
служебным промптом: текущий вопрос, последние три полные успешные пары истории
и снимок kind/content существующей рабочей памяти чата.
Результат используется только для поиска; итоговая генерация получает исходный
вопрос. Лимит ожидания — 60 секунд, автоматических повторов нет. Пустой/невалидный
JSON, незавершённый ответ или отказ модели дают явную ошибку и возвращают ввод.
Настройки чата, MCP-инструменты и инструкции не передаются служебному вызову.

Поиск берёт полные кандидаты и identity индекса из одного закреплённого SQLite
чтения. Реранкинг требует полную JSON-перестановку ID, имеет timeout 60 секунд
и не делает автоматических повторов или fallback. Промпт требует только JSON
без пояснений и полную перестановку фактически найденных ID. Разбор допускает
пояснение перед единственным JSON-объектом, но не текст после него; порядок
не исправляется и недостающие ID не добавляются. Ошибка различает JSON, структуру,
типы, повторы, чужие и пропущенные ID без вывода ответа модели. Он не заменяет cosine
оценками модели. Пустой поиск даёт «В базе не найдена подходящая информация»
без финальной генерации. При RAG OFF поиск, rewrite и реранкинг не выполняются.

Инспектор сохранённого ответа показывает всех кандидатов в итоговом порядке:
«Источник», «До → после», «Cosine». «До → после» и сведения модели ранжирования
видны только при фактически завершённом реранкинге. Метка «В контексте» у
источника отмечает первые N чанков, отправленные модели; полный текст каждого
кандидата доступен под таблицей. Исходный запрос, история и usage rewrite видны
только при его включении в сохранённом снимке. Старые отчёты с cosine-фильтром
и прежними лимитами читаются без переписывания и сохраняют свою диагностику.
Текущие настройки не меняют исторические источники, порядок и контекст.

Фактический JSON содержит все отправленные запросы, включая rewrite и реранкинг.
Usage каждого вызова учитывается один раз; неизвестная стоимость остаётся
неизвестной. Интерактивная ошибка возвращает ввод и временную диагностику без
записи обмена; перегенерация восстанавливает прежний ответ. Ошибка напоминания
сохраняет доступные метрики вместе с сообщением об ошибке.

Порог защиты от слабого контекста действует при каждом RAG-ответе: максимум cosine
выбранных чанков должен достигать порога (по умолчанию 0.3, от -1 до 1 включительно).
Если все кандидаты слабые, отказ возможен до платного реранкинга; иначе проверка
следует за итоговым отбором. Сохранённая политика доступна в инспекторе.

`rag` остаётся самостоятельным пакетом внутри проекта. Используется существующий
HTML-корпус и опубликованный индекс; эмбеддинги предоставляет выбранный HTTP-провайдер.
Новых сервисов, ключей и переменных окружения не требуется. Корпус, приватные кэши,
вопросы и отчёты остаются локальными данными оператора.

## Сравнение ответов

На одном опубликованном индексе задайте одинаковый вопрос в двух новых чатах
с одинаковой моделью и прочими настройками. В обоих включите RAG; в первом
отключите rewrite и реранкинг, во втором включите оба. Сравните полноту и фактическую
точность ответа, найденные источники, исключённые кандидаты, токены и стоимость.
Используйте сохранённые снимки, чтобы видеть точные условия каждого ответа.
Оба количества, rewrite и реранкинг можно менять отдельно; отдельного compare UI нет.

Живое сравнение на пользовательском корпусе здесь не проведено. Offline-проверки
подтверждают контракты приложения, а не улучшение качества конкретной модели.

## Общие команды

Из корня репозитория, с Python >=3.11, `make` и Node.js в PATH:

```bash
make help
make setup
# Если python3.11 не в PATH или нужен другой интерпретатор >=3.11:
make setup PYTHON=/path/to/python
make run             # http://127.0.0.1:8000, автоматическая перезагрузка
make check           # весь offline-набор, включая subprocess и клиент
make check-browser   # только клиентские проверки под Node.js
```

`PYTHON` выбирает интерпретатор только для создания `.venv`. Setup проверяет
версию, создаёт окружение при отсутствии или использует существующее и
устанавливает `requirements.txt`; повторный запуск сохраняет окружение.
Он не создаёт и не перезаписывает `.env`. Все последующие Python-команды
выполняются через `.venv/bin/python`; ошибки команд дают ненулевой exit code.

Приложение читает из окружения и `.env` только `OPENROUTER_API_KEY` и
`RAG_EMBEDDING_API_KEY`. Модель генерации по умолчанию в чате, CLI и RAG —
`openai/gpt-6-luna`; сохраняемые настройки чатов продолжают определять их модель.
База чатов — `data/agents.db`, корпус/индекс — `data/rag`, начальный MCP конфиг —
`mcp.json`. Другие прикладные env настройки не поддерживаются; адреса, модели
и параметры задаются в существующих формах или явных CLI аргументах сервисов.
Стандартные PATH/HOME/LANG и HTTP proxy окружение сохраняют своё назначение.

Для ручного диалога создайте `.env` из `.env.example`, только если его ещё
нет, и задайте `OPENROUTER_API_KEY` локально. Ключ не нужен offline-проверкам.
Секреты не выводите и не коммитьте; используйте только точечный `git add`,
никогда `git add -A` или `git add .`.

## Проверки

Проверки используют временный нейтральный CP1251 HTML, настоящий HTTP embedding
stub, отдельный CLI и SQLite, без живого инференса. Проверяются chunk slices,
cache fingerprint, cosine, валидация векторов, atomic failure, writer lock,
interrupted/stale, bounded API и настоящий клиент под Node с lazy vector/late GET.
День 22 проверяется на нейтральных временных снимках и HTTP-заглушках: ON/OFF,
согласованность контекста и сохранённого снимка, ошибки поиска до генерации,
история после изменения индекса и переключение настройки текущего чата.
День 23: полный реранкинг кандидатов и отбор первых N, три пары rewrite, strict stop и JSON, отмена/timeout,
пустой отбор без генерации, реальные JSON/usage, legacy/restart/ветвление и напоминания.
День 24: ссылки и ID источников из закреплённого снимка, частичный ответ и отсутствие дословной проверки цитат,
строгий формат и stop, буферизация ответа, явная ошибка без retry, порог выбранного контекста,
ошибка неподдерживаемого формата модельного отказа, paid diagnostics и восстановление/ветвление/отмена.
Сохраняется весь offline-набор предыдущих дней: чат, память, задачи, MCP и pipeline.

Подробности: [архитектура](docs/architecture.md), [карта клиента и ручной просмотр](docs/client-guide.md).

## Как запустить

### Где находятся настройки

Кнопка с гаечным ключом справа в шапке открывает «Настройки приложения»: общий адрес совместимого сервера
моделей, профиль ответа, долговременную память, инварианты, подключения MCP и
пайплайн RAG (документы, разбиение, эмбеддинги, публикация и просмотр индекса).
Эти разделы доступны без выбранного чата и действуют для всех чатов.

Шестерёнка рядом с карандашом в строке чата открывает «Настройки чата»:
провайдер и модель генерации со всеми параметрами ответа, системный промпт и
управление контекстом агента, краткосрочную и рабочую память, использование
RAG с rewrite, реранкингом и отбором контекста. Раздел «Напоминания» появляется только
при подключённом MCP-сервере с подтверждённой поддержкой напоминаний, даже
если список пуст. Он показывает состояния и отмену принадлежащих чату задач.
Общий каталог инструментов остаётся только в настройках приложения. Управление подключениями MCP находится в настройках
приложения, где нет кнопок отмены напоминаний конкретного чата.

Общей смешанной верхней вкладки «Настройки» нет. «Вернуться в чат» закрывает
настройки без прерывания ответа и сохраняет ввод. Исторический инспектор RAG
открывается у ответа отдельно, доступен только для чтения и показывает его
сохранённый снимок, независимо от текущих настроек.

После удаления последнего чата создаётся один новый. Пустой список при запуске
или открытие общих настроек сами чат не создают. При ошибке создания удалённая
переписка исчезает с экрана; кнопка «Новый чат» позволяет повторить попытку.

### Чат с RAG

Сначала опубликуйте индекс через этапы ниже. Нажмите шестерёнку рядом с
карандашом в строке чата → «Поиск RAG» и включите
«Использовать RAG в этом чате». Нажмите «Вернуться в чат» и задайте вопрос.
Просмотрите источники под ответом и сохранённый контекст. Кнопка «К текущему
индексу» возвращает к существующим этапам индексации, не меняя историю ответа.
Отключение checkbox возвращает обычную генерацию для следующих вопросов.
Для сравнения режимов включите RAG и настройте rewrite, реранкинг и оба количества рядом.

### Индексация из терминала

Подготовьте **локальный** JSON manifest, например `data/rag/inputs.json`:

```json
[
  {"path": "article.html"}
]
```

Относительный path разрешается относительно manifest. Для HTTP-входов
добавьте объект с полем `url`; для локальной копии можно задать `source`.
Можно повторять `--url` вместо manifest. CLI не импортирует конфигурацию чата
и не читает `.env`.
Приложение использует фиксированный каталог `data/rag`; CLI использует его по умолчанию,
а `--root` позволяет оператору работать с отдельным каталогом:

Примеры ниже используют OpenAI-совместимый сервер на порту 8005;
укажите фактический адрес и ID модели своего сервера.

```sh
.venv/bin/python -m rag ingest --manifest data/rag/inputs.json
.venv/bin/python -m rag --compatible-base-url http://127.0.0.1:8005/v1 index --provider compatible \
  --model YOUR_EMBEDDING_MODEL --batch-size 16
.venv/bin/python -m rag status
make run
```

Для уже запущенного совместимого сервера с авторизацией на порту 8005 в zsh введите ключ
скрыто и укажите точный embedding model ID из списка моделей этого сервера:

```zsh
read -rs 'RAG_EMBEDDING_API_KEY?Ключ совместимого сервера: '; print
export RAG_EMBEDDING_API_KEY
read -r 'RAG_EMBEDDING_MODEL?Embedding model ID сервера: '
.venv/bin/python -m rag --compatible-base-url http://127.0.0.1:8005/v1 index --provider compatible \
  --model "$RAG_EMBEDDING_MODEL" --batch-size 16
unset RAG_EMBEDDING_API_KEY
```

Ключ вводится в prompt, без аргумента CLI и записи в историю команд;
авторизация сервера остаётся включённой. CLI по-прежнему не читает `.env`.

Ingest сохраняет frozen corpus.json и ingest-report.json с ошибками/словами и
оценкой страниц; при любом отказе прежний корпус остаётся. Повторный index
использует кэш. Сборка пишет временную SQLite и атомарно заменяет index.sqlite
только после успеха; прежний индекс доступен при ошибке/остановке. Один OS lock
исключает конкурирующих писателей. Atomic replace — граница успеха; отказ записи
завершающего progress после replace оставляет новый индекс готовым и даёт
диагностическое предупреждение, без обещания отката опубликованной SQLite.
Изменённый корпус отмечает индекс как stale.

Сравнение выполняется отдельно в терминале на том же frozen corpus и конфиге:

```sh
.venv/bin/python -m rag --compatible-base-url http://127.0.0.1:8005/v1 compare --provider compatible \
  --model YOUR_EMBEDDING_MODEL
```

Оба индекса сохраняются в `comparisons/fixed` и `comparisons/structural`,
локальный comparison.json содержит число чанков, длины, перекрытие, разделы,
модель и fingerprint. Активный индекс не заменяется. Это сравнение разбиения;
качество ответа/поиска на контрольных вопросах здесь не измеряется.

### Отдельные этапы CLI

Отдельные CLI этапы (прежний `index` также поддерживается):

```sh
.venv/bin/python -m rag chunks --strategy fixed --size 1200 --overlap 180
.venv/bin/python -m rag chunks --strategy semantic --size 1200 --overlap 180 \
  --semantic-provider openrouter --semantic-model openai/gpt-6-luna
.venv/bin/python -m rag --compatible-base-url http://127.0.0.1:8005/v1 embed --provider compatible --model YOUR_MODEL
.venv/bin/python -m rag save
.venv/bin/python -m rag clear index  # сохраняет все предыдущие этапы и кэши
.venv/bin/python -m rag clear embeddings
.venv/bin/python -m rag clear chunks
```

### Просмотр и запуск этапов в UI

Откройте `http://127.0.0.1:8000` → кнопка «Настройки приложения» → «Настройки приложения → Индекс RAG». Страница работает
без чата/ключа, читает фактические стадии CLI `documents → chunks → embeddings → save`,
счётчики кэша/новых векторов, длительность, модель и размерность. После сохранения
видны объём корпуса, версия/байты/число строк SQLite, документы и чанки с
границами/текстом/метаданными. Раскрытие отдельно читает настоящий числовой
вектор выбранного чанка. Refresh открывает сохранённый индекс; missing/stale/
interrupted/error названы явно, предыдущий индекс при отказе виден отдельно.
UI запускает отдельные этапы «Загрузить документы» → «Разбить на чанки» →
«Создать эмбеддинги» → «Сохранить индекс». Укажите явные URL; локальный HTML
доступен только из фиксированного manifest `data/rag/inputs.json`, без ввода путей в HTTP.
На этапе «Документы» выберите подготовку «Кодом» (по умолчанию) или
«Полностью через LLM»: генеративная модель получает HTML, очищает его и
восстанавливает структуру без пересказа. Чат, подготовка, семантическое разбиение,
эмбеддинги и реранкинг используют общий выбор «Провайдер → Модель»:
OpenRouter или OpenAI-совместимый сервер. Совместимый URL задаётся один раз
в «Настройках приложения → Модели» и действует для приложения; ключ остаётся только на сервере.
Каждый этап сохраняет собственные провайдер и точный ID модели.
Модель подготовки, токены и
фактическая стоимость доступны в «Фактическое состояние операции».
Для медленной локальной модели увеличьте «Ожидание ответа, с»: по умолчанию
600 секунд, допустимо 1–3600; настройка относится только к подготовке документов.
Размер и перекрытие задаются в символах. Для LLM поле называется
«Максимальный размер чанка»: модель выбирает смысловые границы, код ограничивает
размер групп и добавляет заданное перекрытие. В UI доступны «По размеру» и
«Семантическое · LLM». Для semantic по умолчанию OpenRouter /
`openai/gpt-6-luna`. OpenRouter всегда использует свой канонический адрес и
`OPENROUTER_API_KEY`. Для совместимого сервера используется общий URL и
необязательный `RAG_EMBEDDING_API_KEY` для всех типов моделей. В CLI общий URL
задаётся перед командой через `--compatible-base-url`, а этап выбирает
`--semantic-provider compatible --semantic-model <generative-model>`.
Модель разбиения выбирается отдельно от модели эмбеддингов.
«Обновить модели» перечитывает общий каталог; введённые и сохранённые точные ID
сохраняются даже при отсутствии в каталоге. Неизвестные цены и параметры не
выдаются за нулевые. Query rewrite использует провайдер и модель текущего чата.
LLM возвращает
границы абзацев, а приложение сохраняет точные исходные срезы. Проверенный
кэш исключает повторные вызовы на том же корпусе/конфиге; в разделе
«Фактическое состояние операции» доступны
фактические вызовы, модель, токены и стоимость провайдера; trace остаётся
приватным. Компактные строки документов/чанков отмечают выбранный ID синим;
смена документа сразу очищает старый чанк и вектор. Документ и чанки можно
проверить до публикации; создание эмбеддингов не заменяет индекс. Ключи берутся только из окружения процесса приложения. Открытые details,
выбор, черновик и фокус сохраняются при опросе. Удаление эмбеддингов сохраняет
документы/чанки, удаление чанков сохраняет документы; оба удаляют downstream
индекс и кэш. UI не сравнивает стратегии. Смена общего адреса при той же embedding-модели
не требует перестройки: поисковый вектор использует текущий адрес, но модель,
размерность и revision опубликованного индекса. Его fingerprint не переписывается.
Другая модель или несовместимая размерность требуют явной перестройки индекса.

## Что осталось честно назвать

* **Локальный корпус и объём**: репозиторий не содержит подготовленного снимка
  ≥15000 очищенных слов; объём нужно проверить в ingest-report и инспекторе
  после собственного запуска. Ориентир задания: ≥15000 слов ≈30 страниц
  по 500 слов. Эвристики legacy HTML требуют просмотра очищенного текста;
  счётчик сам по себе не подтверждает качество.
* **Только явные HTML-входы**: загрузчик не обходит сайт, не читает PDF
  и не делает OCR.
* **Сравнение разбиения**: CLI сравнивает fixed и structural на одном frozen
  корпусе; UI сравнения нет. Отчёт описывает чанки, не качество ответов.
* **Оценка качества**: набор из 10 вопросов, ожидания и сравнение ответов нужно
  подготовить и провести локально. Автоматически проверяются формат и ID источников;
  дословность цитат и смысловая поддержка ответа остаются ручной оценкой.
  Найденный источник не гарантирует верный ответ.
* **Offline-проверки — проверка контрактов**: живой инференс и качество поиска
  на архиве здесь не измеряются. Модель и сервер запускает оператор;
  приложение не скачивает веса.
