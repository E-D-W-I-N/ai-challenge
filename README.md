## Чистое развёртывание дня 30

Используйте новый Ubuntu 24.04 с cgroup v2. Создайте DNS A/AAAA домена вместо
`ai.example.com`; разрешите входящие SSH, TCP 80 и 443 в firewall провайдера.
Порты 8000 и 11434 наружу не открывайте. Клонируйте публичный репозиторий;
не переносите с Mac `.env`, `data`, ключи, корпус, результаты или рабочий каталог.
Новая база сохраняется на сервере между перезапусками.

```bash
sudo apt update
sudo apt install -y git make python3-venv curl gpg debian-keyring debian-archive-keyring apt-transport-https
sudo useradd --system --create-home --home-dir /var/lib/aichat --shell /usr/sbin/nologin aichat
sudo git clone --branch day-30 https://github.com/E-D-W-I-N/ai-challenge.git /opt/aichat
sudo chown -R aichat:aichat /opt/aichat
cd /opt/aichat
sudo -u aichat make setup PYTHON=python3
sudo -u aichat .venv/bin/python -m app.auth bootstrap-admin
```

Bootstrap запрашивает новый пароль скрытым вводом; не помещайте его в команды,
историю shell или Git. Администратор создаёт остальные аккаунты в интерфейсе,
сбрасывает их пароли и отключает доступ. Существующую локальную базу приложение
не мигрирует и не удаляет. Личные чаты, память, профиль, инварианты и настройки
изолированы по аккаунтам; URL/ключ модели и корпус RAG общие. Подключения MCP,
напоминания и подготовка общего корпуса доступны администратору.

Установите [Ollama по официальной инструкции Linux](https://docs.ollama.com/linux).
Нужна версия не ниже 0.11.10 для [EmbeddingGemma](https://ollama.com/library/embeddinggemma).
Остановите штатный сервис: ниже его заменяет наш launcher с вычисленной ёмкостью.

```bash
curl -fsSL https://ollama.com/install.sh -o /tmp/install-ollama.sh
less /tmp/install-ollama.sh
sudo sh /tmp/install-ollama.sh
sudo systemctl disable --now ollama
sudo install -d -o aichat -g aichat -m 700 /var/lib/aichat/models
sudo -u aichat env OLLAMA_HOST=127.0.0.1:11434 OLLAMA_MODELS=/var/lib/aichat/models OLLAMA_NO_CLOUD=1 ollama serve
```

Последняя команда занимает первый терминал. Во втором терминале загрузите
только публичные веса и создайте явный локальный профиль:

```bash
cd /opt/aichat
OLLAMA_HOST=127.0.0.1:11434 ollama pull qwen3:1.7b
OLLAMA_HOST=127.0.0.1:11434 ollama pull embeddinggemma:latest
OLLAMA_HOST=127.0.0.1:11434 ollama create private-qwen:latest -f deploy/Modelfile
```

`qwen3:1.7b` — [Q4_K_M, около 1.4 GB](https://ollama.com/library/qwen3:1.7b),
EmbeddingGemma — отдельная модель эмбеддингов с контекстом 2048.
В первом терминале остановите временный сервер через Ctrl+C, затем:

```bash
sudo cp deploy/aichat.slice deploy/aichat-ollama.service deploy/aichat.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now aichat-ollama.service
# Явный прогрев оператором, а не приложением:
curl -fsS http://127.0.0.1:11434/api/generate -H 'Content-Type: application/json' -d '{"model":"private-qwen:latest","keep_alive":-1}'
curl -fsS http://127.0.0.1:11434/api/embed -H 'Content-Type: application/json' -d '{"model":"embeddinggemma:latest","input":"warmup","keep_alive":-1}'
curl -fsS http://127.0.0.1:11434/api/ps
sudo systemctl enable --now aichat.service
```

Обе модели должны оставаться загруженными; приложение только читает
[метаданные `/api/ps`](https://docs.ollama.com/api/ps) и не прогревает их автоматически.
Launcher создаёт приватный `data/inference-capacity.json`, вычисляет
`OLLAMA_NUM_PARALLEL`, задаёт `OLLAMA_MAX_LOADED_MODELS=2`,
`OLLAMA_MAX_QUEUE=0` и `OLLAMA_KEEP_ALIVE=-1`. Внутреннюю очередь Ollama
заменяет очередь приложения. Параметры загрузки и параллельного контекста
описаны в [Ollama FAQ](https://docs.ollama.com/faq).

Установите [Caddy из официального репозитория](https://caddyserver.com/docs/install#debian-ubuntu-raspbian):

```bash
curl -1sLf https://dl.cloudsmith.io/public/caddy/stable/gpg.key | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo apt update
sudo apt install -y caddy
sudo cp /opt/aichat/deploy/Caddyfile /etc/caddy/Caddyfile
sudoedit /etc/caddy/Caddyfile
# Замените ai.example.com своим доменом, затем:
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl reload caddy
```

Откройте `https://ваш-домен`, войдите новым администратором. Совместимый URL
изначально `http://127.0.0.1:11434/v1`, ключ пустой. Выберите
`private-qwen:latest` для чата и генеративных этапов, `embeddinggemma:latest`
для эмбеддингов. Reasoning оставьте OFF. Текущая совместимость Ollama
[сопоставляет `reasoning_effort=none` с отключением thinking](https://github.com/ollama/ollama/blob/main/openai/openai.go);
это не подтверждённый здесь живой результат. Если сервер всё же сообщает
reasoning, приложение отклоняет ответ без повторного запроса.

Администратор может сохранить внешний URL и ключ обычным способом: удалять
deployment policy не нужно. Внешние подключения используют ту же очередь,
но без локальных требований к ID моделей, `/api/ps`, контексту 4096 и выходу 512.
Их лимиты и стоимость определяет провайдер. Общий embedding endpoint меняется
вместе с URL: для RAG он должен обслуживать опубликованную embedding identity,
иначе пересоберите индекс явно. Ключ сохраняется только в приватном серверном файле.

## Ёмкость, очередь и ручная проверка

Один worker Uvicorn и Ollama входят в общий systemd slice с MemoryMax=6G.
Boot ceiling вычисляется из доступной RAM, лимитов cgroup и CPU. Расчёт
резервирует 20% бюджета, минимум 1 GiB; веса учитываются с множителем 1.5,
дополнительно 512 MiB для приложения/runtime и 256 MiB для embedding runner.
Для параллельного генеративного контекста заложены 128 KiB на токен при 4096
и 64 MiB буферов на слот. Это допущения, а не точные измерения расхода.
Runtime повторно проверяет доступную память и резервирует 64 MiB на активный
обмен. Текущая ёмкость восстанавливается после временного давления памяти,
но не превышает boot ceiling; увеличивать его нужно перезапуском инференса.

Количество аккаунтов не ограничено числом слотов. Конечная FIFO-очередь
вмещает до восьми ожидающих операций на boot slot; на Mac без VPS policy
сохраняется ёмкость 16 активных обменов и очередь 128. Ожидание видно в чате.
Embedding runner обслуживает одну операцию: RAG ждёт освобождения этого
runner в общей FIFO, включая блокирование следующих операций по порядку.
Переполненная очередь даёт 503; выгруженные/несовпадающие локальные модели —
явную ошибку. Отмена, разрыв подключения и отзыв сессии удаляют ожидающего;
активный слот освобождается после фактического завершения работы. Ошибочные
LLM-запросы не повторяются автоматически.

Локальный профиль: контекст 4096, выход не более 512; служебные этапы используют
этот выходной лимит явно. На HTTP-границе оценивается весь JSON в UTF-8 плюс
256 байт запаса и выходной бюджет: включая историю, память, tools и RAG.
Это консервативная оценка, не tokenizer. Превышение отклоняется явно без
обрезки; `context_window` в OpenAI payload не добавляется. Для первого RAG
на этом профиле начните с коротких документов, fixed chunks 64 символа,
overlap 0, candidates 1 / final 1, Rewrite и rerank OFF, пустой истории и
краткого вопроса. Эмбеддинги стройте CLI с `--batch-size 1`; при запуске CLI
на VPS явно задавайте `INFERENCE_CAPACITY_FILE=/opt/aichat/data/inference-capacity.json`
и общий `--connection-file /opt/aichat/data/model-connection.json`.
Это малый стартовый профиль, не обещание качества; даже он может не вместить
длинный вопрос/промпт. Большие параметры Mac ниже к VPS автоматически не применяются.

Проверьте вручную собственные запросы через HTTPS из другого устройства:
ответ и поток, несколько одновременных чатов, позицию очереди и отмену ожидания.
Создайте второй аккаунт и проверьте отсутствие чужих чатов/памяти, сброс пароля
и отключение аккаунта; административные функции ему недоступны. Проверьте
явный отказ для слишком длинного локального контекста и max tokens >512.
Наблюдайте `systemctl status aichat aichat-ollama`, память общего slice и swap;
сравнивайте первую загрузку с повторной работой. Вопросы, пароли, тела запросов
и результаты не помещайте в журналы/репозиторий. Caddy не включает access log.
Эти проверки оператор ещё должен выполнить; автоматических live-проверок здесь нет.

## День 29: настройка и сравнение на MacBook

Сначала сохраните свои исходные параметры модели и чата, системный промпт,
ID/квантование модели и embedding identity индекса. Если поля Temperature или
Max tokens пусты, запрос их не отправляет: исходные значения уточните на сервере.
Сравнивайте свои одинаковые запросы при одинаковой истории и RAG-контексте;
для изоляции генерации используйте сохранённый final JSON через свой HTTP-клиент.
Меняйте только изучаемый параметр или системный текст, сохраняя историю и
найденные фрагменты. Изменяйте один фактор за раз.

| Параметр | Исходный вариант | Стартовый профиль для проверки |
|---|---|---|
| Temperature в настройках чата → Модель | Ваше текущее значение | `0.2` |
| Max tokens там же | Ваше текущее значение | `512` |
| Лимит контекста на сервере выбранной модели | Записанный текущий лимит | Сравнить `2048` и `4096` токенов |
| Системный промпт чата → Агент | Ваш текущий текст | Шаблон ниже |

Поля чата сохраняются при потере фокуса; фактические `temperature` и `max_tokens`
проверьте в «Информации о запросе». Лимит контекста задайте в настройках выбранной
модели в oMLX (`http://127.0.0.1:8005/admin`). Это серверный параметр
`max_context_window`, ограничивающий число токенов входного промпта, а не поле
OpenAI Chat Completions; см. [официальные настройки моделей oMLX](https://github.com/jundot/omlx/blob/main/omlx/model_settings.py).
Название элемента зависит от установленной версии. «Скользящее окно» в чате
считает сообщения и не заменяет серверный лимит токенов. Если полный RAG-промпт
не помещается в 2048, фиксируйте отказ в сравнении; приложение не обрезает
найденные фрагменты скрыто. Лимит 512 может обрезать JSON ответа: такой результат
также учитывайте как неудачу, а не как ускорение успешной генерации.

Для своего кейса добавьте в «Настройки чата → Агент → Системный промпт»:

```text
Помогай разбирать документы о программе «Буран».
Отвечай кратко и по существу, опираясь на найденные фрагменты.
Не додумывай даты, характеристики и причины событий.
Явно указывай, каких сведений не хватает в источниках.
```

Шаблон задаёт предмет и стиль. При RAG ON приложение по-прежнему добавляет
свой контракт `answer`/`citations` и источники; дополнительные JSON-поля или
особый формат цитат в шаблоне не задаются.

Если доступны два квантования одной исходной модели (например, 4-bit и 8-bit),
выберите их вручную по очереди в модели чата и повторите сравнение при тех же
параметрах и контексте. Доступные варианты и управление моделями описаны в
[официальном README oMLX](https://github.com/jundot/omlx/blob/main/README.md).
Смена только генеративного квантования не требует перестройки RAG-индекса:
embedding-модель, ревизию и размерность оставьте прежними. Rewrite наследует
модель чата; для сравнения самой генерации используйте уже сохранённые фрагменты.

Для качества сравните полноту, поддержку утверждений источниками и соблюдение
формата. В карточках ответов сравните «первый токен», время и ток/с, когда они
доступны; не смешивайте первую загрузку модели с повторными запросами.
Расход памяти процесса oMLX, давление памяти и swap наблюдайте в macOS
«Мониторинг системы → Память» при одинаковой фоновой нагрузке и наборе загруженных
моделей. Повторите свои запросы, отметьте отказы и обрезанные ответы. Оставьте
профиль, который показал подходящий баланс в ваших замерах; вопросы, ответы
и записи сравнения храните приватно, вне Git.

## Локальный RAG на MacBook

1. Запустите существующий oMLX и приложение (`make setup`, затем `make run`).
   В `http://127.0.0.1:8000` откройте гаечный ключ → «Настройки приложения →
   Модели»: общий URL `http://127.0.0.1:8005/v1` и существующий ключ, если
   сервер требует авторизацию. Поля сохраняются при потере фокуса;
   ключ после успешного сохранения очищается, кнопка удаления ключа явная.
   Все модели выбираются из каталога этого сервера или по точному ID вручную.
2. В «Настройках приложения → Индекс RAG» используйте корпус/индекс Недели 6.
   Проверьте опубликованную embedding-модель, ревизию и размерность. Сервер
   должен предоставлять ту же embedding-модель для вопросов: векторы другой
   модели нельзя смешивать с прежним индексом, даже при одинаковой размерности.
   После изменения формата подключения в день 27 старый индекс может
   потребовать пересборки. При смене embedding-модели заново создайте эмбеддинги
   и сохраните индекс; одного изменения выбора модели недостаточно.
3. Для пересборки достаточно сохранённых локальных HTML/корпуса,
   подготовки «Кодом» и разбиения «По размеру». На этапе «Эмбеддинги» выберите
   локальную embedding-модель; публикация — отдельный шаг «Сохранить индекс».
   Подготовка через LLM и семантическое разбиение необязательны: при включении
   у каждого этапа свой выбор локальной генеративной модели.
4. Через шестерёнку чата → «Модель» выберите локальную модель ответа, затем
   в «Поиск RAG» включите «Использовать RAG в этом чате» (по умолчанию OFF).
   Rewrite использует модель чата; модель реранкинга выбирается отдельно.
   Начать можно с выключенными Rewrite и реранкингом. Вернитесь в чат,
   введите свой вопрос и просмотрите ответ, «Источники и цитаты», сохранённый
   контекст и фактические JSON-запросы.
5. В панели oMLX `http://127.0.0.1:8005/admin` подтвердите загрузку выбранных
   моделей и обслуживание запросов на MacBook. В инспекторе RAG проверьте
   идентификатор и конфиг индекса, выбранные фрагменты; в «Информации о запросе» — ID моделей
   и переданный контекст. JSON тела сам по себе не доказывает адрес сервера:
   сверяйте его с общими настройками и фактической работой oMLX. Для проверки
   без интернета используйте уже скачанные модели и локальные документы.

## Существующий чат, RAG и память

Существующая рабочая память чата теперь передаётся в Rewrite отдельным массивом
`working_memory` с полями `kind` и `content`. Записи по-прежнему добавляет,
редактирует и удаляет человек; автоматического ведения памяти и нового слоя нет.
Текущий вопрос приоритетен: память помогает разрешить ссылки, цель и ограничения,
но не считается инструкциями или подтверждёнными фактами источников. Стиль и формат
ответа не должны попадать в поисковый запрос. Глобальная память, профиль, инварианты
и машина этапов задачи в Rewrite не передаются.

Глубокий снимок рабочей памяти фиксируется до первого ожидания обмена и используется
также основной генерацией и номерами врезок. Правки во время Rewrite действуют
со следующего вопроса. Actual JSON служебного вызова виден в существующем инспекторе,
сохраняется с ответом и копируется в ветку. Дополнительных вызовов нет; при RAG OFF
или Rewrite OFF переформулировка не запускается. История, источники и защитные
проверки RAG сохраняются. Проверены offline-контракты на нейтральных данных;
живые два сценария по 10–15 сообщений не выполнялись, качество памяти и модели
в таком диалоге здесь не подтверждается.

При RAG ON содержательный ответ содержит карточки источников
с `source`, `section`, `chunk_id` и цитатой модели. Ссылки `[1]`, `[2]` в тексте
предпочтительны, но не обязательны: ответ без них показывается без изменения. Номер соответствует позиции
полного фрагмента в сохранённом снимке поиска. Сервер проверяет структуру ответа,
соответствие ID выбранным источникам и, если ссылки в тексте есть, точное совпадение
их набора со списком цитат; метаданные
берёт из этого же снимка. Ответ публикуется после проверки. Несовпадающие ссылки или
некорректные/отсутствующие цитаты дают явную ошибку без платного повторного вызова:
ввод возвращается, перегенерация восстанавливает прежний ответ. Причина ошибки
различает незавершённый ответ, некорректный JSON/повторяющиеся ключи, поля и типы,
ID источников, пустую цитату, метаданные и несовпадение ссылок. Сообщение не включает
сырой ответ модели или значения полей. Отсутствие ссылок в тексте допускается
при корректном непустом списке цитат; ссылки автоматически не вставляются. Отмена не сохраняет
непроверенный черновик. Рассуждения, вызовы инструментов и метрики остаются видимыми.

Порог слабого контекста действует всегда при RAG ON.
Если выбранных источников нет или их максимальный cosine меньше порога, финальная модель не
запускается: «Не знаю: в базе не найдена достаточно релевантная информация.
Уточните вопрос.» Порог не исключает отдельных кандидатов до реранкинга.
После его прохождения модель отвечает на подтверждённые части составного вопроса
и явно указывает, для каких частей в источниках нет данных. Пробел в одной части
не превращается в отказ по всему вопросу. Отдельный модельный JSON-отказ не принимается. Подтверждение планирования
напоминания также не требует цитат; содержательный результат напоминания требует.

Cosine — единственная автоматическая проверка релевантности содержания.
Дословное совпадение цитаты и смысловая поддержка ответа автоматически не проверяются.
Новые ответы подписаны «Источники и цитаты»; старые снимки сохраняют прежние статусы.
Проверку на 10 вопросах своего корпуса оператор проводит локально: для каждого
содержательного ответа отмечает наличие источников, цитат и поддержку всех
утверждений приведёнными фрагментами; отдельно фиксирует корректность отказов.
Вопросы и результаты остаются приватными. Здесь проверены offline-контракты,
а не качество живой модели на пользовательском корпусе.

RAG включается отдельно для каждого чата через шестерёнку в его строке →
«Настройки чата → Поиск RAG» и по умолчанию выключен. Rewrite и реранкинг
включаются независимо; rewrite по умолчанию включён в новых чатах, реранкинг
выключен. В старых чатах отсутствующие переключатели остаются выключенными.

Два количества задаются отдельно: «Кандидатов для поиска» — по умолчанию 10,
«Чанков для ответа» — 3. Оба целые от 1 до 100, итоговое количество не больше
кандидатного. Поиск находит до 10 кандидатов; включённый реранкинг переставляет
весь найденный набор, затем первые 3 передаются модели ответа. Без реранкинга
берутся первые 3 по cosine. Предварительного cosine-фильтра нет:
кандидат с низким cosine может попасть в итоговый контекст после реранкинга.
Модель ответа получает выбранные чанки, но не обязана использовать каждый из них.

Во всех селекторах моделей есть независимый переключатель «Рассуждения (если
модель поддерживает)», по умолчанию OFF, включая старые настройки. В чате выбор
применяется также к сжатию и Rewrite; подготовка, чанкинг, реранкинг и эмбеддинги
не наследуют его. Сервер получает reasoning_effort none/medium. Дополнительные параметры не обходят OFF; неподдерживаемый
режим даёт ошибку без автоматического повтора. Совместимый сервер может игнорировать
параметр: обнаруженные reasoning-текст или положительные reasoning_tokens при OFF
дают явную ошибку с фактическими метриками. Отсутствие этих данных не доказывает,
что сервер не рассуждал внутренне. Стандартный /embeddings не имеет reasoning-параметра:
его переключатель сохраняет локальный выбор, не меняя запрос, identity или кэш индекса.
Сохранённые явные количества RAG не заменяются новыми значениями 10/3.

Query rewrite делает один дополнительный вызов текущей модели чата с отдельным
служебным промптом: текущий вопрос, последние три полные успешные пары истории
и снимок kind/content существующей рабочей памяти чата.
Результат используется только для поиска; итоговая генерация получает исходный
вопрос. Лимит ожидания — 60 секунд, автоматических повторов нет. Пустой/невалидный
JSON, незавершённый ответ или отказ модели дают явную ошибку и возвращают ввод.
Настройки чата, MCP-инструменты и инструкции не передаются служебному вызову.

Поиск берёт полные кандидаты и identity индекса из одного закреплённого SQLite
чтения. Реранкинг требует полную JSON-перестановку ID, имеет timeout 60 секунд
и не делает автоматических повторов или fallback. Промпт требует только JSON
без пояснений и полную перестановку фактически найденных ID. Разбор допускает
обычное пояснение перед единственным JSON-объектом и после него; порядок
берётся только из JSON и не исправляется по пояснению. После объекта недопустимы
`{}[]` и code fences ```/~~~: такое содержимое неоднозначно. Недостающие ID не добавляются. Ошибка различает JSON, структуру,
типы, повторы, чужие и пропущенные ID без вывода ответа модели. Он не заменяет cosine
оценками модели. Пустой поиск даёт «В базе не найдена подходящая информация»
без финальной генерации. При RAG OFF поиск, rewrite и реранкинг не выполняются.

Инспектор сохранённого ответа показывает всех кандидатов в итоговом порядке:
«Источник», «До → после», «Cosine». «До → после» и сведения модели ранжирования
видны только при фактически завершённом реранкинге. Метка «В контексте» у
источника отмечает первые N чанков, отправленные модели; полный текст каждого
кандидата доступен под таблицей. Исходный запрос, история и usage rewrite видны
только при его включении в сохранённом снимке. Старые отчёты с cosine-фильтром
и прежними лимитами читаются без переписывания и сохраняют свою диагностику.
Текущие настройки не меняют исторические источники, порядок и контекст.

Фактический JSON содержит все отправленные запросы, включая rewrite и реранкинг.
Usage каждого вызова учитывается один раз; неизвестная стоимость остаётся
неизвестной. Интерактивная ошибка возвращает ввод и временную диагностику без
записи обмена; перегенерация восстанавливает прежний ответ. Ошибка напоминания
сохраняет доступные метрики вместе с сообщением об ошибке.

Порог защиты от слабого контекста действует при каждом RAG-ответе: максимум cosine
выбранных чанков должен достигать порога (по умолчанию 0.3, от -1 до 1 включительно).
Если все кандидаты слабые, отказ возможен до платного реранкинга; иначе проверка
следует за итоговым отбором. Сохранённая политика доступна в инспекторе.

`rag` остаётся самостоятельным пакетом внутри проекта. Используется существующий
HTML-корпус и опубликованный индекс; эмбеддинги предоставляет выбранный HTTP-провайдер.
Новых сервисов, ключей и переменных окружения не требуется. Корпус, приватные кэши,
вопросы и отчёты остаются локальными данными оператора.

## Сравнение локальной и облачной генерации

Если облачная модель уже доступна, сравните её с локальной на одном сохранённом
контексте. У успешного содержательного RAG-ответа откройте «Информацию о запросе»
и скопируйте последний JSON генерации ответа, включая `messages` с вопросом,
историей и закреплёнными фрагментами. Не берите служебный запрос Rewrite,
сжатия или реранкинга. Отправьте это тело через свой HTTP-клиент в облачную
модель, заменив `model`, адрес и авторизацию; сохраняйте остальное содержимое
и параметры. Если API требует иных параметров, отметьте различия при оценке.
Это ручное сравнение генерации; облачный ответ не проходит проверки приложения.

Общий URL приложения и embedding identity для такого сравнения не меняйте:
повторный RAG-запрос к другому серверу мог бы изменить эмбеддинг вопроса,
Rewrite, ранжирование или набор фрагментов. Исторический инспектор показывает
сохранённый снимок, независимо от текущего индекса.

Оцените качество по полноте ответа, поддержке утверждений выбранными фрагментами
и корректности цитат; приложение автоматически не проверяет их дословность
или смысловую поддержку. Для скорости сравните время самой генерации,
отдельно от локального retrieval, Rewrite и реранкинга; различайте первую
загрузку модели и повторные запросы. Для стабильности повторите свои запросы,
отметьте ошибки, обрезанные ответы и нарушения формата. Вопросы, ответы,
измерения и ключи оставьте приватными, вне Git. Если облачной модели нет,
зафиксируйте это и оцените локальный вариант без облачного сравнения.

## Общие команды

Из корня репозитория, с Python >=3.11, `make` и Node.js в PATH:

```bash
make help
make setup
# Если python3.11 не в PATH или нужен другой интерпретатор >=3.11:
make setup PYTHON=/path/to/python
.venv/bin/python -m app.auth bootstrap-admin # один раз для новой базы
make run             # http://127.0.0.1:8000, автоматическая перезагрузка
make check           # весь offline-набор, включая subprocess и клиент
make check-browser   # только клиентские проверки под Node.js
```

`PYTHON` выбирает интерпретатор только для создания `.venv`. Setup проверяет
версию, создаёт окружение при отсутствии или использует существующее и
устанавливает `requirements.txt`; повторный запуск сохраняет окружение.
Он не создаёт и не перезаписывает `.env`. Все последующие Python-команды
выполняются через `.venv/bin/python`; ошибки команд дают ненулевой exit code.

URL и необязательный ключ хранятся сервером приложения в приватном
`data/model-connection.json`. Ключ не передаётся в GET и не хранится в состоянии
клиента или localStorage; браузер отправляет только явно введённое новое значение.
Приложение не использует `.env` или переменные ключей для подключения моделей.
Аккаунты — `data/accounts.db`, личные базы — `data/users/<uuid>/agents.db`;
корпус/индекс — `data/rag`, MCP конфиг — `mcp.json`. Старый `data/agents.db` не импортируется.
Новые чаты и LLM-этапы требуют явного выбора модели; сохранённые ID сохраняются.
Секреты и пользовательские данные не выводите и не коммитьте; используйте
только точечный `git add`, никогда `git add -A` или `git add .`.

## Проверки

Проверки используют временный нейтральный CP1251 HTML, настоящий HTTP embedding
stub, отдельный CLI и SQLite, без живого инференса. Проверяются chunk slices,
cache fingerprint, cosine, валидация векторов, atomic failure, writer lock,
interrupted/stale, bounded API и настоящий клиент под Node с lazy vector/late GET.
День 22 проверяется на нейтральных временных снимках и HTTP-заглушках: ON/OFF,
согласованность контекста и сохранённого снимка, ошибки поиска до генерации,
история после изменения индекса и переключение настройки текущего чата.
День 23: полный реранкинг кандидатов и отбор первых N, три пары rewrite, strict stop и JSON, отмена/timeout,
пустой отбор без генерации, реальные JSON/usage, legacy/restart/ветвление и напоминания.
День 24: ссылки и ID источников из закреплённого снимка, частичный ответ и отсутствие дословной проверки цитат,
строгий формат и stop, буферизация ответа, явная ошибка без retry, порог выбранного контекста,
ошибка неподдерживаемого формата модельного отказа, paid diagnostics и восстановление/ветвление/отмена.
Сохраняется весь offline-набор предыдущих дней: чат, память, задачи, MCP и pipeline.

Подробности: [архитектура](docs/architecture.md), [карта клиента и ручной просмотр](docs/client-guide.md).

## Как запустить

### Где находятся настройки

Кнопка с гаечным ключом справа в шапке открывает «Настройки приложения»: общий адрес совместимого сервера
моделей, профиль ответа, долговременную память, инварианты, подключения MCP и
пайплайн RAG (документы, разбиение, эмбеддинги, публикация и просмотр индекса).
Профиль, память и инварианты относятся к текущему аккаунту и его чатам.
Общий URL/ключ, MCP и RAG pipeline доступны только администратору.

Шестерёнка рядом с карандашом в строке чата открывает «Настройки чата»:
модель генерации со всеми параметрами ответа, системный промпт и
управление контекстом агента, краткосрочную и рабочую память, использование
RAG с rewrite, реранкингом и отбором контекста. Раздел «Напоминания» появляется только
при подключённом MCP-сервере с подтверждённой поддержкой напоминаний, даже
если список пуст. Он показывает состояния и отмену принадлежащих чату задач.
Общий каталог инструментов остаётся только в настройках приложения. Управление подключениями MCP находится в настройках
приложения, где нет кнопок отмены напоминаний конкретного чата.

Общей смешанной верхней вкладки «Настройки» нет. «Вернуться в чат» закрывает
настройки без прерывания ответа и сохраняет ввод. Исторический инспектор RAG
открывается у ответа отдельно, доступен только для чтения и показывает его
сохранённый снимок, независимо от текущих настроек.

После удаления последнего чата создаётся один новый. Пустой список при запуске
или открытие общих настроек сами чат не создают. При ошибке создания удалённая
переписка исчезает с экрана; кнопка «Новый чат» позволяет повторить попытку.

### Чат с RAG

Сначала опубликуйте индекс через этапы ниже. Нажмите шестерёнку рядом с
карандашом в строке чата → «Поиск RAG» и включите
«Использовать RAG в этом чате». Нажмите «Вернуться в чат» и задайте вопрос.
Просмотрите источники под ответом и сохранённый контекст. Кнопка «К текущему
индексу» возвращает к существующим этапам индексации, не меняя историю ответа.
Отключение checkbox возвращает обычную генерацию для следующих вопросов.
Для сравнения режимов включите RAG и настройте rewrite, реранкинг и оба количества рядом.

### Индексация из терминала

Подготовьте **локальный** JSON manifest, например `data/rag/inputs.json`:

```json
[
  {"path": "article.html"}
]
```

Относительный path разрешается относительно manifest. Для HTTP-входов
добавьте объект с полем `url`; для локальной копии можно задать `source`.
Можно повторять `--url` вместо manifest. CLI не импортирует конфигурацию чата
и не читает `.env`.
Приложение использует фиксированный каталог `data/rag`; CLI использует его по умолчанию,
а `--root` позволяет оператору работать с отдельным каталогом.
Перед командами с connection-file сохраните подключение в настройках приложения:

Примеры ниже используют OpenAI-совместимый сервер на порту 8005;
укажите фактический адрес и ID модели своего сервера.

```sh
.venv/bin/python -m rag ingest --manifest data/rag/inputs.json
.venv/bin/python -m rag --connection-file data/model-connection.json index \
  --model YOUR_EMBEDDING_MODEL --batch-size 16
.venv/bin/python -m rag status
make run
```

Команды с `--connection-file data/model-connection.json` используют подключение,
сохранённое в настройках приложения. Для отдельного CLI можно явно указать
другой приватный JSON-файл с `base_url` и необязательным `api_key`; держите его
вне Git. Без `--connection-file` CLI использует `http://127.0.0.1:8005/v1`
без ключа. CLI не читает `.env`; ID модели задаётся явно через `--model`.

Ingest сохраняет frozen corpus.json и ingest-report.json с ошибками/словами и
оценкой страниц; при любом отказе прежний корпус остаётся. Повторный index
использует кэш. Сборка пишет временную SQLite и атомарно заменяет index.sqlite
только после успеха; прежний индекс доступен при ошибке/остановке. Один OS lock
исключает конкурирующих писателей. Atomic replace — граница успеха; отказ записи
завершающего progress после replace оставляет новый индекс готовым и даёт
диагностическое предупреждение, без обещания отката опубликованной SQLite.
Изменённый корпус отмечает индекс как stale.

Сравнение выполняется отдельно в терминале на том же frozen corpus и конфиге:

```sh
.venv/bin/python -m rag --connection-file data/model-connection.json compare \
  --model YOUR_EMBEDDING_MODEL
```

Оба индекса сохраняются в `comparisons/fixed` и `comparisons/structural`,
локальный comparison.json содержит число чанков, длины, перекрытие, разделы,
модель и fingerprint. Активный индекс не заменяется. Это сравнение разбиения;
качество ответа/поиска на контрольных вопросах здесь не измеряется.

### Отдельные этапы CLI

Отдельные CLI этапы (прежний `index` также поддерживается):

```sh
.venv/bin/python -m rag chunks --strategy fixed --size 1200 --overlap 180
.venv/bin/python -m rag --connection-file data/model-connection.json chunks \
  --strategy semantic --size 1200 --overlap 180 --semantic-model YOUR_GENERATIVE_MODEL
.venv/bin/python -m rag --connection-file data/model-connection.json embed --model YOUR_EMBEDDING_MODEL
.venv/bin/python -m rag save
.venv/bin/python -m rag clear index  # сохраняет все предыдущие этапы и кэши
.venv/bin/python -m rag clear embeddings
.venv/bin/python -m rag clear chunks
```

### Просмотр и запуск этапов в UI

Откройте `http://127.0.0.1:8000` → кнопка «Настройки приложения» → «Настройки приложения → Индекс RAG». Страница работает
без чата/ключа, читает фактические стадии CLI `documents → chunks → embeddings → save`,
счётчики кэша/новых векторов, длительность, модель и размерность. После сохранения
видны объём корпуса, версия/байты/число строк SQLite, документы и чанки с
границами/текстом/метаданными. Раскрытие отдельно читает настоящий числовой
вектор выбранного чанка. Refresh открывает сохранённый индекс; missing/stale/
interrupted/error названы явно, предыдущий индекс при отказе виден отдельно.
UI запускает отдельные этапы «Загрузить документы» → «Разбить на чанки» →
«Создать эмбеддинги» → «Сохранить индекс». Укажите явные URL; локальный HTML
доступен только из фиксированного manifest `data/rag/inputs.json`, без ввода путей в HTTP.
На этапе «Документы» выберите подготовку «Кодом» (по умолчанию) или
«Полностью через LLM»: генеративная модель получает HTML, очищает его и
восстанавливает структуру без пересказа. Чат, подготовка, семантическое разбиение,
эмбеддинги и реранкинг используют один компонент выбора модели из каталога
общего сервера. URL и необязательный ключ задаются в
«Настройках приложения → Модели». Каждый этап сохраняет собственный точный ID.
Модель подготовки, токены и
фактическая стоимость доступны в «Фактическое состояние операции».
Для медленной локальной модели увеличьте «Ожидание ответа, с»: по умолчанию
600 секунд, допустимо 1–3600; настройка относится только к подготовке документов.
Размер и перекрытие задаются в символах. Для LLM поле называется
«Максимальный размер чанка»: модель выбирает смысловые границы, код ограничивает
размер групп и добавляет заданное перекрытие. В UI доступны «По размеру» и
«Семантическое · LLM». Модель нужно выбрать явно из каталога общего сервера
или ввести её ID вручную. В CLI подключение задаётся через `--connection-file`,
а генеративная модель разбиения — через `--semantic-model`.
Модель разбиения выбирается отдельно от модели эмбеддингов.
«Обновить модели» перечитывает общий каталог; введённые и сохранённые точные ID
сохраняются даже при отсутствии в каталоге. Неизвестные цены и параметры не
выдаются за нулевые. Query rewrite использует модель текущего чата.
LLM возвращает
границы абзацев, а приложение сохраняет точные исходные срезы. Проверенный
кэш исключает повторные вызовы на том же корпусе/конфиге; в разделе
«Фактическое состояние операции» доступны
фактические вызовы, модель, токены и стоимость провайдера; trace остаётся
приватным. Компактные строки документов/чанков отмечают выбранный ID синим;
смена документа сразу очищает старый чанк и вектор. Документ и чанки можно
проверить до публикации; создание эмбеддингов не заменяет индекс. Ключ берётся из общего сохранённого подключения приложения. Открытые details,
выбор, черновик и фокус сохраняются при опросе. Удаление эмбеддингов сохраняет
документы/чанки, удаление чанков сохраняет документы; оба удаляют downstream
индекс и кэш. UI не сравнивает стратегии. Смена общего адреса при той же embedding-модели
не требует перестройки: поисковый вектор использует текущий адрес, но модель,
размерность и revision опубликованного индекса. Его fingerprint не переписывается.
Другая модель или несовместимая размерность требуют явной перестройки индекса.

## Работа с OpenCode и Pi

Запускайте установленный инструмент из корня этого worktree:

```bash
cd /path/to/ai-challenge-9-week-01
opencode
# Или:
pi
```

Корневой [AGENTS.md](AGENTS.md) автоматически попадает в контекст
[OpenCode](https://opencode.ai/docs/rules/) и
[Pi](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/configuration.md).
Он требует перед изменениями прочитать нужные разделы
[архитектуры](docs/architecture.md): ссылка сама по себе не загружает их
содержимое. Модель и авторизацию настраивайте лично в выбранном инструменте
(OpenCode — пользовательские настройки/подключение провайдера;
Pi — `/login`, `/model`, настройки в `~/.pi/agent`). Эти настройки и
учётные данные не переносите в репозиторий или `.env` приложения.
`mcp.json` настраивает MCP-серверы самого чат-приложения, а не OpenCode/Pi.

## Что осталось честно назвать

* **Локальный корпус и объём**: репозиторий не содержит подготовленного снимка
  ≥15000 очищенных слов; объём нужно проверить в ingest-report и инспекторе
  после собственного запуска. Ориентир задания: ≥15000 слов ≈30 страниц
  по 500 слов. Эвристики legacy HTML требуют просмотра очищенного текста;
  счётчик сам по себе не подтверждает качество.
* **Только явные HTML-входы**: загрузчик не обходит сайт, не читает PDF
  и не делает OCR.
* **Сравнение разбиения**: CLI сравнивает fixed и structural на одном frozen
  корпусе; UI сравнения нет. Отчёт описывает чанки, не качество ответов.
* **Оценка качества**: набор из 10 вопросов, ожидания и сравнение ответов нужно
  подготовить и провести локально. Автоматически проверяются формат и ID источников;
  дословность цитат и смысловая поддержка ответа остаются ручной оценкой.
  Найденный источник не гарантирует верный ответ.
* **Offline-проверки — проверка контрактов**: живой инференс и качество поиска
  на архиве здесь не измеряются. Модель и сервер запускает оператор;
  приложение не скачивает веса.
